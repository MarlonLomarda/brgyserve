# Rental bookings — module rules

This file holds the rules and current state of the Rental bookings list: `pages/RentalBookingsPage.jsx`, which is the Secretary's `/secretary/rentals` and the home page of Staff (`/staff`) and of the Punong Barangay (`/punong-barangay`). It was started on 14 Oct 2026 with the first of four batches (R1 to R4) that bring the Document requests list's improvements to it (see `docs/modules/document-requests.md`). **It is NOT loaded automatically, and it MUST be read before changing the Rental bookings list.** The module's design (self-service booking, the stored and derived statuses, fees through the charges system) stays in `CLAUDE.md` under "Facility Rentals".

## Rental bookings list

- **A failed load is an error, never an empty list** (`013640b`). The list used to store an empty list beside the server's bare message, so the page said "0 bookings" and "No confirmed / upcoming bookings." while it knew nothing, with no Try again. Now `requests` stays `null` on failure and the list area checks the error first, then loading, then empty, then rows (CLAUDE.md: a list that failed to load).
  - **The words:** "Could not load the bookings: <reason>" (`role="alert"`) with a **Try again** button where the rows would be; the heading reads "Bookings" while the list loads or after it failed, and "Loading bookings…" shows while a load is out. The reason is the server's own message, or "the server did not respond" when there is none (a server that cannot be reached, or an error answer with no message): `loadFailure()`, a copy of the Document requests and Payments pages' function, not shared with them.
  - **Every load starts from the loading state** (the first open, Refresh, Try again, and the reload after an action), and loads are numbered (`loadSeq`) so an older answer that arrives late, successful or failed, is dropped instead of replacing a newer one.
  - **A 401** ends the session once, in `authFetch`, and the route guard shows the login screen; the list never says "0 bookings" there either.
- **The list is six status tabs over ONE load** (`515a205`). The page sends `GET /api/rental-requests?status=all` once and splits the bookings in the browser: **Upcoming, Overdue, Completed, Returned, Cancelled, All**, each with its count over the whole list, so the counts read the same on every tab. A tab with none is dimmed and still pressable (it shows its empty text). The strip is `components/ListTabs.jsx`, as on Document requests, in a group named "Status".
  - **A booking is in the tab of the status its badge reads,** `displayStatus()` in `constants/rentals.js`: the server's `derived_status`. **Upcoming** is a confirmed booking whose end is still ahead, begun or not (`derived_status` "confirmed"; its badge says Confirmed). **Overdue** is a confirmed booking of equipment or furniture whose end has passed and that nobody has marked returned; **Completed**, a confirmed facility booking whose end has passed. **Returned** holds the three return outcomes (returned, returned late, returned with an issue), which their badges tell apart. A status outside these seven is counted under All only.
  - **NEVER split the list on the stored status.** The select the tabs replaced did: its first choice, "Confirmed / upcoming", asked the route for `?status=confirmed`, which is the STORED status, so it listed every past confirmed booking as well. On the live data (14 Oct 2026: 28 bookings, 15 stored as confirmed, 7 of them overdue and 8 completed) it showed 15 bookings under "upcoming", none of them upcoming. `test:auth` section AD fails a tab or a count that reads the stored status.
  - **The time comparison stays the server's** (`deriveStatus()` in `routes/rentalRequests.js`): the page never compares a booking's dates with the clock. A list loaded before a booking's end passes keeps it under Upcoming until the next load (Refresh).
  - **A tab must never send a request.** `load` depends on `authFetch` alone; putting the tab into its dependencies reloads on every press, and `test:auth` section AD fails it. The route's `?status=` filter is unchanged (other values still work for any other caller); this page simply no longer asks per status.
  - **The tabs, their order and their words are set in `utils/rentalList.js`:** `RENTAL_TABS`, `inTab`, `tabCounts`, `tabHeading`, `emptyText`, `openingTab`. No React; `test:auth` checks each case by case.
  - **The page opens on Overdue for Staff** (`canReturn`), as the select did, **and on Upcoming for the Secretary and the Punong Barangay, even while it is empty,** as it is on the live data: "0 upcoming bookings" and "No upcoming bookings.".
  - **The heading names the tab:** "7 overdue bookings", "1 overdue booking", "0 upcoming bookings", "28 bookings" on All. **The empty text names it too:** "No upcoming bookings.", "No returned bookings.", "No bookings." on All.
  - **The chosen tab lives through every reload:** Refresh, Try again, and the reload after a saved edit, a recorded return, a cancel or a filed walk-in. Back from the Edit, Mark returned or walk-in panel without saving loads nothing, as before. A booking whose status an action changed is under its new tab after the reload (a cancelled booking under Cancelled, a returned one under Returned). The tab is kept nowhere in the browser: every visit starts on the opening tab. While the list loads or after it fails, no tabs are drawn.
  - **The columns are unchanged:** Booked for, Item, Schedule, Qty, Purpose, Status, and the actions column for the Secretary and Staff, with the same badges, notes and actions. Since R3 the Booked for and Status cells also hold the booking number and the payment marker (below). The Secretary has Edit and Cancel on every booking stored as confirmed, past ones (Overdue, Completed) included; Staff have Mark returned on stored-confirmed equipment and furniture, upcoming or overdue; the Punong Barangay has no actions column. **No role has a View button on this page.**
- **The strip's look is the shared `.pay-tabs` rules in `index.css`**, so **a change to any `.pay-tabs` / `.pay-tab*` rule now changes three pages (Payments, Document requests, Rental bookings): measure all three.** R1 added no CSS; R2 added the two page-scoped rules below; R3 added no rule, only two comments, reusing Document requests' classes by name (below).
- **The list has a search box** (`020203a`, R2), in a row of its own under the heading row and over the tabs: `components/ListToolbar.jsx` as it is, the Document requests box, named "Search bookings". It filters the loaded list as you type, with no request, through `utils/chargeSearch.js`'s `normalise`, `searchTerms` and `matchesTerms` as they are: case, accents and extra spaces ignored, every word required, in any order, part of a word matching ("cru" finds "Cruz"). The tabs split what matches: their counts follow the search, a tab left with none is dimmed, and the chosen tab stays.
  - **The words.** With no search the heading is the tabs' ("7 overdue bookings", "28 bookings"). With one it reads "4 of 7 overdue bookings match", "9 of 28 bookings match" on All: `searchHeading()`, Document requests' words, the verb agreeing with the first number ("1 of 7 overdue bookings matches") and the noun with the second ("0 of 1 overdue booking match"). The heading is a polite live region. A tab whose bookings the search hides reads 'No overdue bookings match "x"' (`noMatchText()`, naming the tab; 'No bookings match "x"' on All) with a **Clear search** button, which clears the search only, keeps the tab and puts focus in the box; a tab with none and no search keeps its R1 text ("No upcoming bookings."). The placeholder is "Search name, account or item" while a row carries an account and "Search name or item" otherwise (`searchPlaceholder()`, decided from the data); it is cut by 1.6px at 320 (209.6px of text, 208 of room) and fits from 342.
  - **A search reads ONLY what a row shows of who and what:** `searchParts()` in `utils/rentalList.js`, which is the name in the Booked for column (`bookedForName()`: the resident's full name, or the guest's name as typed; the requester's name, then "@username", only as the last fallbacks, which the row then shows too), the @account under it (`accountHandle()`, never on a guest's row), the booking number under them ("#12", `bookingNumber()`, since R3, below) and the item's name. **Never the purpose, a guest's contact number (which the row does show, "Guest · 09…"), an email, the filer (the requester), the returner, a return note, the schedule, a status word, the payment marker's words, or the words "Guest" and "No online account".** The row reads `bookedForName`, `isGuest`, `accountHandle` and `bookingNumber` from the same file, so the row and the search cannot disagree. Anything added to the row joins `searchParts` in the same change, or is kept out of it on purpose, as the marker is. `test:auth` sections AE and AF fail a search that reaches any of them.
  - **All three roles' payloads carry the account** (one projection, `MANAGE_FIELDS` in `routes/rentalRequests.js`), so all three rows show "@handle" and all three searches find it, unlike Document requests, where Staff's projection withholds it. The test is still on the data (`"account" in record`), never the role; and the requester's username is never read: on a self-service booking it is the same account, on a walk-in the Secretary's.
  - **The search lives through every reload** (Refresh, Try again, the reload after an action) and through Back from Edit, Mark returned or Encode walk-in, which loads nothing (focus then lands on the page body, as before); it is kept nowhere in the browser. A keystroke never sends a request. Like the tabs, the box is not drawn while the list loads or after a failed load.
- **The list has a pager** (`c22a717`, R2) under the rows, from 11 matches: `components/ListPager.jsx` and `utils/paging.js` as they are, the Document requests bar. Rows per page 10, 25, 50 or 100, 25 to start, never stored. Only the rows drawn are a page: the heading and the tab counts count every match, and the search runs over the whole list before paging. A tab, a search (typed, the x, Escape or Clear search) or a new Rows per page goes back to page 1; Rows per page stays through a tab or a search. Refresh, Try again, Back and the reload after an action keep the page; a list that shrank under it lands on its last page and stays there (the clamp in render, skipped while a list loads), never on an empty page past the end. A page change sends no request. The pager is not drawn while the list loads or beside a failed load.
  - **A page change brings the heading into view**, and `.rental-bookings-head h2` takes the scroll margin the sticky header needs: 16px, and 126px at 1045px and below (`index.css`, beside Document requests' pair, inside the same `@media (max-width: 1045px)` block, so the file has no more 1045px blocks than before).
  - **The list keeps ONE order** (`orderBookings()` in `utils/rentalList.js`, applied to each load as it arrives, so before the search, the tabs and the pager): the route's, newest `start_datetime` first, and among bookings that start at the same moment, the higher `request_id` first. The route orders by start alone, with no tie-breaker, and four live bookings share one start, so the same bookings could come back in another order on every load and a page could show a row twice or leave one out. The times are compared, not the text; a start that cannot be read goes last. **A later sort must not undo it.** `test:auth` section AD's eleven bookings each start a day apart since R2, so its "in the order sent" is also this order.
- **On a phone the heading has a line of its own** (`94d2f4b`, R2): `.rental-bookings-head h2 { flex-basis: 100% }`, inside the ISSUE 7 640px block of `index.css`, beside Document requests' rule; the class is on this page's heading `.list-head` alone, never the search row's. The heading names the tab and, while a search is on, how many match, so its length changes with every tab and keystroke; where it fitted beside Refresh (and Encode walk-in) on some tabs and not others, a tab press or a keystroke moved the strip and the list by 32px. Swept pixel by pixel on the tree before the rule: 342 to 526px for the Secretary (342 to 420 with no search) and 320 to 392px for Staff and the Punong Barangay once a search was on. **Now nothing moves at any width from 320 to 1920**, for the three roles, on every tab, with no search and with two. **The price:** the heading row is 72px at 640 and below on every tab (the heading, then Refresh under it), where it was 40 wherever the heading fitted. Above 640px the row is as it was. Do not reuse `.doc-requests-head` for it, or the reverse: that would tie the two pages' heading rules together.
  - **Not covered, at 320px only:** a heading wider than the row wraps onto two lines and makes the row taller on that tab and search. On the list shaped to the live one the longest heading is "1 of 8 completed bookings matches", 281.4px against the heading's 288 at 320, so nothing wraps. Once Completed holds ten or more bookings, a search that leaves exactly one of them reads "1 of 10 completed bookings matches", 291.1px, and wraps at 320 (it fits from 342); every other tab's longest such heading fits ("1 of 10 upcoming bookings matches", 286.7px), and so do two-digit counts on both sides ("12 of 28 completed bookings match", 284.3px). Document requests has the same limit at 320 on Ready for release.

- **Every row shows its booking number and a payment marker** (`87c696f`, R3), in cells the table already had: still the same headers and cells, so no new column.
  - **The number** is a line of its own under the Booked for name and the line under it: "#12", as the Edit and Mark returned panels name a booking (`bookingNumber()`). - **The list has a filters row** (`914781c`, R3) under the search and over the tabs: `components/ListFilters.jsx` as it is, drawn only once the list has loaded, like the search and the tabs. Three native selects, each with its visible label, the same for the three roles:
  - **Item:** "Any item", then each item the loaded bookings hold, once, sorted by name with case ignored ("stick" comes before "Tables"), matched by the whole name ("Tables" never takes "Folding Tables"). "Any item" is the empty value, never `ANY` ("any"), because an item could be named "any". **A booking reads its item's name live:** `rental_requests` stores only `item_id`, and the list embeds the item. So after the next load a renamed item is one choice under its new name, old bookings included, and a deactivated item (`is_active` false, which the list neither filters on nor sends) is still offered while a loaded booking holds it: the choices are the bookings', never the active items list (`GET /rental-items`). Grouping by name is grouping by item, because no two items, active or not, may share a name (case ignored; `nameTaken()` in `routes/rentalItems.js`).
  - **Payment:** "Any payment", Paid, Unpaid, No fee and Not billed, and Void last, only while a loaded booking's marker says Void (on the live list five do): Document requests' own `paymentOptions()` and `matchesPayment()`, handed on as they are, so a booking matches the choice its own marker shows and the filter and the row cannot disagree.
  - **Starts:** the Manila day a booking starts on (`matchesStarts()`, through `utils/chargeFilters.js`'s `manilaDay` and `backwards` as they are), whatever clock the computer keeps. Any date, Today, Next 7 days, Next 30 days, Last 7 days, Last 30 days and Choose dates (From and To, both ends in): both ways, because bookings are made ahead and looked back on. Each preset counts today: Next 7 days is today and the six days after it, as Payments' Last 7 days is today and the six before (`startsRange()`; a copy of `chargeFilters.js`'s `addDays`, which it does not export). A booking runs within one Manila day by construction (the route builds it from one date and two times at +08:00), so its start day is its day. From after To shows "The start date is after the end date." and matches nothing; it is never swapped, as on Payments. **The Schedule column still shows the browser's time zone** (`formatSchedule`), as Document requests' Submitted column does: on a computer not set to Philippine time a booking near midnight can read one day in its row and be counted on another; on the barangay's computers the two agree.
  - **The list shown is tab AND search AND filters.** The tab counts, the heading ("3 of 5 upcoming bookings match": the tab's count with no search and no filter is the second number) and the pager count what the search and the filters leave. Any filter change goes back to page 1. "Choose dates" with no date yet restricts nothing (the heading stays "5 upcoming bookings") but is a filter on.
  - **Clear filters,** while any of the three is off Any, clears the three, keeps the search and the tab, and moves focus to the Item select; while none is on it keeps its place, disabled and `aria-hidden`. **Where the filters leave a tab nothing,** with or without a search, the text is "No overdue bookings match your search or filters." (`filtersNoMatchText()`, naming the tab; "No bookings match your search or filters." on All) with **"Clear search and filters"**, which clears both, keeps the tab and puts focus in the search box. A search alone keeps its own text and Clear search.
  - **No request, nothing stored.** A filter change never sends a request. The filters start at Any on every visit, live through Refresh, Try again, a tab, a search, a page change, Back from a panel and the reload after an action, and are kept nowhere in the browser. **A choice a reload no longer offers** (its item renamed, the last void charge no longer void) **goes back to Any, and the page to 1.**

It opens and closes the row as a panel in place; Escape in the open panel or on the button closes it and gives focus back to the button. Its open state is the page's (`filtersOpen`), closed on every visit, kept through every reload and Back, and kept nowhere in the browser.

R3 added no rule for it, only a comment in `index.css`. **A change to the `.doc-requests-filters` rules changes both lists: measure both.**
