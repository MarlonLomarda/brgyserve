# Rental bookings — module rules

This file holds the rules and current state of the Rental bookings list: `pages/RentalBookingsPage.jsx`, which is the Secretary's `/secretary/rentals` and the home page of Staff (`/staff`) and of the Punong Barangay (`/punong-barangay`). It was started on 14 Oct 2026 with the first of four batches (R1 to R4) that bring the Document requests list's improvements to it (see `docs/modules/document-requests.md`). Since 16 Oct 2026 it also holds the resident's two rental pages, My rentals and Book a rental (below). **It is NOT loaded automatically, and it MUST be read before changing the Rental bookings list or the resident's rental pages.** The module's design (self-service booking, the stored and derived statuses, fees through the charges system) stays in `CLAUDE.md` under "Facility Rentals".

## Rental bookings list

- **A failed load is an error, never an empty list** (`013640b`). The list used to store an empty list beside the server's bare message, so the page said "0 bookings" and "No confirmed / upcoming bookings." while it knew nothing, with no Try again. Now `requests` stays `null` on failure and the list area checks the error first, then loading, then empty, then rows (CLAUDE.md: a list that failed to load).
  - **The words:** "Could not load the bookings: <reason>" (`role="alert"`) with a **Try again** button where the rows would be; the heading reads "Bookings" while the list loads or after it failed, and "Loading bookings…" shows while a load is out. The reason is the server's own message, or "the server did not respond" when there is none (a server that cannot be reached, or an error answer with no message): `loadFailure()`, a copy of the Document requests and Payments pages' function, not shared with them.
  - **Every load starts from the loading state** (the first open, Refresh, Try again, and the reload after an action), and loads are numbered (`loadSeq`) so an older answer that arrives late, successful or failed, is dropped instead of replacing a newer one.
  - **A 401** ends the session once, in `authFetch`, and the route guard shows the login screen; the list never says "0 bookings" there either.
- **The list is six status tabs over ONE load** (`515a205`). The page sends `GET /api/rental-requests?status=all` once and splits the bookings in the browser: **Upcoming, Overdue, Completed, Returned, Cancelled, All**, each with its count over the whole list, so the counts read the same on every tab. A tab with none is dimmed and still pressable (it shows its empty text). The strip is `components/ListTabs.jsx`, as on Document requests, in a group named "Status".
  - **A booking is in the tab of the status its badge reads,** `displayStatus()` in `constants/rentals.js`: the server's `derived_status`. **Upcoming** is a confirmed booking whose end is still ahead, begun or not (`derived_status` "confirmed"; its badge says Confirmed). **Overdue** is a confirmed booking of equipment or furniture whose end has passed and that nobody has marked returned; **Completed**, a confirmed facility booking whose end has passed. **Returned** holds the three return outcomes (returned, returned late, returned with an issue), which their badges tell apart. A status outside these seven is counted under All only.
  - **NEVER split the list on the stored status.** The select the tabs replaced did: its first choice, "Confirmed / upcoming", asked the route for `?status=confirmed`, which is the STORED status, so it listed every past confirmed booking as well. On the live data (14 Oct 2026: 28 bookings, 15 stored as confirmed, 7 of them overdue and 8 completed) it showed 15 bookings under "upcoming", none of them upcoming. `test:auth` section AD fails a tab or a count that reads the stored status.
  - **The time comparison stays the server's** (`deriveStatus()` in `routes/rentalRequests.js`): the page never compares a booking's dates with the clock. A list loaded before a booking's end passes keeps it under Upcoming until the next load (Refresh).
  - **A tab must never send a request.** `load` depends on `authFetch` alone; putting the tab into its dependencies reloads on every press, and `test:auth` section AD fails it. The route's `?status=` filter is unchanged (other values still work for any other caller); this page simply no longer asks per status.
  - **The tabs, their order and their words are set in `utils/rentalList.js`:** `RENTAL_TABS`, `inTab`, `tabCounts`, `tabHeading`, `emptyText`, `openingTab`. No React; `test:auth` checks each case by case.
  - **The page opens on Overdue for Staff** (`canReturn`), as the select did, **and on Upcoming for the Secretary and the Punong Barangay, even while it is empty,** as it is on the live data: "0 upcoming bookings" and "No upcoming bookings.".
  - **The heading names the tab:** "7 overdue bookings", "1 overdue booking", "0 upcoming bookings", "28 bookings" on All. **The empty text names it too:** "No upcoming bookings.", "No returned bookings.", "No bookings." on All.
  - **The chosen tab lives through every reload:** Refresh, Try again, and the reload after a saved edit, a recorded return, a cancel or a filed walk-in. Back from the Edit, Mark returned or walk-in panel without saving loads nothing, as before. A booking whose status an action changed is under its new tab after the reload (a cancelled booking under Cancelled, a returned one under Returned). The tab is kept nowhere in the browser: every visit starts on the opening tab. While the list loads or after it fails, no tabs are drawn.
  - **The columns are unchanged:** Booked for, Item, Schedule, Qty, Purpose, Status, and the actions column for the Secretary and Staff, with the same badges, notes and actions. Since R3 the Booked for and Status cells also hold the booking number and the payment marker, and since R4 the columns stand in place above 640px and a returned booking's note reads "Returned by @…" (below). The Secretary has Edit and Cancel on every booking stored as confirmed, past ones (Overdue, Completed) included; **since step B2 they are drawn only where the list's `not_started` is true** (stored confirmed and the start still ahead, the server's own rule; see "Edit and Cancel" below), so never on an Overdue, Completed or under-way booking; Staff have Mark returned on stored-confirmed equipment and furniture, upcoming or overdue; the Punong Barangay has no actions column. **No role has a View button on this page.**
- **The strip's look is the shared `.pay-tabs` rules in `index.css`**, so **a change to any `.pay-tabs` / `.pay-tab*` rule now changes three pages (Payments, Document requests, Rental bookings): measure all three.** R1 added no CSS; R2 added the two page-scoped rules below; R3 added no rule, only two comments, reusing Document requests' classes by name (below); R4 added the table's own column blocks and the returned-by note's rules, every one page-scoped (below).
- **The list has a search box** (`020203a`, R2), in a row of its own under the heading row and over the tabs: `components/ListToolbar.jsx` as it is, the Document requests box, named "Search bookings". The tabs split what matches: their counts follow the search, a tab left with none is dimmed, and the chosen tab stays.
  - **The words.** With no search the heading is the tabs' ("7 overdue bookings", "28 bookings"). With one it reads "4 of 7 overdue bookings match", "9 of 28 bookings match" on All: `searchHeading()`, Document requests' words, the verb agreeing with the first number ("1 of 7 overdue bookings matches") and the noun with the second ("0 of 1 overdue booking match"). Anything added to the row joins `searchParts` in the same change, or is kept out of it on purpose, as the marker is. `test:auth` sections AE and AF fail a search that reaches any of them.
  - **All three roles' payloads carry the account** (one projection, `MANAGE_FIELDS` in `routes/rentalRequests.js`), so all three rows show "@handle" and all three searches find it, unlike Document requests, where Staff's projection withholds it. The test is still on the data (`"account" in record`), never the role; and the requester's username is never read: on a self-service booking it is the same account, on a walk-in the Secretary's.

A keystroke never sends a request. Like the tabs, the box is not drawn while the list loads or after a failed load.

The route orders by start alone, with no tie-breaker, and four live bookings share one start, so the same bookings could come back in another order on every load and a page could show a row twice or leave one out. The times are compared, not the text; a start that cannot be read goes last. **A later sort must not undo it.** `test:auth` section AD's eleven bookings each start a day apart since R2, so its "in the order sent" is also this order.

## Edit and Cancel (step B1, 25 Oct 2026)

The server rules, decided by the owner on 25 Oct 2026 (step B1), and the screens that follow them (step B2). **B1 and B2 must ship together:** the server refuses a Secretary cancel that carries no reason, which is what the Cancel button before B2 (a `window.confirm`, no body) sent.

- **"Has not started" is one rule behind both Secretary actions:** stored status `confirmed` AND the stored start still ahead (`hasNotStarted()` in `routes/rentalRequests.js`). An Overdue or Completed booking was used, so it can be neither edited nor cancelled. The refusals are 409s: "Only a booking that has not started can be changed." and "Only a booking that has not started can be cancelled."
- **Edit (`PUT /:id`, Secretary)** changes the date, the start and end time and the purpose of ANY booking that has not started, online or walk-in. **The item, the quantity, the borrower, the guest fields and the status are fixed:** to change the quantity or the item, cancel and book again. A body carrying a different `quantity_requested` gets a 400, "The quantity cannot be changed. Cancel this booking and book again."; the same number is accepted (the Edit panel still sends it), and a body without one keeps the stored quantity. The rest of the validation is as before: the new start must be ahead, one day, the conflict check with this booking excluded, before and again after the update, with the old date, times and purpose put back on a clash.
  - **The charge is never touched by an Edit.** The fee is item fee × quantity once per booking, so a new date or time changes nothing owed; the old branch that recomputed an UNPAID charge on a quantity change was removed with the quantity edit.
  - **The borrower is notified of every edit that changed something:** "BrgyServe: your booking of {item} was changed by the barangay. It is now {date}, {start} to {end}." — to the resident's account and record number, or to a guest's typed number. A save that changed nothing sends nothing and logs nothing.
  - **An edit does not write `processed_by_user_id`** (it never did; the schema doc used to say it did).
- **Secretary Cancel (`POST /:id/cancel`)** needs a **reason**, trimmed, 3 to 300 characters (counted as Postgres counts them), stored in `rental_requests.cancellation_reason` (migration 023) and sent to the borrower: "BrgyServe: your booking of {item} on {date} was cancelled by the barangay. Reason: {reason}." When the charge is PAID above PHP 0 the notice adds " You paid PHP {amount}. Please contact the barangay about your refund."
- **The resident's own cancel (`POST /mine/:id/cancel`)**, under the `/mine` scoping, is allowed only on the resident's OWN ONLINE booking — `resident_id` is their linked record AND `requested_by_user_id` is their own account — while it is confirmed, at least 24 hours before it starts, and unpaid (UNPAID, a PAID PHP 0 charge, or no charge). Someone else's booking, a guest's, or a caller with no linked record: 404 "Booking not found". The other refusals are 409s that send the resident to the hall: "This booking was made at the barangay hall, so it can only be changed there." (a walk-in the Secretary filed for them), "A booking can be cancelled online only until 24 hours before it starts. Please go to the barangay hall.", "A paid booking can only be cancelled at the barangay hall, so your refund can be arranged." A reason is optional, with the same limits; `processed_by_user_id` stays null; **no notification is sent**, because they have just done it.
- **ONE function does the cancel for both routes: `cancelBooking()`.** Each route decides whether its caller may cancel; the shared function re-checks "has not started" and runs the steps in this order, because supabase-js has no transaction:
  1. the booking to `cancelled`, guarded on `confirmed` (a 409 if nothing changed);
  2. an UNPAID charge to VOID, guarded on UNPAID. **A PAID charge above PHP 0 STAYS PAID** — the system never rewrites money or refunds; the refund is arranged by hand. No charge, or a PHP 0 one: nothing;
  3. if step 2 failed, the booking goes back to `confirmed` and the answer is a 500, "Could not cancel this booking; nothing was changed." If the void found no UNPAID row (the charge was paid between the read and the update), the same revert and a 409. **If the revert itself fails:** a `console.error` naming the booking and the charge, and a 500, "Cancel was interrupted; tell the developer.";
  4. an open GCash checkout on the voided charge (`paymongo_session_id` set) is **expired, best effort**: `POST /v1/checkout_sessions/{id}/expire` (`expireCheckoutSession()` in `services/paymongo.js`). A failure never blocks or undoes the cancel; it is a `console.warn` and a line in the log row. A PAID charge's session is never expired;
  5. the borrower is notified (Secretary cancel only);
  6. one CANCEL row: before `{ status: 'confirmed' }`, after `{ status: 'cancelled', charge_outcome, refund_due?, session_expired, session_expire_failure?, reason_given }`. `charge_outcome` is `VOID`, `PAID_REFUND_DUE` or `NONE`; `refund_due` is the amount and appears only with a refund; `session_expired` is `true`, `false` or `'not_needed'`. **The reason's text is never logged**, only `reason_given` (CLAUDE.md, Activity logging: "Never log free text"); the text is on the booking and in the notification.
- **A payment that arrives after the cancel** is logged for the Secretary and the Punong Barangay, not applied: see `docs/modules/payments.md`.
- **What the pages are told (step B2).** `GET /mine` adds `cancellation_reason` and, per booking, `can_cancel_online` and `cancel_online_note`, from `onlineCancelView()`: false and null on a booking that has started or is no longer confirmed; otherwise true exactly when `onlineCancelRefusal()`, the function the cancel route calls, has no objection, and else its sentence. `requested_by_user_id` is read for that and never sent (on a walk-in it is the Secretary's account). `GET /` and `GET /:id` add `cancellation_reason` and `not_started` (`withManaged()`, the same `hasNotStarted()` Edit and Cancel apply). `rentals:test` compares each flag with the route's own answer, booking by booking.
