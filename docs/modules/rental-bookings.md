# Rental bookings — module rules

This file holds the rules and current state of the Rental bookings list: `pages/RentalBookingsPage.jsx`, which is the Secretary's `/secretary/rentals` and the home page of Staff (`/staff`) and of the Punong Barangay (`/punong-barangay`). It was started on 14 Oct 2026 with the first of four batches (R1 to R4) that bring the Document requests list's improvements to it (see `docs/modules/document-requests.md`). Since 16 Oct 2026 it also holds the resident's two rental pages, My rentals and Book a rental (below), and since 26 Oct 2026 the availability rule and what the two booking forms show of it ("Availability and atomic booking", below). **It is NOT loaded automatically, and it MUST be read before changing the Rental bookings list or the resident's rental pages.** The module's design (self-service booking, the stored and derived statuses, fees through the charges system) stays in `CLAUDE.md` under "Facility Rentals".

## Rental bookings list

- **A failed load is an error, never an empty list** (`013640b`). The list used to store an empty list beside the server's bare message, so the page said "0 bookings" and "No confirmed / upcoming bookings." while it knew nothing, with no Try again. Now `requests` stays `null` on failure and the list area checks the error first, then loading, then empty, then rows (CLAUDE.md: a list that failed to load).
  - **The words:** "Could not load the bookings: <reason>" (`role="alert"`) with a **Try again** button where the rows would be; the heading reads "Bookings" while the list loads or after it failed, and "Loading bookings…" shows while a load is out. The reason is the server's own message, or "the server did not respond" when there is none (a server that cannot be reached, or an error answer with no message): `loadFailure()`, a copy of the Document requests and Payments pages' function, not shared with them.
  - **Every load starts from the loading state** (the first open, Refresh, Try again, and the reload after an action), and loads are numbered (`loadSeq`) so an older answer that arrives late, successful or failed, is dropped instead of replacing a newer one.
  - **A 401** ends the session once, in `authFetch`, and the route guard shows the login screen; the list never says "0 bookings" there either.
- **The list is six status tabs over ONE load** (`515a205`). The page sends `GET /api/rental-requests?status=all` once and splits the bookings in the browser: **Upcoming, Overdue, Completed, Returned, Cancelled, All**, each with its count over the whole list, so the counts read the same on every tab. A tab with none is dimmed and still pressable (it shows its empty text). The strip is `components/ListTabs.jsx`, as on Document requests, in a group named "Status".
  - **A booking is in the tab of the status its badge reads,** `displayStatus()` in `constants/rentals.js`: the server's `derived_status`. **Upcoming** is a confirmed booking whose end is still ahead, begun or not (`derived_status` "confirmed"; its badge says Confirmed). **Overdue** is a confirmed booking of equipment or furniture whose end has passed and that nobody has marked returned; **Completed**, a confirmed facility booking whose end has passed. **Returned** holds the three return outcomes (returned, returned late, returned with an issue), which their badges tell apart. A status outside these seven is counted under All only.
  - **NEVER split the list on the stored status.** The select the tabs replaced did: its first choice, "Confirmed / upcoming", asked the route for `?status=confirmed`, which is the STORED status, so it listed every past confirmed booking as well. On the live data (14 Oct 2026: 28 bookings, 15 stored as confirmed, 7 of them overdue and 8 completed) it showed 15 bookings under "upcoming", none of them upcoming. `test:auth` section AD fails a tab or a count that reads the stored status.
  - **The time comparison stays the server's** (`deriveStatus()` in `routes/rentalRequests.js`): the page never compares a booking's dates with the clock. A list loaded before a booking's end passes keeps it under Upcoming until the next load (Refresh).
  - **A tab must never send a request.** `load` depends on `authFetch` alone; putting the tab into its dependencies reloads on every press, and `test:auth` section AD fails it. The route's `?status=` filter is unchanged (other values still work for any other caller); this page simply no longer asks per status.
  - **The tabs, their order and their words are set in `utils/rentalList.js`:** `RENTAL_TABS`, `inTab`, `tabCounts`, `tabHeading`, `emptyText`, `openingTab`. No React; `test:auth` checks each case by case.
  - **The page opens on Overdue for Staff** (`canReturn`), as the select did, **and on Upcoming for the Secretary and the Punong Barangay, even while it is empty,** as it is on the live data: "0 upcoming bookings" and "No upcoming bookings.".
  - **The heading names the tab:** "7 overdue bookings", "1 overdue booking", "0 upcoming bookings", "28 bookings" on All. **The empty text names it too:** "No upcoming bookings.", "No returned bookings.", "No bookings." on All.
  - **The chosen tab lives through every reload:** Refresh, Try again, and the reload after a saved edit, a recorded return, a cancel or a filed walk-in. Back from the Edit, Mark returned or walk-in panel without saving loads nothing, as before. A booking whose status an action changed is under its new tab after the reload (a cancelled booking under Cancelled, a returned one under Returned). The tab is kept nowhere in the browser: every visit starts on the opening tab. While the list loads or after it fails, no tabs are drawn.
  - **The columns are unchanged:** Booked for, Item, Schedule, Qty, Purpose, Status, and the actions column for the Secretary and Staff, with the same badges, notes and actions. Since R3 the Booked for and Status cells also hold the booking number and the payment marker, and since R4 the columns stand in place above 640px and a returned booking's note reads "Returned by @…" (below). The Secretary has Edit and Cancel on every booking stored as confirmed, past ones (Overdue, Completed) included; **since step B2 they are drawn only where the list's `not_started` is true** (stored confirmed and the start still ahead, the server's own rule; see "Edit and Cancel" below), so never on an Overdue, Completed or under-way booking; Staff have Mark returned on stored-confirmed equipment and furniture that has started, under way or overdue (since step C3 never where `not_started` is true; below); the Punong Barangay has no actions column. **No role has a View button on this page.**

## Availability and atomic booking (step C1b, 26 Oct 2026)

Migration 024 (applied and verified on the live database: a 58-check SQL test, and a live concurrency test in which exactly one of two simultaneous bookings went through, every round) holds the rule; step C1b wired the routes and the two booking forms to it. The rules were decided by the owner (R1 to R5, 25 Oct 2026).

- **THE DATABASE DECIDES, AND THERE IS NO SECOND COPY.** `rental_holds()` is the one availability rule; `create_rental_booking` (POST /), `update_rental_booking_time` (PUT /:id) and `rental_availability` (GET /availability) all go through it. The route validates the body and turns a refusal code into words; it computes nothing about availability, and neither does any page. `findConflict`, `overlappingBookings`, `unitsUsed`, `conflictMessage`, `itemQuantityError`, the post-insert race guard and the Edit's revert-on-clash were removed. A new status or item type owes migration 024's functions an edit (they spell the words out).
- **Atomic by a row lock.** Each writer locks the item's `rental_items` row (`SELECT … FOR UPDATE`), then checks and writes in the same transaction, so a second booking or edit of the same item waits and then counts the first. The RENTAL charge is still a separate insert after the booking; if it fails, the route deletes the booking and answers today's 500 ("Booking reverted — failed to create its charge: …").
- **What a booking holds.** A facility holds its booked time only: back-to-back bookings are allowed. Equipment and furniture also **rest for 24 hours** (a literal 24 hours) after the booked end, or after the return when that is later, and only the booking's own units rest. **An overdue booking that nobody marked returned (stuck) holds its units with no end, until Staff mark it returned; nothing releases it automatically.** Marking it returned sets `returned_at` to that moment, so its units then rest 24 hours from the moment of marking. A cancelled booking holds nothing.
- **The gap is two-sided.** A new equipment or furniture booking is refused if it starts inside another booking's rest, and also if its own 24-hour rest would run into a later booking. Capacity is `quantity_available` (never `quantity_total`); a facility's is 1.
- **The refusals, in the route's words** (`refusalOf()` in `routes/rentalRequests.js`; the words it gave before the check moved): TIME_INVALID 400 (parseBookingBody's two sentences), QUANTITY_INVALID 400 (BELOW_ONE, FACILITY_WHOLE, MORE_THAN_EXIST), ITEM_NOT_FOUND 404, ITEM_INACTIVE 400, FACILITY_TAKEN 409 ("The {item} is already booked from {start} to {end} on that date — please pick a different time.", the first clash, in Manila time), NOT_ENOUGH_LEFT 409 ("Only {left} of {quantity_available} {item} is/are available for that time — you asked for {n}."), then, only when above 0, "{n} is/are overdue and not yet returned." and "{n} is/are resting for 24 hours after an earlier booking."; for an edit, BOOKING_NOT_FOUND 404 and BOOKING_STARTED 409 (the not-started sentence). **An unknown code or reason is thrown (a 500), never answered with a sentence.** The answer to a booking or an edit is always re-read (RENTAL_FIELDS, MANAGE_FIELDS), never the function's row, which carries the guest's contact and the purpose.
- **`GET /api/rental-requests/availability?item_id=&date=&start_time=&end_time=`**, resident and Secretary only (Staff, the Treasurer and the Punong Barangay get 403), **declared before `GET /:id`** (`roles:test` asserts the order).
