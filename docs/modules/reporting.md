# Reporting — module rules

This file holds the rules and current state of the Reporting module, moved out of `CLAUDE.md` on 13 Oct 2026, verbatim. **It is NOT loaded automatically, and it MUST be read before changing this module.**

## Reporting

- **Read-only aggregation over existing data** — no new schema, no migration, no writes anywhere in `routes/reports.js`. Roles per Chapter 3: **administrative** reports (`/document-requests`, `/residents`, `/facility-utilization`) are `secretary` + `punong_barangay`; the **financial** report (`/collections`) is `treasurer` + `punong_barangay`. The **PB sees both sets** (oversight); Staff and residents get 403 on every report.
- **Default date range: the last 12 months** — the first day of the month 11 months ago through today, so the series always shows 12 labelled buckets. `?from=&to=` override it. Ranges are **capped at 10 years and REJECTED (400) beyond that** rather than silently truncated, which would leave the monthly chart disagreeing with the headline totals.
- **Aggregation strategy:** PostgREST has no `GROUP BY`/`SUM` without a database function, and this module was scoped as no-migration. So plain totals use `count: 'exact', head: true` (computed in the DB, zero rows transferred) and grouped aggregates run **one narrowly-projected query per report**, bucketed in Node — one round trip beats dozens, and the projection keeps the payload small. If volume ever outgrows this, the fix is SQL aggregate functions in a migration (the pattern migration 003 already uses).
- **Data notes:** `rental_requests` has no created-at column, so facility utilization is keyed on `start_datetime` (the date the item was actually used — the meaningful axis anyway), and cancelled bookings are excluded from usage counts. Resident `sex`/`civil_status` are almost entirely null in the current data, so those breakdowns bucket nulls as **"Not specified"** rather than dropping them. Resident population totals are point-in-time and deliberately NOT date-filtered; only new registrations respect the range.
- **Collections: `no_fee_charges`, and the billed-month bucketing** (`3b2aa75`). `totals.no_fee_charges` counts the PAID charges in the range whose amount is 0, the PHP 0 ones approval and booking create with no payment row. It is the "No-fee charges" tile after "Payments recorded" and a CSV Totals row, and it is why `paid_charges` can exceed `payments_recorded` (69, 67 and 2 on 12 Oct 2026). **Charges are bucketed by `created_at`, the date they were billed**, not the date they were paid, so the monthly series is named "Collected (by billed month)" in the legend, the Monthly table and the CSV; its key is still `collected`. **The headline totals and the by-type figures are keyed on the billed date too, without saying so**, while "By payment method" counts payments by the date they were made, so for a given range the two can differ. **No backend test covers `routes/reports.js`**; `test:auth` section U checks the page without a server.
- **CSV export:** `?format=csv` on the **same endpoint** (one convention everywhere), so role checks and the date range apply identically to JSON and CSV. Sends `text/csv` + `Content-Disposition: attachment` with a `<report>-<from>-to-<to>.csv` filename, a UTF-8 BOM so Excel renders the peso sign, and a barangay/period/generated header block above the sections.
- **PDF export: client-side, `html2canvas` + `jsPDF`** — chosen so the recharts SVGs appear exactly as rendered on screen (a server-side rebuild would mean re-implementing every chart). `utils/exportPdf.js` captures the report node at 2× scale, draws an A4 header (barangay name, report title, period covered, generated timestamp) and a page-numbered footer, and **slices across pages at `data-pdf-block` boundaries so a chart is never cut in half**.
- **UI:** shared `ReportsPage` on `/secretary/reports`, `/treasurer/reports`, `/punong-barangay/reports` — a report picker (grouped Administrative/Financial, filtered to the role), from/to date controls, headline stat tiles, recharts line/bar charts, and a plain table of the same numbers underneath so they are checkable. Loading, error, and empty ("No data for this period") states are all handled — an empty range renders the empty state, never a broken chart.
  - **Report table headers may wrap on a phone; the numbers never do** (`dee0976`). `.report-sheet .data-table th.num { white-space: normal }`, beside the other `.report-sheet` rules in `index.css`, overrides the shared `.data-table .num { white-space: nowrap }` for report header cells only, so the two-word numeric headers ("Collected (by billed month)", "Units booked") wrap instead of widening their tables. **Never edit the shared rule**, which every table in the app uses; scope a report change to `.report-sheet`. On a phone it changes nothing from 530px up, nor at 768, 1280 or 1920; at 510 and 520 "Units booked" wraps in a table that already fit.
- **Render test:** `cd frontend && npm run test:reports` (needs the backend on :5000). The API tests never mounted the components, which is how a payload from one report reached another report's renderer and blanked the screen in the browser while every API test passed. This bundles the real components with the project's own bundler and server-renders each against LIVE data, plus mounts the `ErrorBoundary` in jsdom — **React error boundaries do not catch during SSR**, so boundary behaviour is only verifiable with a client mount. Cross-report payloads are asserted to throw, as a regression guard. **Limit of what it covers:** the per-report checks server-render, so duplicate-key bugs are structurally invisible to them — React validates keys only in the client reconciler (see `25fe20b` under Frontend Layout). Since `3b2aa75` it also checks the Collections "No-fee charges" tile and the "Collected (by billed month)" Monthly header; a server render draws no chart legend, which section U of `test:auth` checks instead.
  - **It needs four environment variables, and the script keeps no credentials:** `REPORT_TEST_SECRETARY_USER` and `REPORT_TEST_SECRETARY_PASS` (an active Secretary account, for the three administrative reports), and `REPORT_TEST_TREASURER_USER` and `REPORT_TEST_TREASURER_PASS` (an active Treasurer account, for Collections). If any is missing it names the missing ones and stops before sending anything. It reports each login by username and HTTP status, and stops at the first refusal, because `/login` allows 5 failed attempts per 15 minutes per connection.
- **Render-race fix (was a live bug):** switching reports re-renders with the NEW renderer before the effect can refetch, so an untagged payload briefly reached the wrong renderer — each report has a different shape, so it threw and blanked the content area. The fetched payload is now tagged `{ key, data }` and only rendered when `key === selected`. The renderers live in `components/ReportRenderers.jsx`, deliberately free of auth/router/`import.meta.env` so they are pure functions of their data (and directly testable).
- **Not built:** event participation / attendance reporting. Events stage 3 (household attendance and fines) has since been built (`docs/modules/events.md`), so the data exists, but no route in `routes/reports.js` reads it.
