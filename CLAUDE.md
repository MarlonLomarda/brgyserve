# BrgyServe

## Project Overview

BrgyServe is a web-based document request and tracking system for **Barangay Ubujan, Tagbilaran City, Bohol**. It is a capstone project that digitizes barangay services: residents request official documents online and track their status, while barangay officials process requests, manage resident records, handle facility rentals and payments, record disputes/blotter entries, and generate reports.

## Tech Stack

- **Frontend:** React (scaffolded with Vite) — `/frontend`
- **Backend:** Node.js with Express — `/backend`
- **Database:** Supabase (PostgreSQL)

## Environment / Secrets

Supabase credentials live in `backend/.env` (see `backend/.env.example` for the required keys). **Never hardcode keys in source files and never commit `.env`.** The service role key bypasses Row Level Security and must only ever be used server-side.

**`SUPABASE_SERVICE_ROLE_KEY` is REQUIRED and the API refuses to boot without it** (`8a949aa`). There is no fallback to the anon key and adding one back would be a bug: RLS is enabled on every table with **zero policies**, so the anon key reads nothing, and the old fallback produced a server that started green, answered `/api/health`, and then returned an **empty result set for every query** — a login reading as "invalid credentials", a resident list reading as "no records". Refusing to start is the better failure, and it is the same reasoning as the `VITE_API_URL` guard above; the difference is that this guard is unconditional, because no environment legitimately wants the anon key. `SUPABASE_ANON_KEY` is **not read by the backend at all** and is kept in `.env.example` only so its absence is not mistaken for an oversight.

The frontend needs `VITE_API_URL` — the API origin **including** the `/api` suffix. It is **required for every build**: `vite.config.js` throws rather than let a build fall back to `http://localhost:5000/api`, which used to deploy green while every request in the browser pointed at a machine that is not there. Locally that means `frontend/.env` must exist (gitignored); on Vercel the value comes from the project's Environment Variables panel. **This reverses the older "delete `frontend/.env` before building" rule** — deleting it now fails the build, which is the point. The dev server keeps the localhost fallback.

## Deployment

The system is live on two hosts, each deploying from `main`.

- **Frontend — `https://brgyserve.vercel.app`** (Vercel). **Root Directory `frontend`**, which is why `vercel.json` lives in `frontend/` and not at the repo root — at the root Vercel would never read it, and the SPA rewrite would silently not apply. `VITE_API_URL` is set to `https://brgyserve-api.onrender.com/api` in the project's Environment Variables panel; the `/api` suffix is part of the value, not appended by the client.
- **Backend — `https://brgyserve-api.onrender.com`** (Render). **Root Directory `backend`**, build `npm install`, start `npm start`, **Free tier**, Singapore region. **16 environment variables**, including `FRONTEND_URL` and `PUBLIC_FRONTEND_URL` — both the Vercel origin, but they are not interchangeable: `FRONTEND_URL` is the **comma-separated CORS allowlist** (`server.js`), `PUBLIC_FRONTEND_URL` is the **single origin the resident is redirected back to** after a GCash payment (`routes/payments.js`), which a list cannot express. `PUBLIC_BASE_URL` is the Render origin, and is what the PayMongo webhook is registered against. The `.env.example` mnemonic still applies: `PUBLIC_BASE_URL` is where PayMongo reaches us, `PUBLIC_FRONTEND_URL` is where the resident is sent back to.

**The Free tier sleeps after about 15 minutes idle, and the first request after that takes 30–45 seconds** (measured, not estimated). **Before any demo, open `https://brgyserve-api.onrender.com/api/health` about five minutes ahead** so the instance is awake and the first real click is not the one that pays for it.

**A cold backend returns 502 on the CORS preflight.** The browser console reports that as a **CORS error** and the app shows "Cannot reach the server", so it reads exactly like a misconfiguration — **it is not one, and there is nothing in the CORS setup to fix.** The instance is asleep and the preflight `OPTIONS` never reached it. Wake it and retry. This cost real debugging time once; it is recorded so it does not cost it twice.

**Local development no longer receives PayMongo webhooks.** The single webhook points at Render, so a GCash payment made against a local backend is never delivered to it. Those charges settle through the Treasurer's **"Re-check with PayMongo"** on the Payments screen, which re-reads the checkout session and settles through the same `settlePaidCharge()` the webhook uses. That is the intended local workflow now, not a workaround.

**NEVER RUN `npm run tunnel`. IT BREAKS PAYMENTS ON THE LIVE SYSTEM.** There is only ever **ONE** PayMongo webhook, and it is registered against `https://brgyserve-api.onrender.com`. `npm run tunnel` repoints *that* webhook at a fresh temporary cloudflared hostname which stops existing the moment the terminal closes. PayMongo would then deliver every GCash payment into nothing and charges would **silently stop settling — with no error anywhere**, because a webhook that is never delivered looks exactly like a resident who abandoned checkout. Reconciliation can recover them one at a time, but only once somebody notices.

**`npm run tunnel:sync -- https://brgyserve-api.onrender.com` is the safe command**, and the fix if the webhook is ever found pointing somewhere else. It takes the **base origin** (the script appends `/api/payments/gcash/webhook` itself), updates the webhook in place, and is **idempotent** — given the url it already holds it reports "already points at this url" and changes nothing. `PAYMONGO_WEBHOOK_SECRET` survives the update unchanged, so no redeploy follows. *(How tunnelling worked during development, and why there is exactly one permanent webhook, is in `docs/brgyserve-implementation-log.md` → "Dev tunnel (webhook reachability) — HISTORICAL, DO NOT RUN".)*

### THE DEPLOYED API IS CLOUDFLARE-FRONTED (`24665ba`, `71bfc37`)

**This is stated here because nothing else in this file said it, and the Dev tunnel section below is easy to misread as saying the opposite.** That section is about **cloudflared quick tunnels**, a dev-only tool that has been dropped. It is a different thing from the Cloudflare edge that sits in front of the Render service in production, which is very much still there and is load-bearing for the rate limiter.

**The live request chain is `caller -> Cloudflare -> Render`, and the hop count was MEASURED, not guessed.** `server.js` sets `app.set('trust proxy', 3)`, confirmed on two different networks against a temporary `/api/proxy-probe` route added in `3c699b6` purely to take the reading and removed again in `71bfc37`. **Re-measure it if the hosting changes** — a region or plan change, a custom domain, or anything placed in front of Cloudflare moves the count, and a stale value fails silently in whichever direction it moved.

**`trust proxy` is a COUNT and must never be `true`.** `true` tells Express to believe the **leftmost** `X-Forwarded-For` entry, which is caller-controlled: a forged `X-Forwarded-For` is **PREPENDED to the real chain** rather than rejected, so anyone could mint a fresh rate-limit bucket per request by changing one header. A forged `CF-Connecting-IP`, by contrast, is **rejected by Cloudflare at the edge with error 1000** and never reaches this process — which is what makes that header trustworthy as the limiter's key. express-rate-limit does have a check for the permissive case (`ERR_ERL_PERMISSIVE_TRUST_PROXY`), but **do not rely on it**: its validations are caught internally and surface as one `console.error` per process, never as an exception the request would show.

**On the Render service, Custom Domains is EMPTY and PR Previews is OFF**, so the `onrender.com` hostname is the only public path in and it is Cloudflare-fronted throughout. **Adding either would create a second path that has not been measured** and would require re-taking the hop count before the limiter's key could be trusted again.

### Security response headers — helmet (`24665ba`)

`app.use(helmet())` is **mounted FIRST in `server.js`**, ahead of `cors()` and ahead of the raw-body PayMongo webhook. That ordering is the point, not a detail: the headers then reach **every** response, including the CORS preflight — which `cors()` short-circuits with a 204 before any router runs — and the 500s from the error handler at the bottom of the file.

**Before this the API sent no security headers at all** — no CSP, no `X-Content-Type-Options`, no `Referrer-Policy`, no `X-Frame-Options` — and advertised `X-Powered-By: Express` on every response, which fingerprints the stack for free and is the first line of any scanner's report. Verified live on the deployed instance before the change was made.

**Helmet only sets response headers and calls `next()`; it never reads the request body or stream.** Verified with an instrumented mock req/res before mounting, because the risk was real: `express.raw()` on the PayMongo webhook needs the exact bytes sent, and anything consuming the stream first would break the HMAC on every genuine call. It does not, so the webhook is unaffected.

**This covers the API ONLY.** The Vercel frontend still sends no CSP and no `X-Frame-Options` — see Outstanding work.

## Auth & Account Approval

- Custom JWT auth (`jsonwebtoken` + `bcryptjs` hashing) against the `users` table — Supabase Auth is NOT used. Requires `JWT_SECRET` (and optional `JWT_EXPIRES_IN`) in `backend/.env`.
- Resident self-registration (`POST /api/auth/register`) creates a **pending** account: `is_active = false`, `profiles.resident_id = null`. Pending accounts cannot log in.
- Login's message for an inactive account (`inactiveMessage` in `routes/auth.js`) has **THREE branches, and only two of them are derived**. The 403 block itself never changes — none of these accounts may log in; only the wording differs.
  1. **REJECTED** — `users.is_rejected`. Checked **FIRST**, and it must stay first: a rejected resident satisfies branch 3 as well, which would swallow it. Returns the reason code's canned sentence.
  2. **ARCHIVED** — linked to an **archived** `resident_records` row ⇒ "This account has been deactivated. Please contact the Barangay Office." Derived: the archive cascade deactivated a previously *active* account.
  3. **PENDING** — any other `resident` ⇒ the pending-approval message, correct both before and after a record is linked (linking and activating are separate steps). Anything else ⇒ a generic "This account is inactive."
- **This section used to argue that no extra column was needed, from there being exactly two paths that clear `is_active`. That argument is dead and the reasoning is worth keeping, because it is the whole justification for migration 017.** A pending registration is *created* with `is_active = false`, so "rejected" could not be expressed by clearing a flag that was already clear — **pending and rejected were byte-identical row states.** Rejecting was therefore a no-op, and login answered "pending approval by the Barangay Secretary" to an applicant whose registration had already been declined. Nothing on `users` or `profiles` was free to hold it either: the live schema was read from PostgREST's OpenAPI document before any code, and all 8 + 10 columns were spoken for. `email_verified` (written, never read) and `profile_pic` (never referenced anywhere) were structurally available and **deliberately not repurposed** — a column named `email_verified` holding "this registration was declined" makes every future reader wrong. *(That count is the state as of migration 017. `profile_pic` has since been dropped in migration 019 — see the next entry; `profiles` is now 9 columns.)*
- Secretary review (role `secretary`, routes under `/api/secretary/`): list pending accounts, link each to an existing `resident_records` row or create-and-link a new one, then **activate or reject**. Activation requires a linked resident record. **Activation is no longer the only decision** — see the rejection module below.
- Active residents view their own record via `GET /api/residents/me` through the `profiles.resident_id` link.
- Staff-type accounts (`secretary`, `punong_barangay`, `treasurer`, `staff`) are created only by the Secretary via `POST /api/secretary/accounts` — active immediately, with a generated temporary password (returned once in the response) and `must_change_password = true`.
- Forced password change: `authenticate` default-denies every request from a `must_change_password` user with a 403 + `code: 'PASSWORD_CHANGE_REQUIRED'`; only routes wrapped with `allowPendingPasswordChange` (i.e. `POST /api/auth/change-password`) are reachable. The frontend mirrors this by routing such users to `/change-password`.
- `authenticate` middleware re-reads the user per request, so deactivating an account (or clearing the password flag) takes effect immediately.

**THE SIX-MONTH RESIDENCY RULE IS NOT AUTOMATED, AND MUST NOT BE.** The barangay's rule, confirmed with the Secretary, is that an applicant must be in the masterlist **and** have been registered in it for at least six months. Nothing computes that, on purpose. **`resident_records.date_registered` is the timestamp the row entered BrgyServe — not the barangay's own registration date.** It is server-set on insert at both creation paths and is never client-writable, so it cannot be corrected even when the Secretary knows the real date. Measured against the live data: **all 47 non-archived records were created in July 2026, so a six-month check against that column would reject 100% of them** — including a resident on the paper masterlist since 2009. The Secretary applies the rule and records `RESIDENCY_TOO_SHORT`; the system informs that judgement and never makes it. `masterlist_registered_on` (migration 018) holds the barangay's own date and drives an **advisory** badge only — nothing reads `meets_minimum` to block, disable, hide or gate anything, and activate works exactly as before on an under-six-months account.

**`ProtectedRoute.jsx` WAS DELIBERATELY NOT TAUGHT ABOUT TOKEN EXPIRY. Do not add the check there.** Expired sessions are dropped in `readStored()` in `auth/AuthContext.jsx`, at the session source. The reason is that `user` is read by two components that would otherwise disagree: `App.jsx` treats a truthy `user` as "already logged in, bounce them off `/login`", while `ProtectedRoute` treats it as "let them in". Teaching only the guard about expiry makes them fight — the guard sends the expired user to `/login`, `App` sees the still-truthy stored `user` and sends them back: **an infinite redirect loop.** Purging in `readStored()` makes `user` null for both readers at once, so they agree by construction. Relatedly, there is deliberately **no auto-logout timer** — an idle expired session is caught on the next action or page load, and a timer would interrupt someone mid-form for no gain.

### Two unused columns, two OPPOSITE decisions — the difference is the point

Both were unused. Both were eyed as a home for the rejection state in migration 017 and refused. They then went different ways, and **which way each went is not arbitrary — it turns on whether anyone intends to use it.**

| column | verdict | why |
|---|---|---|
| `profiles.profile_pic` | **DROPPED (migration 019)** | a resident photo was **declined**, not deferred |
| `users.email_verified` | **KEPT, unused** | **reserved** for planned email verification |

- **`profiles.profile_pic` was DROPPED. Do not re-add it thinking it was an oversight — it was removed on purpose.** A resident photo feature was considered and **declined on data-minimization grounds**: under the Data Privacy Act a photograph needs a stated purpose, and **no function in BrgyServe uses one** — document requests are identified by the resident record, attendance is per household by QR, payments by charge, and the Secretary verifies an applicant by name, birthdate and address. This is the same reasoning already applied to the **Staff narrowing** (see `docs/brgyserve-implementation-log.md` → "DATA MINIMIZATION — Staff receive a narrowed resident record"), where each field Staff receive had to earn its place and the rest were withheld: a field with no task behind it is not collected. Verified before dropping — no read, no write, no select list, no form field, no test, and `git log --all -S "profile_pic"` returned only the three commits that define or describe it. The live column was empty (0 of 17 rows non-null), confirmed by count rather than assumed. **Dropping a column is irreversible without a restore**, which is why the migration's review block counts before it commits.
- **`users.email_verified` is KEPT despite being equally unused. It is RESERVED, not dead, and must not be dropped in a future cleanup.** The group intends to add email verification; the column is written `false` at both account-creation paths (`routes/auth.js`, `routes/secretary.js`) and read nowhere, which is exactly what a reserved column looks like mid-way to a feature. **It must also never be repurposed to hold anything else** — that was refused for the rejection state in migration 017 for the reason stated above, and the refusal stands for whatever the next tempting reuse is. A column named `email_verified` holding something other than whether an email was verified makes every future reader wrong.

**The general rule this pair establishes:** an unused column is dropped when nobody intends to use it and kept when somebody does. "Unused" alone decides nothing — and neither is ever a free slot for unrelated data.

## Research Contribution: Two-Stage Fuzzy Name Matching

The capstone's research component detects **duplicate / near-duplicate resident records** (misspellings, name variations, encoding inconsistencies) using a two-stage pipeline:

1. **Stage 1 — Candidate blocking (database layer):** PostgreSQL `pg_trgm` extension performs trigram similarity blocking to cheaply narrow the full resident table down to candidate pairs. This avoids the O(n²) cost of comparing every record against every other record.
2. **Stage 2 — Fine scoring (application layer):** Jaro-Winkler similarity is computed on each candidate pair in the Node.js backend to produce a final match score. Jaro-Winkler weights agreement in name prefixes, which suits person-name matching.

**Evaluation:** the component is evaluated with **precision, recall, and F1-score** against a labeled set of known duplicate/non-duplicate pairs.

Implementation status:
- Engine implemented in `backend/src/services/nameMatching.js` (`findMatches(first, last, options)`); tunable defaults live in its exported `DEFAULTS` (trigramThreshold 0.3, scoreThreshold 0.85, maxCandidates 50). Do not hardcode thresholds elsewhere — the evaluation sweeps them.
- Stage 1 runs as the `match_resident_candidates` SQL function (migration 003) called via RPC; it uses `set_limit()` + the `%` operator so the GIN indexes are used with a per-call threshold. Jaro-Winkler comes from the `jaro-winkler` npm package and scores the normalized `first last` string (middle names are stored separately and excluded from scoring).
- Test harness: `npm run match:test` (backend); seed test data with planted duplicate pairs in `backend/seeds/test_resident_records.sql` (the six planted pairs are the basis for the future labeled evaluation set).
- Evaluation harness: `npm run match:eval` (backend, `scripts/evaluate-matching.js`) — labeled ground truth manifest mirrors the seed file (6 positive pairs, 624 negative pairs from the 36 seeded records; small initial set to be expanded), runs the real engine, and prints TP/FP/FN/TN + precision/recall/F1 across a Stage 2 threshold sweep. On the current labeled set: perfect separation up to threshold 0.85 (P=R=F1=1.0), recall drops above it. Keep the manifest in sync with the seed file.

## Conventions

- Backend uses CommonJS (`require`), frontend uses ES modules (Vite default)
- API routes are prefixed with `/api/`
- Commit messages must never include AI attribution lines ("Co-authored-by: Claude", "Generated with Claude Code", or similar)
- Database schema lives in `docs/brgyserve-database-schema.md` (source of truth) and is applied via numbered SQL files in `backend/migrations/`, run manually in the Supabase SQL Editor. Keep the doc and migrations in sync.
- **THE FIVE PASSWORD COMPOSITION RULES EXIST TWICE ON PURPOSE. If one changes in `backend/src/constants/passwordPolicy.js`, change it in `frontend/src/components/PasswordChecklist.jsx` too.** The browser copy cannot import the server one: `passwordPolicy.js` does `require('crypto')`, which Vite substitutes with an **empty object plus a warning** rather than failing, so the bundle would carry a function that throws at call time in the browser and nowhere else. Five regexes are cheaper to duplicate than to share. **The checklist covers COMPOSITION ONLY** — the blocklist, the username rule and the banned terms stay server-side, two of them because the reset screen does not know whose account it is, so a password showing five green ticks can still be refused on submit (`Password1!` is the standard case). That is expected, not a contradiction.
- **Case-insensitive email lookup goes through `backend/src/utils/userEmail.js` — never a fresh `.eq('email', …)`.** That comparison is **silently case-sensitive**, so a pre-check written with it misses a collision the case-insensitive unique index then rejects at insert time, turning a clear 409 into a confusing one. The shared helper uses an `ilike` prefilter with an exact lowercased comparison after it, because real addresses contain underscores and **PostgREST treats `_` as a single-character wildcard**. One implementation, so the mistake can only be made once.
- **Branch a 23505 on the CONSTRAINT NAME in `error.message`, not on `details`.** `details` names the offending **column** and a **functional** index reports it differently from a column constraint — `Key (lower(email::text))=(…)` versus `Key (username)=(…)` — while the constraint name is stable across both shapes. **An unrecognised 23505 must be re-thrown rather than reported as either**, because answering with a message we cannot support is worse than a 500.
- **Charge statuses are UPPERCASE; request statuses are lowercase.** `constants/charges.js` (`UNPAID | PAID | VOID`) follows Table 15; `constants/requestStatus.js` (`pending | approved | …`) and `constants/rentals.js` are lowercase. The two vocabularies are deliberately different and neither may drift toward the other. Registration reason codes and notification types are UPPERCASE, matching charges.
- **A review block's final `SELECT` must carry an EXPLICIT column alias list on the derived table** — `) AS x (ord, section, detail)` — never rely on the branches' own `AS` aliases. That happened once (the migration-018 seeding block), and because it fails at the outer select the whole transaction aborts and nothing is written — a safe failure, but a wasted round trip on a block that is otherwise ready to run. The explicit list names every column regardless of what any branch does.

## Standing Rules

How work is done in this repository, as distinct from how code is written (see Conventions).

- **Never start the backend or frontend dev server.** The developer starts them. The `npm run dev` lines under Commands and Repository Structure record *how* they are started, not permission to start them — assume a server on :5000 or :5173 is one somebody else is using. Verification that needs a browser uses a `file://` harness loading the real `index.css`, driven by headless Chrome over CDP, which starts no server at all.
  - **A harness must reproduce the real NESTING, not just the element.** Available width comes from the whole ancestor chain, so a flattened copy measures an **optimistic** width and passes when the app would not. Measured case: a `.head-actions` sitting inside a `.pending-card` has less room than one directly in `.dash-main`, which is why the QR scanner's Record button wraps to its own line in the app and did not in a harness that modelled the row alone. **Also assert the device width itself** — with `<meta viewport width=device-width>` an overflowing page makes Chrome widen the layout viewport to swallow the overflow, so `scrollWidth <= innerWidth` passes **vacuously**; assert `innerWidth === 390` first, then compare against 390.
- **WHAT GOES IN THIS FILE, AND WHAT GOES IN THE LOG.** This is the rule that stops `CLAUDE.md` filling back up — it was 204,386 chars and past its limit before the split.
  - **`CLAUDE.md` holds rules, current state and open decisions** — what a change must honour, what is true of the running system right now, and what has been decided but not settled.
  - **`docs/brgyserve-implementation-log.md` holds what was built and why it is finished** — the narrative, the alternatives weighed, the bugs found on the way.
  - **A commit that ships a feature updates the LOG, not this file — unless it changes a rule.** If it adds a constraint, invalidates one, or creates something the next change has to work around, that part belongs here and the rest belongs there. Most feature commits touch this file not at all.
  - **HEADINGS IN THE LOG ARE STABLE ONCE WRITTEN. Do not rename or re-level them.** The 21 stubs here name log headings **as prose**, and **nothing checks that they still resolve** — there is no link checker, and a renamed heading leaves a stub pointing at text that no longer exists, silently. Add new headings freely; leave existing ones alone. If one genuinely must change, grep this file for the old title in the same commit.
- **Any SQL that WRITES is handed over wrapped in `BEGIN … ROLLBACK`, never `BEGIN … COMMIT`.** That covers `INSERT`, `UPDATE`, `DELETE`, `ALTER` and `DROP` — **it is not a delete-only rule**, because an `UPDATE` with a wrong `WHERE` destroys exactly as much as a `DELETE` and, unlike one, still reads as a success. The Supabase SQL Editor has **no undo**, and this database holds the thirteen records behind the six planted evaluation pairs — the positive set `npm run match:eval` measures recall against, and the evidence base for Chapter 3 (see Protected Data). Nothing brings them back. **The block states its expected row count as a comment**, so the dry run is checked against an expectation rather than eyeballed — a rollback reporting 47 rows where the comment says 2 is the entire reason for running it first. **The developer reviews that output, then switches `ROLLBACK` to `COMMIT` and re-runs the block themselves. Claude Code never hands over SQL that commits on its first run.**
- **Never use `git add .` — stage explicitly by path**, every time. That is what keeps `frontend/.env`, `dist/` and the ignored bundles in `frontend/scripts/` out of a commit by construction rather than by luck.
- **Build prompts and commit prompts are separate.** A build ends with the edit made and verified, the working tree dirty and **nothing staged**; the commit follows in its own prompt. Committing inside a build prompt removes the review step the separation exists for.
- **Diagnose before any structural change.** Measure, report what was found, propose candidates, let the developer choose. This has caught real errors more than once — including a proposed diff that would not have compiled, and a test harness that "passed" against code already known to be broken. A harness that does not reproduce the bug proves nothing when it passes: **always run it against the pre-fix code first.**
- **After any turn that edits files, run `git status --porcelain` and `git diff --stat`, and report what they actually returned.** A diff written into a chat response is not evidence that anything changed — it is a description of an intention, and the two come apart silently. This session produced a turn confidently reporting five applied edits against a **completely clean working tree**, and the mismatch surfaced only when the next turn happened to read the file. One command is the whole cost, and it is the difference between reporting work and reporting a plan.
- **Commit messages:** subject line plus three or four bullets, plain language, **no attribution trailers** (see also Conventions).
- **A JSX comment cannot go inside an implicit-return arrow function.** In `{columns.map((c) => (` … `))}` the callback returns a single expression, so a `{/* … */}` placed beside the element makes two sibling expressions with no wrapper and **the Vite build fails**. Put the comment on the line above the `.map(` call instead. **The same applies to a parenthesised ternary branch** — `cond ? (<A/>) : ({/* … */}<B/>)` fails identically; this cost a build in `eba84ae`.
- **A WITHHELD FIELD MUST BE ABSENT FROM THE PAYLOAD — never `null`, never `[]`, and never a shape whose flags read as a finding.** This caused two bugs in one day, both shipping a false statement to the screen. `account: null` on the resident list made every row render an em dash, so the Account column asserted **no resident has registered online**. `linked_accounts: []` on the detail said the same thing in prose: *"Not linked to any account — this resident has not registered online"* — on record #9, which has one. Both were reported as "keeping the response shape stable across roles", and that is exactly the trap: **a shape that stays constant by asserting something false is worse than a shape that varies honestly.** `null` and `[]` are positive claims ("we looked, there is none") and a client cannot tell them apart from a genuine empty result. Absence is the only representation of *withheld* that a client can detect. The frontend tests presence with **`key in object`** and **never checks the viewer's role** — the server has already decided, and a role check in the component would be a second opinion free to disagree with it.
  - **The same rule governs a DERIVED value with nothing to derive from, and `deriveResidency()` is the live case.** `deriveResidency(null)` **returns `null`, and that is load-bearing** — it must never return a shape carrying `meets_minimum: false` for a missing `masterlist_registered_on`. `false` is a **positive claim** ("we checked, they do not meet it"), indistinguishable from "there was nothing to check", so every record the barangay has no date for would wear an under-six-months badge and the Secretary would decline people for failing a test that never ran. The frontend renders **nothing** when it is absent — no date, no badge, no "unknown" pill.
  - **The same rule governs a LIST THAT FAILED TO LOAD.** On failure store `null` and the error — **never an empty shape** like `{ rows: [], total: 0 }`, which is the claim "we looked and there are none" and reaches the empty-state text. **Render the error first, then loading, then empty, then rows**; with `null` stored, checking loading first shows "Loading…" forever. This `null` is not the payload claim above: it always travels with an error, and the render never reads it as empty. **Only a thrown error is a failure** — a successful response with zero rows is a real empty state. `HouseholdsPage.jsx` (`32ec107`) and the attendance roster (`AttendanceRoster` in `EventsPage.jsx`) follow this. **`SecretaryReviewPage`'s own list does not** — `setPending([])` on failure shows the error beside its empty text; queued.
- **A ROUTE FILE THAT DROPPED ITS ROUTER-LEVEL ROLE GUARD DOES NOT FAIL CLOSED. `routes/residentRecords.js` and `routes/households.js` are both in that state.** Each moved from `router.use(authenticate, requireRole('secretary'))` to `router.use(authenticate)` plus a per-route guard, so **a route added to either file without an explicit `requireRole(...)` is readable by ANY authenticated user, residents included — and nothing about the code would look wrong.** The protection is `cd backend && npm run roles:test` (87 assertions, no server started): it probes every route in `residentRecords.js` and `documentRequests.js` with all five roles through the real middleware chain and compares against a declared table, where **a route with no entry FAILS as undeclared** rather than passing silently. Add the route to that table in the same change that adds the route.
- **THE COMMITTED DEV API FALLBACK IS `http://localhost:5000/api`, AND IT IS DELIBERATE. Do not change it. It has regressed FOUR times.** The value in `frontend/src/api/config.js` is one side of a two-sided pair: the backend listens on 5000 (`server.js`), and `vite.config.js`'s own error text names 5000. Changing only the frontend side points the dev app at a port nothing is listening on, which presents as "Cannot reach the server" and looks like a backend problem. **If port 5000 is taken on your machine, the fix is `backend/.env` `PORT` plus `frontend/.env` `VITE_API_URL` — both gitignored, both local to you — never the committed fallback.** It is dev-only either way: `vite.config.js` throws without `VITE_API_URL`, so no deployed bundle has ever carried it. `44ed8e4` changed it to 3000 and `22d7f35` reverted it; that is the pattern to stop repeating.
- **Beware a test that pins a bug in place.** The assertion `check('response SHAPE is stable (linked_accounts present for both)', …)` did not merely tolerate the bug above — it would have **failed anyone who fixed it**, under a name asserting the arrangement was correct. It was deleted along with the behaviour. When a test's name states a design claim, the claim is what needs reviewing, not just the assertion.

## Frontend Layout

**No CSS variables exist in this codebase and none are to be introduced.** Values are literal. This is a live constraint rather than a style preference — the `capped-column` coupling below would be a one-line binding if variables were available, and instead has to be held by a comment.

**Spacing or layout wanted by ONE screen goes on a scoped selector, never on a shared utility class.** The worked example is `.muted`: it carries no margin, and the dashboard header's subtitle gap lives on `.dash-header .muted` instead. `.muted` is on **163 elements across 24 files** — helper text, empty states, table captions, loading lines — so a margin added to the utility itself lands on all of them at once. That is exactly what happened in `07cc26d`, which set `margin: 5px 0 0 0` on `.muted` to space one header subtitle; `e83e56c` reverted it and scoped it. Specificity does the work — `.dash-header .muted` is (0,2,0) against (0,1,0), so it wins regardless of source order and the scoped rule can sit with the other `.dash-header` rules rather than being wedged in beside `.muted`.

### The auth pages are scoped under `.auth-page`, and that changed the specificity order

The login/registration redesign (PR #4, merged as `9adea3c`) originally restyled the **shared** `.card`, `.card h1`, `label`, `input` and `button` rules to suit two screens. That is the `.muted` mistake at a much larger blast radius — those selectors are on every screen in the app — so the shared rules were restored to their previous values and `.auth-page`-scoped equivalents added instead (`9e2efc4`).

Any `.btn` inside an auth page loses to the scoped rule regardless of source order. The password toggle survives this only because **`.pw-field .pw-toggle` is (0,2,0)** and beats both. A new control added to `/login` or `/register` needs at least (0,2,0) to hold its own styling, and a single class will not do it.

**`.auth-page button` appears TWICE in `index.css`** — one sets `padding: 15px`, the other sets `width: 100%; margin-top: 6px`. **Tell them apart by the properties they set, not by position**: the two are far apart in the file, they have moved more than once, and the properties are what you are actually looking for. They are **disjoint**, so there is no conflict today and no bug. It is recorded because a reader who finds one will reasonably assume it is the only one and edit the wrong occurrence. A grep for `.auth-page button` returns a **third** hit, `.auth-page button.link-button` — a different, more specific selector (0,2,1), not one of the pair.

**`/login` now carries three modals — Help Center, Terms of Use, Privacy Policy (PR #8).** They render from `LoginPage.jsx` into `.modal-overlay` > `.legal-modal`, opened from `.legal-links` beneath the form. Four things a future change has to honour:

- **The modals do NOT trap focus.** Tab from inside an open panel walks out into the login form behind it. Escape closes, the overlay click closes, and opening twice is clean — so it works, it is simply not a focus-trapped dialog. Adding a trap later is a real change, not a tidy-up.

Change the markdown first and carry the change into the JSX in the same commit; never edit the JSX copy alone. ### The 640px mobile treatment — one breakpoint, three changes

**640px is the ONLY breakpoint in the dashboard CSS. Do not add a second.** Everything below is inside one `@media (max-width: 640px)` block, and every rule in it is **additive** — the six protected desktop rules were verified byte-identical after each change, and full computed-style snapshots at **641, 1280 and 1920** showed **zero differences**. 641 is the check that matters: one pixel above the breakpoint.

- **`ISSUE 7` — `.list-head` and `.head-actions` wrap.** `flex-wrap: wrap` on both, `row-gap: 10px` on `.list-head`, and `.head-actions input { width: auto; flex: 1 1 200px; min-width: 0 }` so the search field can shrink instead of collapsing. **The 390px document overflow was the HEADER ROW, not the table** — `.table-wrap { overflow-x: auto }` had always contained every table. The tell was a sticky header scrolling sideways: `position: sticky; top: 0` pins only vertically, so a header that moves horizontally means the overflow reached the viewport.
- **`ISSUE 8` / `ISSUE 9` — `.data-table.stack-narrow` turns rows into cards.** `thead` hidden, every `tr`/`td` `display: block`, and **`td[data-label]::before` renders the hidden column header** from the attribute. **On sixteen tables**, carrying 53 `data-label` attributes: the fifteen dashboard tables plus the Privacy Policy provider table (`components/legal/LegalPrivacy.jsx`, added by `bd03c74` with 12 attributes). Counted as `className` containing `stack-narrow` and `data-label="`/`data-label={` across `frontend/src/**/*.jsx`; a bare grep also hits comments and returns 19 and 56 — the old figure of 42 was such a grep, 41 attributes plus one comment in `ResidentRecordsPage.jsx`. **A cell gets a label unless it carries its own type marker** — `₱` marks money, `@` marks an account, a badge marks a status; dates, bare integers and bare nouns do not, and any cell that can render a bare em dash gets one regardless.
- **Five tables are deliberately NOT stacked, and each for its own reason.** `ReportRenderers.jsx` feeds the PDF — `exportReportPdf` runs html2canvas over the live DOM at no forced width, so stacking it would change the exported document. `HouseholdsPage.jsx` and `PaymentResultPage.jsx` have key-value tables whose `<th>` **is** the label already. `RentalItemsPage.jsx` is a small admin catalogue whose tallest card measured 294px. The attendance **roster** keeps its own near-duplicate block (`.roster-table`), left that way on purpose — **both comments say to check the other**, and consolidating them is post-defense work.

- **`.dash-header h1` renders at 1.05rem everywhere.** **This is the ONE place in this section where position, not the selector, is the mechanism** — and the one place a line number was doing real work. `.dash-header h1` is declared **twice, with the byte-identical selector**: an earlier rule setting `font-size: 1.25rem` and a later one setting `1.05rem`. Identical selector means identical specificity, so **source order alone decides and the later occurrence wins**. You cannot disambiguate these two by selector, because the selector is the same string — **identify them by the value each sets**, and if one is ever moved, moving it past the other silently changes the header everywhere.
- **There is deliberately NO resize handler.** One used to close the drawer above 900px, which was right while the tab row took over at that width — closing simply handed navigation back. With the drawer as the only navigation, that same close took away the user's only way to move around the app, mid-drag, with nothing replacing it. Removed in `e83e56c`. **Do not add one back.**
- `.dash-nav { display: none }` is kept as a backstop so a re-added tab row cannot appear alongside the drawer by accident.

### The dashboard header is STICKY (`a62f8d7`)

`.dash-header` carries **`position: sticky; top: 0; z-index: 30`**. It was static from the beginning and nothing had ever revisited it — not a regression, a choice nobody had costed.

**Why:** it follows directly from the section above. With the drawer as the ONLY navigation, scrolling to the bottom of a long list (the payments queue, the attendance roster, the resident list) put the **hamburger off-screen**, and the only way back to navigation was scrolling all the way up. While a tab row existed that cost nothing; once it was deleted, it did.

**`z-index: 30` IS LOAD-BEARING — it is a value in a ladder, not a free number.** The whole ladder:

| element | z-index | |
|---|---|---|
| `.dash-header` | **30** | scrolls beneath nothing; covers `.dash-main` |
| `.dash-backdrop` | 40 | must cover the header while the drawer is open |
| `.dash-drawer` | 50 | covers the backdrop |
| `.modal-backdrop` (Households create) | 50 | |
| `.modal-overlay` (the `/login` legal modals) | 50 | added by PR #8, brought into line by `94737da` |

30 must stay **below 40**, or the header sits on top of the dimming backdrop and its Log out button stays clickable behind an open drawer; and **above 0**, or `.dash-main` content scrolls over the header instead of under it. Two consequences for anything added later: **a new floating element must sit at 40 or above to clear the header**, and **anything given 40+ that is not meant to cover the header will cover it anyway** — that is now a decision every fixed element makes, whether or not its author realises it.

**The cost is vertical space, permanently: 89.6px at 640px and up, 109.6px at 480px and below** (the subtitle wraps to a second line there). That is 10% of a 900px viewport, 12.2% on a phone. Padding was deliberately **not** shrunk to claw any of it back — that is a separate judgement about density, and `.dash-header` padding has already been through one revert cycle (`2c6d7c1` / `07cc26d`).

**Measured against `main` at 1280 and 1920 before shipping — two stylesheets on disk, not a runtime injection — and every value matched exactly: all six protected desktop rules, the 1132px content box, table widths, and `.table-wrap` overflow.** That result is not luck and generalises: `position: sticky` keeps the element **in flow** and does not change its width, and `.dash-header` is a **sibling** of `.dash-main` rather than an ancestor, so it cannot enter the width cascade the payments column budget depends on. The 45.5px of slack in that budget is untouched.

**Nothing needed a `scroll-margin-top`.** No `.jsx` in the app calls `scrollIntoView` or `window.scrollTo`, and the dashboard has no in-page anchors — so there is nothing that could land under the pinned header. (The two `scroll-margin-top` values in `index.css` — 72px on `.landing-hero`, 68px on `.landing-section` — belong to `.landing-nav`, a **different** sticky element on the landing page, which has real anchor links. They are unrelated to `.dash-header` and were never measuring it.)

### Overlays follow one pattern — copy it, do not invent a second

**Two implementations exist: the dashboard drawer (`DashHeader.jsx`) and the `/login` legal modals (`LoginPage.jsx`). A new overlay copies the `/login` one**, and sits at 50 on the z-index ladder above.

- **One effect keyed on the open flag** (`open` in `DashHeader.jsx`, `activeModal` in `LoginPage.jsx`) adds an Escape listener, locks body scroll — **capturing the previous value**, never assuming `''` — and moves focus into the panel (`tabIndex={-1}`). Its cleanup undoes the listener and the scroll lock.
- **Focus RETURN is not in the effect. It lives in the close handler, and every close route must call it** — Escape, the Close button and the backdrop. `closeModal()` in `LoginPage.jsx` does this, returning focus to the link captured from the click.
- **The drawer falls short on one route:** its `.dash-backdrop` calls `close`, not `closeAndRefocus` (both in `DashHeader.jsx`), so a backdrop click drops focus to `<body>` (measured, 12 Sep 2026). Known and not yet fixed.
- **Neither traps focus.** Tab walks out of an open panel into the page behind; adding a trap is a real change to both.
- **The Households create modal (`.modal-backdrop` in `HouseholdsPage.jsx`'s `CreateHouseholdModal`) predates the pattern and follows none of it** — no Escape, no focus handling, no scroll lock. It is a counter-example, not a third implementation.

## Facility Rentals

## Resident Records Management

**Module invariants that outlive the build narrative:**

- **ARCHIVE IS SOFT-DELETE ONLY — a resident record is NEVER hard-deleted.** It cannot be: `document_requests.resident_id` is NOT NULL and holds real data, so a delete would break history. Archiving **CASCADES** — it also deactivates the linked account (`users.is_active = false`) so no "archived but still logging in" state can exist — and unarchive is symmetric. **Known limitation, accepted:** unarchive reactivates linked accounts unconditionally, so an account deactivated *for cause* before the archive would come back active; distinguishing that needs extra state, so the simple symmetric behaviour stands.
- **EDIT IS REACHABLE ONLY FROM THE DETAIL PANEL, NEVER FROM A LIST ROW.** The list projection omits several columns, so prefilling an edit form from a row would **blank them on save**. Archive/Unarchive live in the detail panel for the same reason. This is a correctness constraint, not a UI preference.
- **The duplicate check on add is deliberately SOFT.** It informs and requires confirmation; it never hard-blocks, because same-name-different-person is real. The server re-runs the check and is the final authority — matches without `confirm_duplicate: true` return a **409 carrying the ranked matches** and insert nothing. It reuses `findMatches` with no options passed, so `DEFAULTS` apply and **thresholds are never hardcoded here** — `npm run match:eval` sweeps them.

## Households

The prerequisite for Events stage 3 (household attendance + fines): `household_records`, `household_qr` and `household_members` existed structurally since migration 001 but were empty with no module managing them.

- **NO MIGRATION.** The live schema was introspected before any code (via PostgREST's OpenAPI document, which reports real columns) and **matches Chapter 3 exactly** — no extra columns, no missing ones, all three tables empty. Everything stage 1 needs already exists, so nothing was altered.
- **A household is identified by its HEAD, not its address.** There is no head column: the head is *derived* as the member whose `role = 'Head'` and whose `date_ended IS NULL`. Two households may legitimately share an address, so there is no uniqueness constraint on address — a duplicate address returns a **non-blocking notice** in the create response, never an error.
- **Roles** live in `constants/households.js` (`Head | Spouse | Child | Relative | Other`; `Other` added so boarders/wards aren't forced into a wrong role). `ROLE_ORDER` drives the members-list ordering. **Stage 1 only ever writes `Head`.**
- **Stage 1 implemented (Secretary-only** — Staff, PB, Treasurer and residents all get 403; widening access is a later stage): `GET /api/households` (paginated + searchable), `GET /api/households/:id` (household + members, head first), `POST /api/households` (create + install head).
- **The list mirrors the resident master list exactly** — same 25/page (max 100), same multi-word case-insensitive AND-ed search, same `{ rows, total, page, per_page, total_pages }` shape, same PGRST103 empty-page handling. Those rules now live in `utils/listQuery.js` and `residentRecords.js` was refactored to import them, so there is **one implementation** rather than a copy. Search matches address, household number, and any current member's name (which covers the head, since the head is a member) — the member hop resolves `resident_records` → `household_members` → household ids, the same two-hop the blotter's party search uses. Ordered by household number ascending, because the head's name lives behind a join and can't be sorted on in the query.
- **Create validation:** head must exist and must NOT be archived; a resident may hold only ONE active membership, so a head already in a household is refused with **409 carrying that household's id and head name** so the Secretary can go straight to it; address is required, trimmed, ≤255.
- **Atomicity:** supabase-js still has no transactions, so create uses the established compensation pattern — insert `household_records` → `household_members` (role `Head`, `date_started` = today in Manila, `date_ended` null) → `household_qr` (`crypto.randomUUID()` token, active), unwinding anything already written if a later step fails. A household must never exist without its head, nor a head without a QR row. No column in these tables has a DEFAULT, so every NOT NULL value is set explicitly.
- **`activity_logs` is deliberately NOT written** — no existing module writes it, so this one doesn't invent the pattern.
- **A MEMBERSHIP ROW IS NEVER DELETED.** Leaving a household **sets `date_ended` to today (Manila)**; the row stays, because the history is the audit trail. A resident holds **at most one active membership** (`date_ended IS NULL`) at a time, and a household has **at most one active head**. The **head's membership cannot be ended or role-edited directly** — headship changes only via `POST /:id/head`, so a role edit can never mint a second head. *(Contrast attendance, where deletion IS hard — see Events & Activities → absence is derived.)*
- **DEACTIVATING A HOUSEHOLD ENDS EVERY ACTIVE MEMBERSHIP, AND REACTIVATING DOES NOT RESTORE THEM.** Members must be re-added by hand. **This is deliberately asymmetric with the resident archive/unarchive cascade**, which *does* reactivate the linked account: a dissolved household's members have usually moved on, and blind restoration could double-assign someone who has since joined another household, violating the one-active-membership rule. Restoring an account cannot collide with anything; restoring a membership can. The confirmation states how many memberships will end and that reactivating will not bring them back.
- **UI:** `/secretary/households` ("Households" tab, next to Resident records) — paginated table (Household #, Head, Address, Members, Registered, Status) with row-click into an in-page detail view (household header, address/registered/status, then a members table with Name/Role/Sex/Age/Date started, plus a warning banner if the head's resident record is archived). Create is a **modal** (the dashboard's only one; every other form is inline) with a resident picker for the head that auto-fills the address from that resident, editable; the duplicate-address notice is shown inline after a successful create. The debounced resident picker was extracted to `components/ResidentPicker.jsx` and the blotter now imports it, so both screens share one search.

## Dispute / Blotter Records

- A **sensitive** module: `secretary` manages (create/edit/mark settled), `punong_barangay` views only, and **everyone else — Staff, Treasurer, residents — gets 403** (residents must never see blotter cases, not even their own party entries). Two tables only (`dispute_records` + `dispute_parties`); no hearing schedules, mediation logs, summons, or settlement documents (out of documented scope).
- **Party model:** a party is EITHER a linked resident (`resident_id`, name from the record) OR a typed non-resident walk-in (`first_name`/`last_name`, `resident_id` null) — blotter cases routinely involve non-residents. Roles are `Complainant | Respondent` (`constants/disputes.js`); a case requires at least one of each. `nature_of_case` is a fixed `Criminal | Civil | Others` (varchar(20)).
- **Routes** (`/api/disputes`, `router.use(authenticate)` then per-route role guards): `GET /` (paginated like resident records — `page/per_page/total/total_pages`; `?search=` across case no / filed_for / party name, `?settled=open|settled|all`, `?nature=`, newest `date_filed` first; each row carries a server-computed `party_summary` "A & B vs. C") and `GET /:id` (full parties) are **Secretary + PB**; `POST /`, `PUT /:id` and `PATCH /:id/settle` are **Secretary-only**. Party-name search is a two-hop: linked parties store no name, so it resolves matching `resident_id`s from `resident_records` first, then `dispute_parties`, then filters cases by `dispute_id.in.(…)`.
- **Atomicity (no supabase-js transactions):** create inserts the case then its parties, deleting the case if the party insert fails (a dispute is never party-less). Edit updates case fields, inserts the new parties, then deletes the old ones by their captured ids — reverting case fields and dropping the new rows on any failure. `barangay_case_no` uniqueness is enforced in the app (friendly 409 pre-check + 23505 backstop); **migration 012 adds an OPTIONAL UNIQUE index** — the module runs without it. Referenced `resident_id`s are existence-checked for a clear error instead of a raw FK violation.
- **UI:** shared `DisputesPage` — Secretary's Blotter tab (`/secretary/blotter`, `canManage`: search + open/settled + nature filters, Record case, detail with Edit and a Settle/Reopen toggle) and the same page read-only on the Punong Barangay's Blotter tab (`/punong-barangay/blotter`, no write actions). The create/edit form has case fields + a repeatable parties section; each party toggles between a **resident picker** (debounced search reusing `/api/resident-records`) and typed non-resident names, with a role selector, and enforces ≥1 complainant/≥1 respondent client-side (server is the real gate).

## Events & Activities

- **Two record kinds in one `events` table**, split by `type` (`constants/events.js`): an **`activity`** is a real timed event (start/end REQUIRED, end after start — "General Assembly, Aug 3 8:00 AM–5:00 PM") and an **`announcement`** is an informational notice with NO required window (start/end/location may be null — "Barangay office closed Monday"). Validation enforces the rules per type: an activity without a schedule is a 400, an announcement without one is fine.
- **Migration 013** (REQUIRED — routes select the new columns) adds `type varchar(20) NOT NULL DEFAULT 'activity'` and `is_archived boolean NOT NULL DEFAULT false`, **drops NOT NULL from `start_datetime`/`end_datetime`/`location`** (they were NOT NULL in Table 5, which made announcements impossible), and adds CHECK backstops mirroring the app rules (valid type; activity ⇒ start+end present; end after start when both present).
- **Auto-hide finished activities is DISPLAY LOGIC ONLY** — a past activity is computed from `end_datetime < now` at query time. `is_archived` is never flipped by time and there is no scheduled job. Status is likewise DERIVED, never stored (`deriveStatus()` adds `status` to every row): announcements are always `posted`; activities are `upcoming | ongoing | past`. **Manual archive is separate** (`PATCH /:id/archive|unarchive`, soft delete only; archived records stay readable in the detail route).
- **Stage 1 implemented** (management CRUD + archive; **Secretary AND Staff both manage** — no PB approval gate, since the activity diagram has the PB and residents as view-only): `/api/events` behind `requireRole('secretary', 'staff')` — `GET /` (paginated like resident records; `?view=active|past|archived|all`, `?type=`, `?search=` across title/description/location), `GET /:id`, `POST /`, `PUT /:id`, `PATCH /:id/archive|unarchive`. **View semantics:** `active` = not archived AND (announcement OR activity not yet finished); `past` = not archived AND activity past its end; `archived` = `is_archived` true. **Ordering:** active puts the soonest activity first (`start_datetime` asc, nulls last) with announcements after, newest first; past is most-recently-finished first; archived/all are newest-created first. UI: shared `EventsPage` on `/secretary/events` and `/staff/events` — list splits Activities and Announcements into separate sections, the create/edit form's fields adapt to the chosen type, and status badges show Upcoming/Ongoing/Past/Posted/Archived.
- **Stage 2 implemented** (read-only viewer for `resident` + `punong_barangay`, no migration, no new validation — it only EXPOSES stage 1 data): `GET /api/events/public[/:id]`. The list and detail handlers were factored into shared `listEvents()` / `getEvent()` helpers that both audiences call with a `publicOnly` flag, so the viewer returns the **same shape and the same derived statuses** as management. `publicOnly` limits `?view=` to `active|past` (archived is not an allowed viewer value), adds a belt-and-braces `is_archived = false` filter, and makes the detail route **404 on an archived record** — archived events are invisible to viewers, not merely hidden. The viewer routes are declared BEFORE the `requireRole('secretary','staff')` gate (the layering document types and rental items use), so those roles have no create/edit/archive path at all; the treasurer is excluded from events entirely. UI: `PublicEventsPage` on `/resident/events` and `/punong-barangay/events` — same Activities/Announcements sectioning, search, type filter and Current-&-upcoming/Past views, reusing the stage 1 display constants, with no write actions anywhere.
- **ABSENCE IS DERIVED, NEVER STORED.** A household is absent iff there is **no `event_attendees` row** for it at that event. There is no present/absent status column and there must not be one: the derivation is only trustworthy because `UNIQUE (event_id, household_id)` (migration 015) guarantees at most one row per pair, and an explicit absent row would be a second representation of the same fact — free to disagree with the first, and a silent way to fine the wrong household. Attendance deletion is therefore a **hard** delete, unlike household memberships which are only ever ended with `date_ended`: an attendance row *is* the presence marker, so a soft-deleted one would still make the household look present to any reader that did not know about the flag.
- **VOIDING A FINE IS MANUAL, ALWAYS — recording attendance NEVER touches a charge.** Money must not move as a side effect of an attendance edit. The reason is the partial unique index on `charges (event_id, household_id)`: because it covers the pair **whatever the status**, **a void is PERMANENT for that event** and no replacement charge can ever be raised for that pair. An automatic void would let a single mis-tapped "Mark present" destroy a chargeable fine for good, and undoing the attendance would not bring it back. A disagreement surfaces as a **mismatch** in the preview instead — a household marked present that still holds a live `UNPAID` *or* `PAID` fine — counted separately and flagged on its own roster row. **PAID fines cannot be voided at all** (409): money received is a record, and refunds happen at the Barangay Office. *(An earlier draft auto-voided on late attendance; it was rejected for exactly this reason.)*

## Reporting

- **Read-only aggregation over existing data** — no new schema, no migration, no writes anywhere in `routes/reports.js`. Roles per Chapter 3: **administrative** reports (`/document-requests`, `/residents`, `/facility-utilization`) are `secretary` + `punong_barangay`; the **financial** report (`/collections`) is `treasurer` + `punong_barangay`. The **PB sees both sets** (oversight); Staff and residents get 403 on every report.
- **Default date range: the last 12 months** — the first day of the month 11 months ago through today, so the series always shows 12 labelled buckets. `?from=&to=` override it. Ranges are **capped at 10 years and REJECTED (400) beyond that** rather than silently truncated, which would leave the monthly chart disagreeing with the headline totals.
- **Aggregation strategy:** PostgREST has no `GROUP BY`/`SUM` without a database function, and this module was scoped as no-migration. So plain totals use `count: 'exact', head: true` (computed in the DB, zero rows transferred) and grouped aggregates run **one narrowly-projected query per report**, bucketed in Node — one round trip beats dozens, and the projection keeps the payload small. If volume ever outgrows this, the fix is SQL aggregate functions in a migration (the pattern migration 003 already uses).
- **Data notes:** `rental_requests` has no created-at column, so facility utilization is keyed on `start_datetime` (the date the item was actually used — the meaningful axis anyway), and cancelled bookings are excluded from usage counts. Resident `sex`/`civil_status` are almost entirely null in the current data, so those breakdowns bucket nulls as **"Not specified"** rather than dropping them. Resident population totals are point-in-time and deliberately NOT date-filtered; only new registrations respect the range.
- **CSV export:** `?format=csv` on the **same endpoint** (one convention everywhere), so role checks and the date range apply identically to JSON and CSV. Sends `text/csv` + `Content-Disposition: attachment` with a `<report>-<from>-to-<to>.csv` filename, a UTF-8 BOM so Excel renders the peso sign, and a barangay/period/generated header block above the sections.
- **PDF export: client-side, `html2canvas` + `jsPDF`** — chosen so the recharts SVGs appear exactly as rendered on screen (a server-side rebuild would mean re-implementing every chart). `utils/exportPdf.js` captures the report node at 2× scale, draws an A4 header (barangay name, report title, period covered, generated timestamp) and a page-numbered footer, and **slices across pages at `data-pdf-block` boundaries so a chart is never cut in half**.
- **UI:** shared `ReportsPage` on `/secretary/reports`, `/treasurer/reports`, `/punong-barangay/reports` — a report picker (grouped Administrative/Financial, filtered to the role), from/to date controls, headline stat tiles, recharts line/bar charts, and a plain table of the same numbers underneath so they are checkable. Loading, error, and empty ("No data for this period") states are all handled — an empty range renders the empty state, never a broken chart.
- **Render test:** `cd frontend && npm run test:reports` (needs the backend on :5000). The API tests never mounted the components, which is how a payload from one report reached another report's renderer and blanked the screen in the browser while every API test passed. This bundles the real components with the project's own bundler and server-renders each against LIVE data, plus mounts the `ErrorBoundary` in jsdom — **React error boundaries do not catch during SSR**, so boundary behaviour is only verifiable with a client mount. Cross-report payloads are asserted to throw, as a regression guard. **Limit of what it covers:** the per-report checks server-render, so duplicate-key bugs are structurally invisible to them — React validates keys only in the client reconciler (see `25fe20b` under Frontend Layout).
- **Render-race fix (was a live bug):** switching reports re-renders with the NEW renderer before the effect can refetch, so an untagged payload briefly reached the wrong renderer — each report has a different shape, so it threw and blanked the content area. The fetched payload is now tagged `{ key, data }` and only rendered when `key === selected`. ## GCash Payment Gateway (PayMongo) — implemented

- **Flow: Checkout Sessions** (decided over Sources and Payment Intents) — PayMongo hosts the payment page, so **no payment details ever touch BrgyServe**: one call out, one webhook back. Test mode; keys in `backend/.env` (gitignored, placeholders in `.env.example`), read via `process.env`. **`PAYMONGO_SECRET_KEY` is server-only** — never logged, never sent to the frontend; the browser only ever receives a `checkout_url`.
- **The manual flow is UNCHANGED and remains the fallback.** Cash onsite and the resident-declared GCash reference verified by the Treasurer work exactly as before. A gateway payment produces the *same kind of* `payments` row, so it lands on the Treasurer's normal screen; the only difference is `received_by_user_id` staying **NULL** (Table 16 already described this as "null for online automated payments"), which is the discriminator between a staff-verified and an automated payment. Nothing in the charges/payments model was reworked.
- **Migration 014** adds `charges.paymongo_session_id` and `charges.paymongo_payment_id`, both nullable and **both UNIQUE**. Charges paid at the hall never acquire either.
- **Routes** (`routes/payments.js`, client in `services/paymongo.js`): `POST /api/payments/gcash/checkout` (owner-only — a charge belonging to someone else 404s, not 403; rejects PAID/VOID/zero-amount; **resumes an in-flight session** instead of opening a second one), `GET /gcash/status/:chargeId` (owner-only, what the return page polls — **local read only, it never contacts PayMongo**), `POST /gcash/recheck/:chargeId` (owner-only, the resident's own re-check — see trigger 4 below), `POST /gcash/reconcile/:chargeId` (`treasurer` + `secretary`), and the unauthenticated webhook.
- **Amounts are in CENTAVOS.** Every peso↔centavo conversion goes through `toCentavos`/`toPesos` in one place so a ×100 error cannot creep in. Verified live: a ₱200 charge produced a PayMongo intent of `amount: 20000`.
- **Webhook security — the signature IS the authentication** (PayMongo cannot log in, so an unverified endpoint would let anyone mark charges paid for free). Header `Paymongo-Signature: t=…,te=…,li=…`; HMAC-SHA256 over `` `${t}.${rawBody}` `` keyed with the **webhook's own `secret_key`** (`PAYMONGO_WEBHOOK_SECRET`), NOT `PAYMONGO_SECRET_KEY`. Two hardenings PayMongo's own SDK lacks: `crypto.timingSafeEqual` and a 300s timestamp window against replay. Test-mode keys also refuse `livemode: true` events. The route is mounted in `server.js` with `express.raw()` **BEFORE the global `express.json()`** — the HMAC covers the exact bytes sent, so a parsed-and-reserialised body would fail verification on every genuine call.
- **Idempotency, three layers:** (1) early no-op when this exact PayMongo payment is already recorded; (2) the status-guarded claim `UPDATE … WHERE status = 'UNPAID'` — the same pattern manual verification uses, so concurrent deliveries serialise; (3) `UNIQUE(paymongo_payment_id)` as the database backstop, turning any duplicate that slips past (2) into a 23505 treated as "already recorded". A charge the Treasurer already settled manually is **never** double-recorded. The charge is resolved from the session's `metadata.charge_id`, not from a stored session id, so a late callback for an abandoned-then-recreated checkout still lands correctly.
- **FOUR triggers can settle a charge, all funnelling through ONE function (`settlePaidCharge`)** — that single funnel is the design point: every trigger inherits the same idempotency, so adding one can never create a second way to double-record. Adding the fourth (`c95fd4e`) required no change to the funnel at all, which is the argument for it.
  1. **The signature-verified webhook** — automatic, and the primary path.
  2. **Treasurer reconciliation** — manual recovery, because PayMongo auto-disables endpoints and never replays missed events.
  3. **The checkout-resume interlock** — if a resident starts checkout again on a charge whose stored session PayMongo reports as already paid, the charge is settled there. This exists to prevent a **double payment**: without it the resident would be handed a fresh checkout page for money PayMongo has already collected. Settling (rather than merely refusing) avoids knowingly holding a charge UNPAID after the server has just proven it paid. It is opportunistic — it only fires if the resident clicks again — so it supplements reconciliation rather than replacing it.
  4. **The resident's own re-check** (`POST /gcash/recheck/:chargeId`, `c95fd4e`) — the self-service version of (2), for the resident whose webhook never arrived. Before it, `GET /gcash/status` re-read the local `charges` row and nothing else, so "Check again" could only ever repeat UNPAID however many times it was pressed. **What makes it different from the other three:** it is **owner-scoped** (`charge.user_id !== req.user.user_id` ⇒ **404, not 403**, so charge ids cannot be probed); it **cannot open a checkout session**, only ask about one that already exists, which makes it strictly narrower than (3), the path that already let an owning resident trigger a settlement; a charge with no `paymongo_session_id` is a **409**, not a silent no-op that would read as "GCash says you have not paid"; and it **reuses `RESUME_MESSAGES`** rather than adding a third map, so `gateway:test`'s coverage assertions already govern its wording. It is deliberately NOT the reconcile route with its role guard relaxed — **that one has no ownership check at all**, which is exactly why it stays `treasurer` + `secretary`.
- **Outcome wording is pinned, not incidental.** `SETTLE_OUTCOME` names every outcome in one place, and `RESUME_MESSAGES` / `RECONCILE_MESSAGES` must cover all of them. This followed a real bug found in manual browser testing: the resume path ignored `settlePaidCharge`'s return value and always answered "This charge has already been paid" — including for `underpaid` and `void`, where the money was NOT applied. Telling a resident they have paid when they have not is the worst failure this module can produce. `npm run gateway:test` (backend) enforces it: every outcome has wording in both maps, unsettled outcomes never claim payment succeeded and always point the resident to the Barangay Office, and no raw outcome literal escapes `SETTLE_OUTCOME`. It makes no network calls and does not need the API running.
- **Reconciliation is part of the module, not optional.** PayMongo auto-disables an endpoint after 12 failed retries on each of 3 consecutive events and **never replays what was missed**, so a tunnel/server outage could otherwise strand a genuinely paid charge as UNPAID forever. "Re-check with PayMongo" on the Payments screen re-reads the checkout session and settles through the *same* `settlePaidCharge()` the webhook uses — so it can never double-record.
- **The redirect is NOT proof of payment.** `PaymentResultPage` (`/resident/payment-result`) reads the charge's real status back from the API and polls until the webhook lands; if confirmation never arrives it tells the resident **not to pay again** and to show their GCash receipt to the Treasurer. Residents see three clearly distinguished options: **"Pay online via GCash"** (gateway), "Pay onsite", and **"I already paid via GCash"** (the unchanged manual reference flow).
- **The two buttons on that page do different things, deliberately.** "Check again" re-reads our own record (the local poll, right while the webhook is seconds away); **"Ask GCash directly"** is trigger 4 and names the system it queries so the two are tellable apart by someone who has paid and is worried. It locks for **10 seconds** after each press — an outbound PayMongo call per click, and **the rate limiters added in `71bfc37` cover only the three unauthenticated auth routes, not this one**, so the cooldown is client-side only and is not a security control. (The route is authenticated and owner-scoped, so a caller must already hold a session and can only ask about their own charge — which is why it was left unlimited, not an oversight.)
- **The billing prefill sends the phone as BARE NATIONAL DIGITS** — `9171234567`, no country code and no leading zero — because PayMongo renders **"+63" as a fixed label beside the input**, and their own placeholder in that field reads `917 123 4567`. `toNationalMobileDigits()` in `routes/payments.js` normalises the stored `09XXXXXXXXX` on the way out; an unparseable number returns null and the field is **omitted rather than sent malformed**, the same rule already used for a number that is absent (42 of 47 residents have none). **Verified by screenshot of the hosted page on 18 Aug 2026, and this describes their CURRENT UI, not a documented contract** — the field has now changed behaviour twice, so re-check the rendered page rather than this note if the prefill ever looks wrong again. See also the E.164 attempt under Decided Against.
- **Verified end to end against the live sandbox** (27/28 + 9 authorisation + 8 signature checks, plus a full manual browser run-through): a real test GCash payment → PAID charge with one `payments` row (`gcash`, reference = the `pay_…` id, `received_by_user_id` NULL) visible on the Treasurer's screen; duplicate webhook delivery → `already_recorded`, still one row; Treasurer-settled-first → no second row, manual record kept; webhook disabled → charge stranded UNPAID → reconcile recovers it, and reconciling twice is a no-op. Forged, tampered, replayed and stale-signature requests are all rejected. **Known PayMongo sandbox defect:** their "Fail Test Payment" endpoint (`/sources/{id}/fail`) returns HTTP 500 for GCash sources — their bug, not ours; the resulting state is still correct (source stays `pending`, charge stays UNPAID, no `payments` row), which is also what an abandoned checkout produces. On PayMongo's hosted test page the button to click is **"Authorize Test Payment"**; avoid "Fail Test Payment" because of that defect.
- **Trigger 4 verified in the browser, 18 Aug 2026** (`c95fd4e`): the **409** on a charge with no checkout session; the reached-PayMongo wording on an abandoned session — which is the proof the route really leaves the server, since the local poll cannot produce that sentence; the **10s cooldown** locking the button between presses; and the **`recorded` path settling a real sandbox payment**, leaving **one** `payments` row on the Treasurer's screen. That last one is the assertion that matters: a second row would have meant the funnel's idempotency did not hold from the new entry point.

## Notifications

**NO MIGRATION.** `notifications` (Table 17) has existed since migration 001; it was empty and nothing read or wrote it. `status` is `varchar(50)` with no CHECK, so the extended vocabulary needed no schema change — only the Table 17 doc edit, which is done.

- **No SMS is ever sent. `SMS_MODE` defaults to `SIMULATED`** (unset behaves as SIMULATED, so a missing value can never send anything) — messages are composed, addressed and recorded, and stop there. No provider, no API key, no HTTP call on the SMS path. **The ONE exception in the whole project is email, and only for password reset** (`EMAIL_MODE=RESEND`) — see `docs/brgyserve-implementation-log.md` → "Forgot password — IMPLEMENTED". `EMAIL_MODE` is a **separate variable** precisely so this exception cannot spread to SMS: no SMS setting can route email and no email setting can claim an SMS was sent.
- **`SIMULATED` is its own status, never `SENT`.** Recording SENT for a message nobody sent would make the log assert something untrue, which is the whole point of choosing this over a half-finished real integration. `sent_at` stays NULL for the same reason — "when it was sent" has no honest answer. The screen states plainly that sending is simulated.
- **`SKIPPED` rows are written when there is no contact number** (43 of 47 active residents). The row is kept rather than dropped: `destination` is NOT NULL so it stores an empty string, the status carries the reason, and the screen's "No contact number" count becomes the barangay's list of residents it cannot reach — the argument for collecting numbers.
- **The provider seam is one function body.** `PROVIDERS` in `services/notifications.js` maps **type → mode → adapter** (it mapped mode → adapter until forgot-password, which could not have reached an email adapter at all). SMS: `SIMULATED` is implemented, `SEMAPHORE` is a documented placeholder that returns FAILED without making a request — going live is write that body, set `SMS_MODE=SEMAPHORE`, and no call site, route or screen changes. Email: `SIMULATED` and a real `RESEND` adapter, both implemented.
- **THE REDACTION SPLIT IS MANDATORY, and the reason is an account-takeover path, not tidiness.** `notify()` takes the **sent** message and the **recorded** message separately (`message` and `logMessage`). `/secretary/notifications` renders `notifications.message` on screen for the Secretary, so **a reset link stored in that column is readable by every Secretary, who could use it to take over any resident's account.** Hashing the token in `password_resets` does not substitute for this — the raw token would be sitting in `notifications.message` in plain text one table over. The two strings are written **separately in `constants/passwordReset.js`, never derived from one another**: a redaction implemented as "take the sent message and strip the link" is one regex away from leaking. Structurally, `buildRow()` never sees the sent text at all.
- **A backstop refuses to record ANY message matching `/[?&]token=/`.** The split above is the mechanism; this is the guard for the next link-bearing message someone writes without `logMessage`. It **refuses the write** rather than recording a live token, and because `notify()` never throws, the effect is a FAILED result and a loud log line while the business action that triggered it is untouched. **This changes what a regression looks like**: dropping `logMessage` no longer leaks — it silently stops recording the notification. That is why `reset:test` asserts **both** that no URL reaches the column **and** that a row was nonetheless recorded; the safety assertion alone would pass either way.
- **FAILURE ISOLATION — `notify()` and `notifyMany()` NEVER throw.** Their whole bodies are wrapped and they return `{ ok, status }`. Every call site runs *after* its business write is committed, so a notification problem cannot roll back an approval, a rejection, a payment or a fine. `notifyMany()` batches fine generation into ONE insert — an assembly can cover every household and must not become a write each.
- **Phone number source of truth: `resident_records.contact_number` wins — with ONE documented exception.** `profiles.phone_number` is what the resident *claimed* at registration; the record is what the barangay maintains, and eight of the nine call sites read it. **The exception is registration rejection**, where the applicant usually has no linked resident record at all — being unmatchable is the commonest reason to reject one — so the claimed number is the only number in existence. That call site reads `profiles.phone_number` **by availability, not by preference**; see Auth & Account Approval. **Bug found and fixed:** `POST /api/secretary/pending-residents/:userId/link` (link to an EXISTING record) silently discarded the claimed number, while the create-and-link path copied it — so linking to a record with no number on file lost the only number the barangay had. `/link` now backfills, but **only into a blank**; a number the Secretary entered is never overwritten. Reported as `contact_backfilled` in the response.
- **Encoding matters and is enforced.** `₱`, `—` and `×` are outside GSM 03.38 and force UCS-2, cutting the segment from 160 characters to 70. Replacing them with `PHP`, `-` and `x` took one round of all ten templates from **18 credits to 10 (44% cheaper)**. A test asserts no template contains those characters, so it cannot regress.
- **Screen:** `/secretary/notifications` (Secretary-only — it exposes contact numbers and message content). Read-only: no re-send, no delete, no POST route. Filters by status and by what the message relates to; summary counts run over the whole log, not the page.
- **Test: `cd backend && npm run notif:test`** — no server, no network, `SMS_MODE` forced to SIMULATED. The centrepiece is failure isolation: the `notifications` table is sabotaged to throw, a real document-request approval is invoked through its actual route handler, and the test asserts the approval still returns **200**, the request is still `approved`, the charge still exists, and no notification row was written (proving the failure was real and not skipped).

## Outstanding work on the live system

**The system is deployed** — frontend on Vercel (`https://brgyserve.vercel.app`), backend on Render (`https://brgyserve-api.onrender.com`). Every module is built, so the items below are housekeeping on a running system rather than blockers before launch. They are still live-system work: real accounts and real payment plumbing are in play, so treat them accordingly.

- **RLS is now ENABLED on all 19 tables, with ZERO policies written.** With RLS on and no policy to permit anything, direct table access through the anon/publishable key is denied by default — previously that key could read *and* write 17 of the 19. The backend is unaffected because the **service role key bypasses RLS entirely**, and authorization was never in the database anyway: it lives in the Express layer (`authenticate` + `requireRole`). **Still outstanding:** per-role policies (`secretary`, `punong_barangay`, `treasurer`, `staff`, `resident`), needed only if anything is ever given direct database access. Note they cannot key off `auth.uid()` — auth here is custom JWT, not Supabase Auth, so it is permanently NULL.
- **Rotate the weak passwords already on file — and it is more than the two accounts this bullet used to name.** `secretary1` and `pb_ubujan` were shared in plaintext during development, but the measurement taken during `d58c83a` found **ten of the then-nineteen accounts had identifiable weak passwords**, and **nine could not be identified at all** — bcrypt is one-way, so those are unknown rather than fine. The new password policy does **not** fix this: login never runs the rules, so every one of them still works. `must_change_password` is `false` on every account, so nobody meets the new rules by accident either. Remediation means deliberately setting `must_change_password` on named accounts, which is its own task and has not been done. **The database is now at 18 accounts, not nineteen** — `staff_test` and `staff_test2` were created to test the no-op password change fix (`a08a752`) and deleted afterwards by a guarded block, and `test_email_a` was created and deleted the same way while walking through email uniqueness. The ten/nine split was measured against the nineteen present at the time, so re-measure before acting on it rather than assuming which accounts it named.
- **RATE LIMITING EXISTS on the three unauthenticated auth routes (`71bfc37`), and nowhere else.** This bullet used to say there was none anywhere, with a grep as evidence; that was true when written and is now wrong in every particular. What is there: **`/login` 5 per 15 minutes with `skipSuccessfulRequests`** (a successful sign-in is refunded, so someone who gets it right on the fifth try is not left one attempt from a lockout — but note a **403** from an inactive, pending or rejected account **counts**, even with the correct password), **`/register` 5 per hour**, **`/forgot-password` 10 per hour**. Everything else in the API is behind `authenticate`, so a caller needs a valid session before they can spend anything.
  - **Keyed on the CONNECTION, never on the account or username** — `cf-connecting-ip` first, falling back to `req.ip`. That choice is deliberate and not a shortcut: an account-keyed limiter is an **account lockout**, which lets anyone deny service to any user just by guessing at their username. The failure mode of connection-keying is that a shared address is limited together; the failure mode of account-keying is a weapon.
  - **The reason it exists is unchanged and worth keeping**: `POST /api/auth/register` is unauthenticated and **writes rows to `users` AND `profiles`**, so nothing stopped ten thousand pending registrations flooding the Secretary's review screen. Forgot-password was the worse case still, because its side effect is outbound and metered (Resend free tier: 100/day, 3,000/month), so exhausting the quota breaks the feature for everyone.
  - **The store is IN MEMORY, so counters reset on every cold start** — and Render's free tier sleeps after about 15 minutes idle, as does every deploy. That costs less than it sounds against a sustained attacker: they keep the instance awake by attacking it, so the idle timer never fires, and going quiet for fifteen minutes to clear a counter is the outcome the limiter wanted anyway. **What it does cost is the record** — after a redeploy there is nothing to show anyone was ever limited. A persistent store is the fix if that ever matters.
- **PayMongo stays in SANDBOX — going live is explicitly NOT a to-do.** Putting real money through a student capstone demo is out of scope, so the `sk_test_`/`pk_test_` keys stay as they are. (For reference, if that ever changed it would mean swapping in live keys, re-registering the webhook against the deployed origin for a new `secret_key`, and confirming the signature check compares against `li=` rather than `te=` — the code already selects on live-vs-test but has only ever run against test keys.)
- **The `/login` timing oracle tells an attacker whether a username exists, and it is deliberately NOT fixed.** `const valid = user && (await bcrypt.compare(…))` short-circuits, so a username that does not exist skips bcrypt entirely. Measured: **58.3 ms** of difference at cost factor 10. Rate limiting narrows it — five attempts per fifteen minutes is a slow way to enumerate — but does not eliminate it. Closing it means comparing against a dummy hash on the miss path so both branches cost the same, which is a change to the login handler and was out of scope for the rate-limiting work.
- **`POST /api/auth/register` now returns TWO 409s, and both are enumeration oracles** — no measurement needed, just read the status code. **"Username is already taken"** discloses which usernames exist, and since `952e971` **`EMAIL_TAKEN`** discloses which email addresses do. Both are arguably unavoidable: a registration form has to tell someone their chosen username is taken, and it has to tell them the address is already registered or they cannot proceed. The email one is the more sensitive of the pair — an address identifies a person off-system in a way a username does not — and it is also the one that makes password reset unambiguous, which is why it was accepted. `POST /api/secretary/accounts` returns the same pair, but it is behind `requireRole('secretary')`, so it discloses nothing to an anonymous caller. Recorded so both are known accepted disclosures rather than something discovered at the defense.
- **Logout revokes nothing server-side, so a stolen token outlives the password change meant to stop it.** The JWT carries only `sub` and `role`, and `authenticate` never reads `password_hash`, so changing a password — by reset or by `/change-password` — leaves every issued token valid until `exp`, **up to 8 hours**. If the reason for the reset is that someone else is in the account, they stay in. The fix is `users.password_changed_at` plus an `iat` check in `authenticate`; it edits the middleware every route depends on, which is why it has been deferred rather than bundled into any of the auth work so far.
- **The Vercel frontend sends no CSP and no `X-Frame-Options`.** `24665ba` added helmet to the **API**, which is a different origin — nothing was added on the frontend, so `https://brgyserve.vercel.app` can still be framed by any site. The fix is a headers block in `frontend/vercel.json`, not a code change.
- **`cd frontend && npm run test:auth` DOES NOT RUN, and has not since the PR #4 image merge.** It dies before executing a single assertion: `[UNLOADABLE_DEPENDENCY] Could not load src/assets/brgy-personnel.jpg` (`LoginPage.jsx`) and the same for `src/assets/brgy-hall.jpeg` (`LandingPage.jsx`), both "stream did not contain valid UTF-8". **The cause is the harness, not the code it guards:** `scripts/test-auth-session.cjs` builds with rolldown and configures no asset loader, so the two images those pages import are read as UTF-8 source. **The session-handling behaviour it covers is unaffected and still correct — but it is currently unguarded**, so a regression in `readStored()`, `authFetch` identity stability or the single-teardown collapse would not be caught. The fix is an asset loader in the harness build config.
- **`/login` now loads THREE images totalling about 1.34 MB, and this bullet used to describe one at 513 KB.** The PR #5 merge (`488e529`) moved `brgy-personnel.jpg` into `frontend/src/assets/loginSlider/` — **the old path in this bullet was wrong** — and added two more beside it for the slider:

  | file | size |

  | `assets/loginSlider/ubujan-event-group-foto.jpg` | 427,654 B |
  | `assets/loginSlider/ubujan-group-photo.jpg` | 418,817 B |
  | **total on `/login`** | **≈ 1.34 MB** |

  Roughly **2.6× the payload** on the app's entry screen, on a Free-tier instance that already takes 30–45 s to wake. Each is displayed in a panel that is half the viewport, so resizing to the rendered width and re-encoding as WebP would still cut the total by about an order of magnitude. Outstanding since the PR #4 merge (`9adea3c`), whose commit message records the original as still to be reduced; PR #5 tripled it rather than addressing it.

## Decided Against — do not revisit

Each of these was investigated, measured, and deliberately left as it is. They are recorded so the same ground is not covered a second time.

- **The payments table overflowing `.table-wrap` below about 1135px.** It is correct at **1280 and 1920, so no demo resolution is affected**, and `.table-wrap { overflow-x: auto }` already provides the scroll. Hiding columns was rejected on domain grounds: **"Declared payment" is precisely what the Treasurer checks against GCash** before verifying, so hiding it would make the screen useless for its main task. Shortening the button labels was **measured impossible** — with every button removed the Actions column still measures exactly 200px, its `.row-actions` floor, so that approach can recover at most 27.7px against a 91px gap at 1024.
- **Row dividers not painting under the action column.** Diagnosed by rasterising the rendered page: a `display: flex` `<td>` is not stretched to its row's full height, and **the shortfall varies with row content**, so no single shadow offset can cover it. Both remaining fixes change table-cell display app-wide — a blast radius out of all proportion to a cosmetic divider.
- **E.164 for the PayMongo billing phone.** Sending `+639171234567` rendered on their hosted page as **`+63  +639171234567`** — composing to `+63639171234567`, worse than the bug it replaced (a stored `09171234567` showing as `+63 09171234567`, one digit too many). Their `+63` is a **fixed label beside the input**, so the field must carry the bare national number only. The correct form and the evidence for it are recorded under GCash Payment Gateway; `toNationalMobileDigits()` carries the same warning in a comment, because the tempting "fix" here is exactly the wrong one.
- **Semaphore SMS.** The minimum top-up is **1,000 credits at PHP 560** for a demo that sends roughly 20 messages. **`SMS_MODE` stays `SIMULATED`.** The provider seam described under Notifications is real and still one function body; the decision is that it will not be exercised, not that it does not exist.
- **`pg_trgm` living in the `public` schema**, which Supabase's advisor flags. Moving it **drops the GIN trigram indexes Stage 1 blocking depends on** — the whole performance argument of the two-stage design. The warning stands; the extension stays.
- **The search input collapsing at 500px on `.list-head` screens.** Pre-existing, unrelated to any recent change, and nothing is demoed at 500px.
- **The 1420px fixed desktop sidebar** that was to replace the horizontal nav row. **The drawer is the permanent desktop navigation instead, at every width** (see Frontend Layout). One nav implementation rather than two, no breakpoint to keep in sync between CSS and JS — the pair that used to disagree by ~15px on Windows is simply gone — and no new element competing for horizontal space, so `.dash-main`'s 1180px cap and the 720px form cap are untouched and the payments column budget keeps its full 1132px content box. A sidebar would have reopened all three.
