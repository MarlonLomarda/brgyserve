# BrgyServe

## Project Overview

BrgyServe is a web-based document request and tracking system for **Barangay Ubujan, Tagbilaran City, Bohol**. It is a capstone project that digitizes barangay services: residents request official documents online and track their status, while barangay officials process requests, manage resident records, handle facility rentals and payments, record disputes/blotter entries, and generate reports.

## Tech Stack

- **Frontend:** React (scaffolded with Vite) — `/frontend`
- **Backend:** Node.js with Express — `/backend`
- **Database:** Supabase (PostgreSQL)

## Environment / Secrets

Supabase credentials live in `backend/.env` (see `backend/.env.example` for the required keys). **Never hardcode keys in source files and never commit `.env`.** The service role key bypasses Row Level Security and must only ever be used server-side.

**`SUPABASE_SERVICE_ROLE_KEY` is REQUIRED and the API refuses to boot without it** (`8a949aa`). There is no fallback to the anon key and adding one back would be a bug: RLS is enabled on every table with **zero policies**, so the anon key reads nothing, and the old fallback produced a server that started green, answered `/api/health`, and then returned an **empty result set for every query** — a login reading as "invalid credentials", a resident list reading as "no records". Refusing to start is the better failure, and it is the same reasoning as the `VITE_API_URL` guard above; the difference is that this guard is unconditional, because no environment legitimately wants the anon key. `SUPABASE_ANON_KEY` is **not read by the backend at all** and is kept in `.env.example` only so its absence is not mistaken for an oversight.

The frontend needs `VITE_API_URL` — the API origin **including** the `/api` suffix. It is **required for every build**: `vite.config.js` throws rather than let a build fall back to `http://localhost:5000/api`, which used to deploy green while every request in the browser pointed at a machine that is not there. Locally that means `frontend/.env` must exist (gitignored); on Vercel the value comes from the project's Environment Variables panel. **This reverses the older "delete `frontend/.env` before building" rule** — deleting it now fails the build, which is the point. The dev server keeps the localhost fallback.

## Deployment

The system is live on two hosts, each deploying from `main`.

- **Frontend — `https://brgyserve.vercel.app`** (Vercel). **Root Directory `frontend`**, which is why `vercel.json` lives in `frontend/` and not at the repo root — at the root Vercel would never read it, and the SPA rewrite would silently not apply. `VITE_API_URL` is set to `https://brgyserve-api.onrender.com/api` in the project's Environment Variables panel; the `/api` suffix is part of the value, not appended by the client.
- **Backend — `https://brgyserve-api.onrender.com`** (Render). **Root Directory `backend`**, build `npm install`, start `npm start`, **Free tier**, Singapore region. **13 environment variables**, including `FRONTEND_URL` and `PUBLIC_FRONTEND_URL` — both the Vercel origin, but they are not interchangeable: `FRONTEND_URL` is the **comma-separated CORS allowlist** (`server.js`), `PUBLIC_FRONTEND_URL` is the **single origin the resident is redirected back to** after a GCash payment (`routes/payments.js`), which a list cannot express. `PUBLIC_BASE_URL` is the Render origin, and is what the PayMongo webhook is registered against. The `.env.example` mnemonic still applies: `PUBLIC_BASE_URL` is where PayMongo reaches us, `PUBLIC_FRONTEND_URL` is where the resident is sent back to.

**The Free tier sleeps after about 15 minutes idle, and the first request after that takes 30–45 seconds** (measured, not estimated). **Before any demo, open `https://brgyserve-api.onrender.com/api/health` about five minutes ahead** so the instance is awake and the first real click is not the one that pays for it.

**A cold backend returns 502 on the CORS preflight.** The browser console reports that as a **CORS error** and the app shows "Cannot reach the server", so it reads exactly like a misconfiguration — **it is not one, and there is nothing in the CORS setup to fix.** The instance is asleep and the preflight `OPTIONS` never reached it. Wake it and retry. This cost real debugging time once; it is recorded so it does not cost it twice.

**Local development no longer receives PayMongo webhooks.** The single webhook points at Render (see the Dev tunnel section — `npm run tunnel` must never be run again), so a GCash payment made against a local backend is never delivered to it. Those charges settle through the Treasurer's **"Re-check with PayMongo"** on the Payments screen, which re-reads the checkout session and settles through the same `settlePaidCharge()` the webhook uses. That is the intended local workflow now, not a workaround.

## Auth & Account Approval

- Custom JWT auth (`jsonwebtoken` + `bcryptjs` hashing) against the `users` table — Supabase Auth is NOT used. Requires `JWT_SECRET` (and optional `JWT_EXPIRES_IN`) in `backend/.env`.
- Resident self-registration (`POST /api/auth/register`) creates a **pending** account: `is_active = false`, `profiles.resident_id = null`. Pending accounts cannot log in.
- Login's message for an inactive account (`inactiveMessage` in `routes/auth.js`) has **THREE branches, and only two of them are derived**. The 403 block itself never changes — none of these accounts may log in; only the wording differs.
  1. **REJECTED** — `users.is_rejected`. Checked **FIRST**, and it must stay first: a rejected resident satisfies branch 3 as well, which would swallow it. Returns the reason code's canned sentence.
  2. **ARCHIVED** — linked to an **archived** `resident_records` row ⇒ "This account has been deactivated. Please contact the Barangay Office." Derived: the archive cascade deactivated a previously *active* account.
  3. **PENDING** — any other `resident` ⇒ the pending-approval message, correct both before and after a record is linked (linking and activating are separate steps). Anything else ⇒ a generic "This account is inactive."
- **This section used to argue that no extra column was needed, from there being exactly two paths that clear `is_active`. That argument is dead and the reasoning is worth keeping, because it is the whole justification for migration 017.** A pending registration is *created* with `is_active = false`, so "rejected" could not be expressed by clearing a flag that was already clear — **pending and rejected were byte-identical row states.** Rejecting was therefore a no-op, and login answered "pending approval by the Barangay Secretary" to an applicant whose registration had already been declined. Nothing on `users` or `profiles` was free to hold it either: the live schema was read from PostgREST's OpenAPI document before any code, and all 8 + 10 columns were spoken for. `email_verified` (written, never read) and `profile_pic` (never referenced anywhere) were structurally available and **deliberately not repurposed** — a column named `email_verified` holding "this registration was declined" makes every future reader wrong. *(That count is the state as of migration 017. `profile_pic` has since been dropped in migration 019 — see the next entry; `profiles` is now 9 columns.)*
- Secretary review (role `secretary`, routes under `/api/secretary/`): list pending accounts, link each to an existing `resident_records` row or create-and-link a new one, then **activate or reject**. Activation requires a linked resident record. **Activation is no longer the only decision** — see the rejection module below.
- Active residents view their own record via `GET /api/residents/me` through the `profiles.resident_id` link.
- Staff-type accounts (`secretary`, `punong_barangay`, `treasurer`, `staff`) are created only by the Secretary via `POST /api/secretary/accounts` — active immediately, with a generated temporary password (returned once in the response) and `must_change_password = true`.
- Forced password change: `authenticate` default-denies every request from a `must_change_password` user with a 403 + `code: 'PASSWORD_CHANGE_REQUIRED'`; only routes wrapped with `allowPendingPasswordChange` (i.e. `POST /api/auth/change-password`) are reachable. The frontend mirrors this by routing such users to `/change-password`.
- `authenticate` middleware re-reads the user per request, so deactivating an account (or clearing the password flag) takes effect immediately.

### Two unused columns, two OPPOSITE decisions — the difference is the point

Both were unused. Both were eyed as a home for the rejection state in migration 017 and refused. They then went different ways, and **which way each went is not arbitrary — it turns on whether anyone intends to use it.**

| column | verdict | why |
|---|---|---|
| `profiles.profile_pic` | **DROPPED (migration 019)** | a resident photo was **declined**, not deferred |
| `users.email_verified` | **KEPT, unused** | **reserved** for planned email verification |

- **`profiles.profile_pic` was DROPPED. Do not re-add it thinking it was an oversight — it was removed on purpose.** A resident photo feature was considered and **declined on data-minimization grounds**: under the Data Privacy Act a photograph needs a stated purpose, and **no function in BrgyServe uses one** — document requests are identified by the resident record, attendance is per household by QR, payments by charge, and the Secretary verifies an applicant by name, birthdate and address. This is the same reasoning already applied to the **Staff narrowing** (see Resident Records Management → DATA MINIMIZATION), where each field Staff receive had to earn its place and the rest were withheld: a field with no task behind it is not collected. Verified before dropping — no read, no write, no select list, no form field, no test, and `git log --all -S "profile_pic"` returned only the three commits that define or describe it. The live column was empty (0 of 17 rows non-null), confirmed by count rather than assumed. **Dropping a column is irreversible without a restore**, which is why the migration's review block counts before it commits.
- **`users.email_verified` is KEPT despite being equally unused. It is RESERVED, not dead, and must not be dropped in a future cleanup.** The group intends to add email verification; the column is written `false` at both account-creation paths (`routes/auth.js`, `routes/secretary.js`) and read nowhere, which is exactly what a reserved column looks like mid-way to a feature. **It must also never be repurposed to hold anything else** — that was refused for the rejection state in migration 017 for the reason stated above, and the refusal stands for whatever the next tempting reuse is. A column named `email_verified` holding something other than whether an email was verified makes every future reader wrong.

**The general rule this pair establishes:** an unused column is dropped when nobody intends to use it and kept when somebody does. "Unused" alone decides nothing — and neither is ever a free slot for unrelated data.

### Registration rejection (migration 017)

- **Migration 017 adds five columns to `users`:** `is_rejected boolean NOT NULL DEFAULT false`, `rejection_reason varchar(50)`, `rejection_note varchar(255)`, and the `rejected_at` / `rejected_by_user_id` accountability pair (matching `payments.received_by_user_id` and `rental_requests.returned_by_user_id` in type and FK target — a rejection may be contested at the office, so who decided it must be answerable). Two CHECK backstops mirror the app rules: `users_rejection_state_consistent` (not rejected ⇒ all four detail columns null; rejected ⇒ reason + `rejected_at` + `rejected_by_user_id` all present) and `users_rejection_reason_valid` (the code vocabulary). **The migration is a hard dependency — `routes/auth.js` login selects `is_rejected`, so login 500s for every user until it is applied.** Same shape as migration 016's dependency on the Events endpoints.
- **Fixed reason codes** in `backend/src/constants/registration.js` (UPPERCASE, matching charges and notifications): `NOT_IN_MASTERLIST | RESIDENCY_TOO_SHORT | OTHER`. Each carries the **canned sentence the applicant is shown at login**, and each sentence says what to do **next** rather than only stating the verdict — a rejected applicant with no next step just returns to the same dead login. They deliberately never say "register again": the account still exists and the username is taken, so that would fail. All three are inside GSM 03.38 and compose to **one SMS segment**. `OTHER` is the only code that requires a note. `frontend/src/constants/registration.js` mirrors the labels; the applicant sentence is deliberately **not** copied there, because the frontend never renders it and a copy could only drift.
- **The note is INTERNAL and never leaves the office** — not in the login message, not in the SMS. That is what lets the Secretary write something specific without it becoming a message to the person it is about.
- **Routes** (`/api/secretary/`, inheriting the router-level `requireRole('secretary')`): `POST /pending-residents/:userId/reject` (valid code required; note required for `OTHER`; 409 on an already-active or already-rejected account) and `POST /pending-residents/:userId/unreject`. `GET /pending-residents` gained **`?status=pending|rejected|all`**, default `pending`, with an unknown value a **400 rather than a silent fallback** — following `?archived=` on resident records and `?view=` on events.
- **ACTIVATE NOW REFUSES A REJECTED ACCOUNT with a 409.** This was a real bug: activate checked only `is_active` and `profiles.resident_id`, and a rejected account is still `is_active = false`, so it matched the pending list and could be activated straight from it — the decision undone by the next click with nothing to show it had been made. The update is also status-guarded (`.eq('is_active', false).eq('is_rejected', false)`), closing the read-then-write gap.
- **Rejection is REVERSIBLE.** Eligibility changes — someone gets added to the masterlist, or reaches six months. Un-reject clears all five columns and returns the account to exactly the pending state, from which link-and-activate continues normally. Un-reject deliberately sends **no** notification: nothing was granted, the applicant still cannot log in, and a message would announce a non-event.
- **A `notifications` row is written on rejection** (SIMULATED like every other call site), via a new `RELATED_TYPE.ACCOUNT` — a constants-only change, since `related_type` is `varchar(50)` with no CHECK. `frontend/src/constants/notifications.js` gained the matching `RELATED_TYPE_FILTERS` entry, or the rows would be unfilterable on the Notifications screen. **This is the ONE call site where `profiles.phone_number` is the number used** — everywhere else `resident_records.contact_number` wins, but a rejected applicant usually has no linked record at all (being unmatchable is the commonest reason to reject one), so the claimed number is the only number in existence. **An exception by availability, not by preference.**
- `rejected_by_user_id` is resolved to a username with a **second query, not a PostgREST embed** — the embed would be a self-referential join needing the FK constraint name, which could not be verified before the migration was applied.

#### THE SIX-MONTH RESIDENCY RULE IS NOT AUTOMATED, AND MUST NOT BE

The barangay's rule, confirmed with the Secretary, is that an applicant must be in the masterlist **and** have been registered in it for at least six months. **Nothing computes that, on purpose.**

**`resident_records.date_registered` is the timestamp the row entered BrgyServe — not the barangay's own registration date.** It is server-set on insert at both creation paths and is never client-writable (`validateBody` builds from an allowlist that excludes it), so it cannot be corrected even when the Secretary knows the real date. Measured against the live data: **all 47 non-archived records were created in July 2026, so a six-month check against that column would reject 100% of them** — including a resident on the paper masterlist since 2009. Implementing the rule against `date_registered` would be wrong every single time it fired.

So the **Secretary applies the rule and records `RESIDENCY_TOO_SHORT`** when it fails. The system informs that judgement; it never makes it.

### Stage 2 implemented — `masterlist_registered_on` (migration 018)

- **Migration 018 adds `resident_records.masterlist_registered_on date`** — the barangay's OWN registration date, which is what the six-month rule counts from. **Nullable, no default, no CHECK, no index.** No CHECK because the rule is "not in the future" and expressing that needs `CURRENT_DATE`, a non-immutable expression in a constraint; `birthdate` has the identical rule and no database constraint either, enforced in `validateBody()`. No index because the comparison is display-only and never a query filter. `date_registered` is unchanged and both columns are kept — they measure different things.
- **Secretary-writable on add AND edit**, unlike `date_registered`. The `birthdate` validation block was factored into a shared **`validateOptionalDate(body, field, label)`** so both date columns validate identically — shape (regex) before validity (`Date`) before not-in-the-future, composed at **`+08:00`**, with a blank clearing the column. One implementation, because the `+08:00` on one and not the other is exactly the divergence that survives review. `date_registered` stays locked by construction, not by a denylist: `value` is built key-by-key, so an unnamed column cannot enter an insert or update.
- **`deriveResidency()` / `withResidency()` live in `constants/registration.js`**, not a route file. The `deriveStatus()` precedents in rentals and events sit in their route because only that route serves them; this one is served by **two** (`residentRecords.js` and `secretary.js`), and putting it beside `RESIDENCY_MINIMUM_MONTHS` keeps the threshold next to `RESIDENCY_TOO_SHORT`, the reason code it justifies. **Display-only, never stored**, same rule as both precedents. `>=` on the boundary: exactly six months COUNTS, which is what "at least six months" means.
- **`deriveResidency(null)` RETURNS `null`, and that is load-bearing.** It must never return a shape with `meets_minimum: false` for a missing date. `false` is a **positive claim** — "we checked, they do not meet it" — indistinguishable from "there was nothing to check", so every record the barangay has no date for would wear an under-six-months badge and the Secretary would decline people for failing a test that never ran. Same defect as `account: null` and `linked_accounts: []` in the Standing Rules, in a new place. The frontend renders **NOTHING** when it is absent: no date, no badge, no "unknown" pill.
- **ADVISORY ONLY, everywhere.** Nothing reads `meets_minimum` to block, disable, hide or gate anything. Activate works exactly as before on an under-six-months account. The badge reuses the amber `.badge.status-pending` variant — a caution, not an error — and **no CSS was added**.
- **Staff do not receive the column.** In `LIST_FIELDS`, not in `STAFF_FIELDS`. Argued from the written purpose of Staff access (confirming a resident is registered — an identity task): no Staff task uses the date, the whole rejection module is Secretary-only, and `date_registered` is already withheld, so exposing a second and more meaningful registration date while hiding the first would be incoherent. `roles:test` gained a **`RESTRICTED_DATES`** sweep so the omission is guarded by name rather than incidental.
- **`GET /resident-records/:id` needed no change** — it already selects `'*'` for non-Staff. Note `GET /api/residents/me` also uses `'*'`, so **a resident now sees their own masterlist date automatically**; that is their own data and was allowed to stand, but it is a consequence of `'*'` rather than a decision anyone typed.
- **The review screen gets the date two ways.** Unlinked: hydrated onto the ranked match suggestions with **one extra `.in()` read** (bounded by `DEFAULTS.maxCandidates`, 50) rather than adding a column to `match_resident_candidates` — `CREATE OR REPLACE FUNCTION` **cannot** change a `RETURNS TABLE`, so that would need a `DROP FUNCTION` that removes the duplicate checker mid-migration. Linked: a **nested `profiles → resident_records` embed** on `loadResidentAccount` and `GET /pending-residents`; that branch previously fetched no resident record at all. The embed is the same shape `inactiveMessage` in `auth.js` already runs, so it is proven here rather than assumed.

#### THE SEEDED DATES ARE FABRICATED

**The team could not obtain the real barangay masterlist, so the dates were invented and seeded by us.** They are plausible and spread across three decades, and they are not barangay data. Anything presented from them — a screenshot, a demo, a figure in the manuscript — is illustrating the mechanism, not reporting a fact about Barangay Ubujan.

### Client-side session handling

Two defects were fixed here as a standalone task (no backend change, and none needed — the `exp` claim is already in the token):

- **Expired sessions are dropped when the session is read back**, not when a request fails. `readStored()` in `auth/AuthContext.jsx` runs `isTokenExpired()` and clears localStorage if the token is dead, so `user` is null before anything renders. Previously the stored session was trusted whole, so an expired token produced a **fully logged-in view that only broke on first use** — the dashboard rendered, then its first request 401'd.
- **`auth/session.js` decodes the token; it never verifies it.** This is a **UX guard, not a security control** — no signature check, no secret involved; the server's `jwt.verify` stays the only authority, so faking a later `exp` in localStorage gains nothing. It **fails OPEN**: an unreadable token or one with no `exp` is left alone, so a valid session behaves exactly as it did before the check existed. A 60s leeway absorbs ordinary browser-vs-server clock skew, which must never log out a session the server still accepts.
- **A session is torn down exactly once.** A 401 used to call `logout()` per failing request, and `logout()` changed `authFetch`'s identity — which **every loader effect in the app depends on** (27 of them across 17 modules). One screen can have several requests in flight (the Secretary review screen fetches match suggestions per pending account), so a single expiry became a burst: measured against the unfixed code, **6 concurrent 401s produced 12 teardowns and 12 requests, 6 of them token-less**. Now a `sessionEndedRef` collapses concurrent 401s into one teardown, and `authFetch` reads the token from a **ref so its identity is stable** — no auth change can re-fire a loader. Every caller still gets its 401 thrown, so existing error handling is untouched.
- **`authFetch` pre-flights**: a missing or expired token short-circuits before `fetch`, so requests that cannot succeed never leave the browser. This also catches a session that expires mid-use. There is deliberately **no auto-logout timer** — an idle expired session is caught on the next action or page load, and a timer would interrupt someone mid-form for no gain.
- **`ProtectedRoute.jsx` was deliberately NOT changed.** The check belongs at the session source because `user` is read by two components that would otherwise disagree: `App.jsx` treats a truthy `user` as "already logged in, bounce them off `/login`", while `ProtectedRoute` treats it as "let them in". Teaching only the guard about expiry makes them fight — the guard sends the expired user to `/login`, `App` sees the still-truthy stored `user` and sends them back, **an infinite redirect loop**. Purging in `readStored()` makes `user` null for both readers at once, so they agree by construction and every consumer inherits the fix without knowing it exists.
- **Test: `cd frontend && npm run test:auth`** (no backend required). Both defects live between the stored session and the first request, which no API-level test can see — so it bundles the real `AuthProvider`/`ProtectedRoute`/`App`, mounts them in jsdom against a stubbed `fetch` and `localStorage`, and counts requests fired, tokens attached, and teardowns. Verified to FAIL against the pre-fix code (12 teardowns for 6 failures, `authFetch` identity CHANGED), so it is a real regression guard rather than a test that passes either way.

### Forgot password — DECIDED DESIGN, **NOT BUILT**

**⚠ NOTHING IN THIS SUBSECTION DESCRIBES EXISTING CODE.** There is no `/api/auth/forgot-password`, no `/api/auth/reset-password`, no `password_resets` table, no email adapter and no reset screen. This records decisions taken before the work, so that whoever builds it inherits the reasoning rather than re-deriving it. Every other subsection in this file describes what is; this one describes what was agreed.

- **It IS being built.** **Residents only** — a non-resident role gets no email, silently. **Pending and rejected accounts get no email either.** The response is **identical whether or not the address exists**, so the form cannot be used to discover which addresses have accounts.
- **Real email via Resend, not simulated.** Note the free tier can only send to the Resend account owner's address until a domain is verified, so testing uses a throwaway resident whose email is that address. This is the one place the project sends something for real — everything under Notifications remains `SIMULATED`.
- **THE REDACTION SPLIT IS MANDATORY, and the reason is an account-takeover path, not tidiness.** `notify()` must log a **safe** message while sending the **real** one. `/secretary/notifications` renders `notifications.message` on screen for the Secretary; a reset link stored in that column is therefore **readable by every Secretary, who could use it to take over any resident's account.** Hashing the token in `password_resets` does not help — the raw token would be sitting in `notifications.message` in plain text. The row must record something like "Password reset link sent"; only the provider ever sees the URL.
- **Tokens: `crypto.randomBytes(32).toString('base64url')` (43 chars, 256 bits), stored as a SHA-256 hash.** The **fast hash is deliberate and is the opposite of the password rule**: bcrypt is slow because passwords are low-entropy and brute-forceable, whereas a 256-bit random token is not, so slowness buys nothing and only makes verification expensive. **`household_qr.qr_token` is stored RAW, and that is a different case, not an inconsistency** — it is a long-lived identifier scanned repeatedly that grants no account access, while a reset token IS the account password for its lifetime.
- **SESSION INVALIDATION IS DEFERRED — a known, accepted limit.** Changing `password_hash` **does not end existing sessions**: the JWT carries only `sub` and `role`, and `authenticate` re-reads `user_id, username, email, role, is_active, must_change_password` — never `password_hash`, and there is nothing to compare `iat` against. **A stale token keeps working until `exp`, up to 8 hours.** If the reason for the reset is that someone else is in the account, they stay in. This is **pre-existing**, not introduced by reset — `POST /api/auth/change-password` has always behaved this way. A separate change adding `users.password_changed_at` (with `authenticate` rejecting older `iat`) will follow, and **it must NOT be bundled into the forgot-password work**: it edits the auth middleware every route depends on, and mixing it in would put the riskiest change inside the largest one.

## User Roles (5)

Role strings in code and in the `users.role` column always use the lowercase canonical values below, defined in `docs/brgyserve-use-cases.md`. Always say "Punong Barangay", never "Barangay Captain".

1. **Punong Barangay** (`punong_barangay`) — highest approving authority; approves/signs documents, views reports, and **reads resident records and document requests in full** (see Resident Records Management → read-only access)
2. **Barangay Secretary (System Administrator)** (`secretary`) — manages the system, user accounts, resident records, and document processing

## Research Contribution: Two-Stage Fuzzy Name Matching

The capstone's research component detects **duplicate / near-duplicate resident records** (misspellings, name variations, encoding inconsistencies) using a two-stage pipeline:

1. **Stage 1 — Candidate blocking (database layer):** PostgreSQL `pg_trgm` extension performs trigram similarity blocking to cheaply narrow the full resident table down to candidate pairs. This avoids the O(n²) cost of comparing every record against every other record.
2. **Stage 2 — Fine scoring (application layer):** Jaro-Winkler similarity is computed on each candidate pair in the Node.js backend to produce a final match score. Jaro-Winkler weights agreement in name prefixes, which suits person-name matching.

**Evaluation:** the component is evaluated with **precision, recall, and F1-score** against a labeled set of known duplicate/non-duplicate pairs.

Implementation status:
- Engine implemented in `backend/src/services/nameMatching.js` (`findMatches(first, last, options)`); tunable defaults live in its exported `DEFAULTS` (trigramThreshold 0.3, scoreThreshold 0.85, maxCandidates 50). Do not hardcode thresholds elsewhere — the evaluation sweeps them.
- Stage 1 runs as the `match_resident_candidates` SQL function (migration 003) called via RPC; it uses `set_limit()` + the `%` operator so the GIN indexes are used with a per-call threshold. Jaro-Winkler comes from the `jaro-winkler` npm package and scores the normalized `first last` string (middle names are stored separately and excluded from scoring).
- Test harness: `npm run match:test` (backend); seed test data with planted duplicate pairs in `backend/seeds/test_resident_records.sql` (the six planted pairs are the basis for the future labeled evaluation set).
- Evaluation harness: `npm run match:eval` (backend, `scripts/evaluate-matching.js`) — labeled ground truth manifest mirrors the seed file (6 positive pairs, 624 negative pairs from the 36 seeded records; small initial set to be expanded), runs the real engine, and prints TP/FP/FN/TN + precision/recall/F1 across a Stage 2 threshold sweep. On the current labeled set: perfect separation up to threshold 0.85 (P=R=F1=1.0), recall drops above it. Keep the manifest in sync with the seed file.

## Conventions

- Backend uses CommonJS (`require`), frontend uses ES modules (Vite default)
- API routes are prefixed with `/api/`
- Commit messages must never include AI attribution lines ("Co-authored-by: Claude", "Generated with Claude Code", or similar)
- Database schema lives in `docs/brgyserve-database-schema.md` (source of truth) and is applied via numbered SQL files in `backend/migrations/`, run manually in the Supabase SQL Editor. Keep the doc and migrations in sync.
- **A review block's final `SELECT` must carry an EXPLICIT column alias list on the derived table** — `) AS x (ord, section, detail)` — never rely on the branches' own `AS` aliases. In a `UNION`, column names come from the **first branch only**, so one branch missing an alias makes the column unnamed and the outer `SELECT` fails with `42703: column "detail" does not exist`. That happened once (the migration-018 seeding block), and because it fails at the outer select the whole transaction aborts and nothing is written — a safe failure, but a wasted round trip on a block that is otherwise ready to run. The explicit list names every column regardless of what any branch does.
- Implemented so far: the base schema + auth slice (migrations 001–004; 005–011 were added incrementally and are documented in their module sections), resident registration with Secretary-approved linking/activation, the frontend auth slice (login/registration pages, auth context with localStorage persistence, role-based routing), the Secretary review screen on `/secretary` (pending list with ranked fuzzy-match suggestions via `GET /api/secretary/pending-residents/:userId/match-suggestions`, link/create-and-link, activate), and document-type management on `/secretary/document-types` (`/api/document-types`: active list for any authenticated user; `/all` + create/update/deactivate/reactivate Secretary-only — types are deactivated, never deleted, to preserve future request history; migration 004 added `is_active`), the resident document-request screens and the full Document Requests pipeline (see Document Requests section, incl. the Treasurer's Payments landing page), and the complete Facility Rentals module on `/secretary/rental-items` + the shared rental-bookings views (stages 1–5: rental-item management, self-service booking with conflict check, Secretary schedule management, payment through the charges system, and Staff return tracking — see that section; migrations 009–011). All five roles now have real landing pages (Staff: rental bookings with the return action; the Punong Barangay: the read-only rental-bookings list). Blotter/dispute records on `/secretary/blotter` (manage) + `/punong-barangay/blotter` (view-only) — see that section; optional migration 012. **Resident records and document requests are now read by three roles** — `/staff/residents`, `/punong-barangay/residents`, `/staff/requests`, `/punong-barangay/requests`, all view-only, with Staff on a narrowed projection (`177dabd`, `eba84ae`; see Resident Records Management → read-only access). ## Standing Rules

How work is done in this repository, as distinct from how code is written (see Conventions).

- **Never start the backend or frontend dev server.** The developer starts them. The `npm run dev` lines under Commands and Repository Structure record *how* they are started, not permission to start them — assume a server on :5000 or :5173 is one somebody else is using. Verification that needs a browser uses a `file://` harness loading the real `index.css`, driven by headless Chrome over CDP, which starts no server at all.
- **Never use `git add .` — stage explicitly by path**, every time. That is what keeps `frontend/.env`, `dist/` and the ignored bundles in `frontend/scripts/` out of a commit by construction rather than by luck.
- **Build prompts and commit prompts are separate.** A build ends with the edit made and verified, the working tree dirty and **nothing staged**; the commit follows in its own prompt. Committing inside a build prompt removes the review step the separation exists for.
- **Diagnose before any structural change.** Measure, report what was found, propose candidates, let the developer choose. This has caught real errors more than once — including a proposed diff that would not have compiled, and a test harness that "passed" against code already known to be broken. A harness that does not reproduce the bug proves nothing when it passes: **always run it against the pre-fix code first.**
- **Commit messages:** subject line plus three or four bullets, plain language, **no attribution trailers** (see also Conventions).
- **A JSX comment cannot go inside an implicit-return arrow function.** In `{columns.map((c) => (` … `))}` the callback returns a single expression, so a `{/* … */}` placed beside the element makes two sibling expressions with no wrapper and **the Vite build fails**. Put the comment on the line above the `.map(` call instead. **The same applies to a parenthesised ternary branch** — `cond ? (<A/>) : ({/* … */}<B/>)` fails identically; this cost a build in `eba84ae`.
- **A WITHHELD FIELD MUST BE ABSENT FROM THE PAYLOAD — never `null`, never `[]`.** This caused two bugs in one day, both shipping a false statement to the screen. `account: null` on the resident list made every row render an em dash, so the Account column asserted **no resident has registered online**. `linked_accounts: []` on the detail said the same thing in prose: *"Not linked to any account — this resident has not registered online"* — on record #9, which has one. Both were reported as "keeping the response shape stable across roles", and that is exactly the trap: **a shape that stays constant by asserting something false is worse than a shape that varies honestly.** `null` and `[]` are positive claims ("we looked, there is none") and a client cannot tell them apart from a genuine empty result. Absence is the only representation of *withheld* that a client can detect. The frontend tests presence with **`key in object`** and **never checks the viewer's role** — the server has already decided, and a role check in the component would be a second opinion free to disagree with it.
- **THE COMMITTED DEV API FALLBACK IS `http://localhost:5000/api`, AND IT IS DELIBERATE. Do not change it. It has regressed FOUR times.** The value in `frontend/src/api/config.js` is one side of a two-sided pair: the backend listens on 5000 (`server.js`), and `vite.config.js`'s own error text names 5000. Changing only the frontend side points the dev app at a port nothing is listening on, which presents as "Cannot reach the server" and looks like a backend problem. **If port 5000 is taken on your machine, the fix is `backend/.env` `PORT` plus `frontend/.env` `VITE_API_URL` — both gitignored, both local to you — never the committed fallback.** It is dev-only either way: `vite.config.js` throws without `VITE_API_URL`, so no deployed bundle has ever carried it. `44ed8e4` changed it to 3000 and `22d7f35` reverted it; that is the pattern to stop repeating.
- **Beware a test that pins a bug in place.** The assertion `check('response SHAPE is stable (linked_accounts present for both)', …)` did not merely tolerate the bug above — it would have **failed anyone who fixed it**, under a name asserting the arrangement was correct. It was deleted along with the behaviour. When a test's name states a design claim, the claim is what needs reviewing, not just the assertion.

## Frontend Layout

**No CSS variables exist in this codebase and none are to be introduced.** Values are literal. This is a live constraint rather than a style preference — the `capped-column` coupling below would be a one-line binding if variables were available, and instead has to be held by a comment.

**Spacing or layout wanted by ONE screen goes on a scoped selector, never on a shared utility class.** The worked example is `.muted`: it carries no margin (`index.css:318`), and the dashboard header's subtitle gap lives on `.dash-header .muted` (`index.css:248`) instead. `.muted` is on **163 elements across 24 files** — helper text, empty states, table captions, loading lines — so a margin added to the utility itself lands on all of them at once. That is exactly what happened in `07cc26d`, which set `margin: 5px 0 0 0` on `.muted` to space one header subtitle; `e83e56c` reverted it and scoped it. Specificity does the work — `.dash-header .muted` is (0,2,0) against (0,1,0), so it wins regardless of source order and the scoped rule can sit with the other `.dash-header` rules rather than being wedged in beside `.muted`.

### The auth pages are scoped under `.auth-page`, and that changed the specificity order

The login/registration redesign (PR #4, merged as `9adea3c`) originally restyled the **shared** `.card`, `.card h1`, `label`, `input` and `button` rules to suit two screens. That is the `.muted` mistake at a much larger blast radius — those selectors are on every screen in the app — so the shared rules were restored to their previous values and `.auth-page`-scoped equivalents added instead (`9e2efc4`).

**The consequence to know before touching either file:** `.auth-page button` is **(0,1,1)**, which now **outranks `.btn` (0,1,0)**. Any `.btn` inside an auth page loses to the scoped rule regardless of source order. The password toggle survives this only because **`.pw-field .pw-toggle` is (0,2,0)** and beats both. A new control added to `/login` or `/register` needs at least (0,2,0) to hold its own styling, and a single class will not do it.

**`.auth-page button` appears TWICE in `index.css`, 178 lines apart** — `index.css:88` (`padding: 15px`) and `index.css:266` (`width: 100%; margin-top: 6px`). The two set **disjoint** properties, so there is no conflict today and no bug. It is recorded because a reader who finds one will reasonably assume it is the only one and edit the wrong occurrence. A grep for `.auth-page button` returns a **third** hit, `.auth-page button.link-button` (`index.css:569`) — a different, more specific selector (0,2,1), not one of the pair.

### The dashboard header is STICKY (`a62f8d7`)

`.dash-header` carries **`position: sticky; top: 0; z-index: 30`**. It was static from the beginning and nothing had ever revisited it — not a regression, a choice nobody had costed.

**Why:** it follows directly from the section above. With the drawer as the ONLY navigation, scrolling to the bottom of a long list (the payments queue, the attendance roster, the resident list) put the **hamburger off-screen**, and the only way back to navigation was scrolling all the way up. While a tab row existed that cost nothing; once it was deleted, it did.

**`z-index: 30` IS LOAD-BEARING — it is a value in a ladder, not a free number.** The whole ladder:

| element | z-index | |
|---|---|---|
| `.dash-header` | **30** | scrolls beneath nothing; covers `.dash-main` |
| `.dash-backdrop` | 40 | must cover the header while the drawer is open |
| `.dash-drawer` | 50 | covers the backdrop |
| `.modal-backdrop` (Households create) | 50 | |

30 must stay **below 40**, or the header sits on top of the dimming backdrop and its Log out button stays clickable behind an open drawer; and **above 0**, or `.dash-main` content scrolls over the header instead of under it. Two consequences for anything added later: **a new floating element must sit at 40 or above to clear the header**, and **anything given 40+ that is not meant to cover the header will cover it anyway** — that is now a decision every fixed element makes, whether or not its author realises it.

**The cost is vertical space, permanently: 89.6px at 640px and up, 109.6px at 480px and below** (the subtitle wraps to a second line there). That is 10% of a 900px viewport, 12.2% on a phone. Padding was deliberately **not** shrunk to claw any of it back — that is a separate judgement about density, and `.dash-header` padding has already been through one revert cycle (`2c6d7c1` / `07cc26d`).

**Measured against `main` at 1280 and 1920 before shipping — two stylesheets on disk, not a runtime injection — and every value matched exactly: all six protected desktop rules, the 1132px content box, table widths, and `.table-wrap` overflow.** That result is not luck and generalises: `position: sticky` keeps the element **in flow** and does not change its width, and `.dash-header` is a **sibling** of `.dash-main` rather than an ancestor, so it cannot enter the width cascade the payments column budget depends on. The 45.5px of slack in that budget is untouched.

**Nothing needed a `scroll-margin-top`.** No `.jsx` in the app calls `scrollIntoView` or `window.scrollTo`, and the dashboard has no in-page anchors — so there is nothing that could land under the pinned header. (The two `scroll-margin-top` values in `index.css` — 72px on `.landing-hero`, 68px on `.landing-section` — belong to `.landing-nav`, a **different** sticky element on the landing page, which has real anchor links. They are unrelated to `.dash-header` and were never measuring it.)

## Document Requests

- Agreed workflow: resident submits → Secretary approves/rejects → payment (record/verify) → release. The Punong Barangay only views/signs.
- Status lifecycle — canonical lowercase values defined in `backend/src/constants/requestStatus.js` (single source of truth; later stages must not invent new strings): `pending` (resident submitted) → `approved` / `rejected` (Secretary review) → `ready_for_release` (payment verified + signed) → `claimed` (released, `claimed_at` set). `cancelled` = withdrawn by the resident.
- Implemented: Stage 1 document-type management; Stage 2 resident submit (`POST /api/document-requests`, requires a linked resident record) and tracking (`GET /api/document-requests/mine[/:id]` — filtered by `requested_by_user_id`, so users only ever see their own). Resident screens: `/resident` (My Requests) and `/resident/request`. Migration 005 added `requested_at`.
- Stage 3 Secretary processing: `GET /api/document-requests[?status=…]` (list across residents) and `GET /:id` (detail incl. the resident record for verification) — **these two GETs now also admit `punong_barangay` and `staff`** (`177dabd`); `POST /:id/approve|reject` stays **Secretary-only**; only `pending` may be decided, reject requires a reason (migration 006 added `rejection_reason` + `processed_at`). Screens: `/secretary/requests` (manage), `/staff/requests` and `/punong-barangay/requests` (view-only). A **Staff** caller receives a narrowed resident embed and no requester email — see **Resident Records Management → read-only access for Staff and the Punong Barangay**, which is the one place that decision is written down. Rejection reason is shown to the resident in My Requests.
- Resident cancel: `POST /api/document-requests/mine/:id/cancel` — own requests only (404 otherwise), only from `pending` (409 otherwise) → status `cancelled`. Cancel button on pending rows in My Requests. No edit — residents cancel and resubmit.

### Stage 4 (Payment + Release)

- A `charges` row is created when the Secretary **approves** a document request (`charge_type = 'DOCUMENT'`, `amount` = the document type's fee only for now; the charges table's structure already supports adding fines later).
- Residents pay at the barangay hall (cash) or via GCash by providing a reference number. Payments are **recorded/verified manually** in `payments` (`payment_method`, `reference_no`) — no payment gateway integration.
- Both the **Treasurer and the Secretary** can record/verify payments and mark a charge paid (`charges.status = 'PAID'`).
- The **Secretary** moves the request `approved → ready_for_release` (payment verified) and `ready_for_release → claimed` (sets `claimed_at`), per the shared status vocabulary.
- The SMS notification stub (`logSmsNotification`) fires on `ready_for_release`, same pattern as approve/reject.
- Build order: **4a** charge creation on approval → **4b** payment record/verify + Treasurer dashboard → **4c** release flow (ready_for_release + claimed).
- **4a implemented:** approval inserts the charge (`constants/charges.js` — charge statuses are UPPERCASE per Table 15, unlike lowercase request statuses); zero-fee documents get an amount-0 charge auto-marked `PAID` (nothing to collect; must not wait on the Treasurer). No transaction support in supabase-js, so a failed charge insert reverts the approval; migration 007 adds UNIQUE on `charges.document_request_id` (one charge per request, NULLs exempt) and backfills charges for requests approved before 4a. Charges are embedded in `/mine` and Secretary list/detail responses — no separate charge endpoints.
- **4b implemented:** payment declaration vs verification are modeled separately. The resident declares via `POST /api/document-requests/mine/:id/pay` (`method: onsite|gcash`, GCash requires `reference_no`) — stored as `declared_*` on the charge (migration 008), charge stays UNPAID, re-declarable while unpaid. Verification (`/api/charges`: `GET ?status=` queue + `POST /:id/verify`, roles `treasurer` + `secretary`) creates the `payments` row (verifier in `received_by_user_id`; method/reference default from the declaration, overridable) and flips the charge to PAID with a status-guarded claim → insert → revert-on-failure sequence. The payments table only ever holds verified payments. UI: Pay onsite / Pay via GCash on approved unpaid rows in My Requests; `PaymentsPage` (verification queue) is the Treasurer's landing page and the Secretary's Payments tab. SMS stub fires on verification.
- **4c implemented (module complete):** release flow. `POST /api/document-requests/:id/ready-for-release` (Secretary-only; only from `approved` and only when the charge is `PAID` — zero-fee auto-PAID charges qualify immediately) and `POST /:id/claim` (Secretary-only; only from `ready_for_release`, sets `claimed_at`). ## Facility Rentals

### Design & implementation

- **Workflow (self-service, instant confirmation):** rentals are SELF-SERVICE — the resident submits a booking and the system runs the conflict check at submission; if the slot/units are free, the booking is CONFIRMED instantly, otherwise it is refused with a clear reason. There is NO Secretary approve/reject step for rentals (this supersedes the earlier "Secretary approves rentals" plan). The Secretary manages bookings (view/edit/cancel). Barangay Staff are view-only except their single write action, marking returns (stage 5); the Punong Barangay is view-only.
- **Fees** go through the existing charges/payments system (`charges.rental_request_id` already exists; Treasurer and Secretary can both verify, Treasurer primary).
- **Availability:** a simple conflict check — prevent overlapping bookings for the same item/time slot, and for countable items verify enough units are free in that slot. No visual calendar (future enhancement).
- **Scheduling model:** rentals use a date plus start/end time. Countable items (chairs, tables) have a quantity; whole facilities (court, hall) are single-unit (`quantity_total = 1`).
- **Build order (all implemented):** (1) rental items setup → (2) resident submission + tracking with the conflict check (instant confirmation) → (3) Secretary schedule management (view/edit/cancel) → (4) payment → (5) return tracking.
- **Stage 1 implemented** (rental-items management, `/api/rental-items` + `/secretary/rental-items`, mirrors document types): active list for any authenticated user; `/all` + create/update/deactivate/reactivate Secretary-only. Soft delete only — future `rental_requests` rows will FK to items, so history must survive. Migration 009 added `fee numeric(10,2)` (per **unit** per booking — facilities are 1 unit, so it reads as per-booking; stage 4 computes `fee × quantity_requested`). Item `type` is canonical lowercase `facility | equipment | furniture`; `facility` enforces `quantity_total = 1` in validation. `quantity_available` currently mirrors `quantity_total` on create/update (a scalar can't express per-time-slot availability; stage 2 derives free units per slot from bookings against `quantity_available`, which later allows damaged/retired stock to lower it below total). Starter items seed: `backend/seeds/sample_rental_items.sql`.
- **Stage 2 implemented** (resident booking + tracking, no migration — `rental_requests` exists since 001): rental statuses in `constants/rentals.js` — initially `confirmed | cancelled | completed` (no pending/approved: bookings confirm instantly; `cancelled` frees the slot; the vocabulary was later extended and `completed` made derived-only — see stage 5). `POST /api/rental-requests` (requires a linked resident record, same rule as document submit; `processed_by_user_id` stays null — nobody approves) and `GET /mine` (own bookings only, `request_id` desc — the table has no created-at column). API takes `date + start_time + end_time`, composed server-side with an explicit `+08:00` offset (same-day bookings by construction); validates end > start, start in the future, purpose ≤1000, quantity ≥1, facility ⇒ quantity 1, quantity ≤ `quantity_available`. **Conflict check:** overlap = `existing.start < new.end AND existing.end > new.start` (strict — slots touching at an endpoint don't conflict) over non-cancelled bookings of the item; refuse when `used + requested > quantity_available` (facilities are the same math with capacity 1). Refusals name the conflicting slot (facility) or the free unit count (countable). **Concurrency (no transactions in supabase-js):** optimistic insert, then re-check counting only overlapping rows with a LOWER `request_id`; earliest insert always survives, a loser deletes its own row and gets the 409 — never double-books. SMS stub fires on confirmation. Screens: `/resident/book-rental` (item picker with fee/units, date+time+quantity, estimated fee = fee × qty, conflict errors shown inline) and `/resident/rentals` (My rentals list); both in the resident nav.
- **Stage 3 implemented** (Secretary schedule management, no migration): `GET /api/rental-requests[?status=…]` (all bookings, requester name via `users→profiles` embed, ordered `start_datetime` desc) and `GET /:id` are open to `secretary`, `staff`, and `punong_barangay` (view roles); `PUT /:id` (edit date/times/quantity/purpose — the item is fixed) and `POST /:id/cancel` are Secretary-only, enforced server-side. Edits re-run the SAME stage 2 conflict check (shared `findConflict()` helper — one implementation) with `excludeId` so a booking never collides with its own current slot; a post-update re-check reverts to the previous schedule on a race. Only `confirmed` bookings can be edited/cancelled (409 otherwise); cancelling sets `processed_by_user_id` and frees the slot automatically because the conflict check filters out cancelled rows. SMS stub fires on Secretary cancel (the resident is told their booking was cancelled). UI: shared `RentalBookingsPage` (filter, list, edit panel, confirm-guarded cancel) — Secretary's Rentals tab (`/secretary/rentals`, `canManage`), and the same page read-only as the Staff and Punong Barangay landing pages (their first real screens; Staff's later gained the return action — see stage 5).
- **Stage 4 implemented** (rental payment through the EXISTING charges/payments system — no parallel plumbing): booking confirmation inserts a `RENTAL` charge (`amount = fee × quantity_requested`, the same `rentalAmount()` formula the booking screen shows as estimated fee; zero-fee ⇒ amount-0 charge auto-`PAID`, matching documents; `user_id` = requester, linked via `rental_request_id`; insert-fail ⇒ booking deleted, mirror of the document compensation). Migration 010 adds UNIQUE on `charges.rental_request_id` + backfills charges for bookings confirmed pre-stage-4. Charge lifecycle on management actions: Secretary **edit** that changes quantity recomputes an UNPAID charge's amount (PAID stays — money received is a record; differences settle offline); Secretary **cancel** VOIDs an UNPAID charge (record kept, drops off the queue) and leaves PAID alone (refunds are offline). Resident declares payment via `POST /api/rental-requests/mine/:id/pay` (identical semantics to the document declare route). The shared `/api/charges` queue/verify now embeds `rental_requests→rental_items` + the payer's profile name, the verify SMS wording adapts per type, and `PaymentsPage` gained Type + For columns and a Void filter. My Rentals shows amount due/status with the same Pay onsite / Pay via GCash flow as My Requests.
- **Stage 5 implemented (module complete): return tracking.** Migration 011 adds `return_note`, `returned_at`, `returned_by_user_id` to `rental_requests`. Status vocabulary extended (`constants/rentals.js`): STORED = `confirmed | cancelled | returned | returned_late | returned_with_issue`; `completed` (facilities) and `overdue` (physical items) are DERIVED at display from a confirmed booking whose end has passed — never stored (`deriveStatus()` puts `derived_status` on every management/mine response; the time logic lives in one place, GETs stay read-only, and no scheduler is needed). Returnability is by item type: `equipment`/`furniture` returnable, `facility` not. `POST /api/rental-requests/:id/return` is **Staff-only** (their one rental write action; edit/cancel stay Secretary-only) — records outcome + optional note + who/when, only for a confirmed physical item (facilities and non-confirmed bookings are refused with a clear message), status-guarded, SMS stub fires. The management list gained virtual `?status=overdue|completed` filters (derived from confirmed + past-end). UI: Staff landing (`RentalBookingsPage` with `canReturn`) defaults to the Overdue filter and shows a "Mark returned" action (outcome + note panel) on confirmed physical items only; return outcome/note surface on the Secretary and Staff lists and on the resident's My Rentals (which now shows Pay while the charge is UNPAID regardless of return state). Note: this expanded rental scope beyond booking+payment — the team is to reflect it in Chapters 1–3 of the manuscript.

## Resident Records Management

### Planned design

- A module to view, search, add, edit, and archive resident records — the master list in `resident_records` (~5,564 residents in Barangay Ubujan, so lists must paginate). **Originally Secretary-facing end to end; since `177dabd` the two GETs are also read by the Punong Barangay and Staff** — every write remains Secretary-only (see the read-only access subsection below).
- **Duplicate check on add (Stage 2):** the fuzzy-matching duplicate check will ALSO run when the Secretary ADDS a new resident record, not just at resident self-registration — reusing the existing `findMatches` two-stage engine. This strengthens the research contribution: duplicate detection guards both entry points into the master list.
- **Archive/soft-delete only** — records are never hard-deleted, consistent with document types and rental items (`is_archived` has existed since migration 001). Archiving must account for linked `profiles` (accounts) and existing document requests / rental bookings — handled carefully in Stage 3.
- **Build order:** (1) view + search list → (2) add (with duplicate check) + edit → (3) archive with dependency handling.
- **Stage 1 implemented** (view + search, no migration — read-only over existing columns): `/api/resident-records` was Secretary-only end to end at this stage (`GET /?search=&page=&per_page=` and `GET /:id`; Staff/PB/residents got 403 — residents keep `GET /api/residents/me`). **The two GETs were widened to the Punong Barangay and Staff in `177dabd`** — see the read-only access subsection below; residents are still refused. Pagination: default 25/page (max 100), `count: 'exact'` + `range()`, non-archived records only, ordered by surname; an out-of-range page returns an empty page (PGRST103), not an error. Search: input is split into words, each sanitized (PostgREST `.or()` syntax chars and LIKE wildcards stripped) and AND-ed as one `.or(ilike first/middle/last/address)` group per word — so "juan dela" finds Juan Dela Cruz and "purok 2" works as an address filter. Each list row and the detail carry the linked account via `profiles.resident_id` (that column is UNIQUE per migration 002, so at most one account per record; the code still handles it as a list so the stage 3 cascade stays correct regardless). UI: `/secretary/residents` ("Resident records" tab) — search box, paginated table (name, birthdate, address, contact, @username badge when registered), read-only detail panel with all record fields + linked-account section.
- **Stage 2 implemented** (add with duplicate check + edit, no migration): the duplicate check REUSES `findMatches` exactly as self-registration does — same call signature, no options passed so `DEFAULTS` apply (thresholds are never hardcoded here; `match:eval` sweeps them) — so duplicate detection now guards BOTH entry points into the master list. `POST /check-duplicates` returns ranked candidates (name, birthdate, address, score) and creates nothing. `POST /` validates, then **re-runs the check server-side** so the server is the final authority: matches + no `confirm_duplicate: true` ⇒ **409 with the ranked matches** and no insert; with the flag ⇒ insert (`date_registered` server-set, `is_archived` false) and the overridden matches come back in the 201. The check is deliberately SOFT — same-name-different-person is real, so it informs and requires confirmation, never hard-blocks. `PUT /:id` validates identically but runs NO duplicate check (correcting an existing person isn't creating an identity, and it would flag the record against itself); archived records 404. Validation mirrors document types/rental items (`validateBody` → `{ error }` or `{ value }`): `first_name`/`last_name`/`address` required (address is NOT NULL in the DB), per-column max lengths from Table 4, `birthdate` must be YYYY-MM-DD and not in the future; `resident_id`/`date_registered`/`is_archived` are never client-writable. UI: "Add resident" button → full form with an explicit "Check for duplicates" step (ranked matches reuse the `.suggestions` markup from the Secretary review screen) plus the authoritative 409 path, which swaps the save button to "This is a new person — add anyway"; after adding, the list re-searches on the new surname so the record is visible. **Edit is reachable only from the detail panel**, never a list row — the list projection omits several columns, so prefilling from a row would blank them on save. `ApiError` now carries the parsed error body (`data`) so the 409's matches reach the UI.
- **Stage 3 implemented (module complete): archive + unarchive with the account cascade.** No migration — `is_archived` (Table 4) and `users.is_active` already exist. **Dependencies on `resident_records.resident_id`:** `profiles.resident_id` (UNIQUE ⇒ ≤1 account), `document_requests.resident_id` (NOT NULL — real data), plus `household_members`, `dispute_parties`, `resident_duplicate_candidates` (schema-only; those modules aren't built — and `event_attendees` dropped its `resident_id` in migration 015, so it is no longer a dependency at all). `rental_requests` has NO `resident_id` — bookings belong to the USER, so they're reached through the linked account. Hard delete is therefore impossible without breaking `document_requests`; archiving is soft only and archived records stay readable via `GET /:id`. **Policy:** archiving CASCADES — `POST /:id/archive` sets `is_archived = true` AND deactivates the linked account(s) (`users.is_active = false`) so no "archived but still logging in" state can exist; `POST /:id/unarchive` is symmetric (restores + reactivates). Both are status-guarded with revert-on-failure compensation (no transactions in supabase-js) so record and account state can't drift. **Dependency gate:** before archiving, open document requests (`pending|approved|ready_for_release`) and active rentals (confirmed and either upcoming or a physical item past its end that was never returned — a facility past its end has auto-completed) are collected along with the linked account; if anything is found and `confirm_archive: true` is absent, it returns **409 with a plain-language summary + the itemized dependencies** ("2 open document requests, 1 active rental booking. This will also deactivate account @juan (they can no longer log in)."). The account-deactivation line always appears when an account exists — the cascade is never silent. **Known limitation (accepted):** unarchive reactivates linked accounts unconditionally, so an account deactivated for cause *before* the archive would come back active; distinguishing that needs extra state (a flag recording who was deactivated by the archive), so the simple symmetric behavior stands. UI: Archive/Unarchive live in the detail panel next to Edit (never a list row), the 409 renders the itemized dependencies with a blunt deactivation warning and an "Archive and deactivate account" confirm (mirroring the stage 2 duplicate flow), archived records show a badge + explanatory banner, and the list gained an Active/Archived/All filter (`?archived=false|true|all`).

Both now have **READ-ONLY** access to both modules. **No writes, ever, for either role** — all five resident-record writes and all four document-request transitions stay `requireRole('secretary')`, enforced server-side and verified over HTTP with 403 on all eight probes.

Neither array's first item changed, because the landing route depends on it.

#### DATA MINIMIZATION — Staff receive a narrowed resident record

**This is a deliberate design decision, not an implementation detail, and it is the kind of thing a defense panel asks about.**

- **Staff may see:** `resident_id`, `first_name`, `middle_name`, `last_name`, `suffix`, `birthdate`, `address`, `is_archived` — identity and nothing more.
- **Withheld from Staff:** `birthplace`, `sex`, `civil_status`, `religion`, `educational_attainment`, `contact_number`, `date_registered`, the linked user account, and **the requester's email on BOTH document-request endpoints** (list and detail).
- **The Punong Barangay receives the full record**, exactly as the Secretary does.

**The reason** is the **Data Privacy Act commitment made in Chapter 1** together with the **stated purpose of Staff access in Chapter 3** — confirming that a resident is registered. That task needs *identity*; it does not need to know anyone's religion, civil status or phone number. Collecting a justification for each field and withholding the rest is what data minimization means in practice, and it is defensible precisely because the purpose is written down.

**The narrowing is on the SERVER.** Hiding these columns in the frontend would still ship them to the browser, where anyone can read them out of the network tab — that is not withholding, it is concealment. The projection is chosen in `routes/residentRecords.js` (`STAFF_FIELDS`) and `routes/documentRequests.js` (`STAFF_LIST_FIELDS`, `STAFF_DETAIL_FIELDS`), and the linked-account lookups are **skipped entirely for Staff rather than filtered**, so the withheld data is never even read.

**These are the first role-varying response bodies in the codebase.** Every other role check is all-or-nothing: `requireRole()` admits you to a handler or 403s you, and until now no route read `req.user.role` to shape what it returned.

**GCash `declared_method` and `declared_reference` are deliberately NOT withheld.** A payment reference belongs to the **transaction**, not to the person — it identifies a payment, not a resident's private circumstances — and it is needed to make sense of a request's payment state. Recorded here so the omission reads as a decision rather than an oversight.

**The requester's `username` IS kept** on document requests. A request is defined by who filed it, and a username identifies the filer without being a way to contact them; `email` is the contact detail, and it is the part that goes.

#### `residentRecords.js` NO LONGER FAILS CLOSED

It moved from a router-level `router.use(authenticate, requireRole('secretary'))` to `router.use(authenticate)` plus a per-route guard — the same migration Households made at its stage 2. **The cost is real: a route added to that file without an explicit `requireRole(...)` is readable by ANY authenticated user, residents included, and nothing about the code would look wrong.**

**`cd backend && npm run roles:test` is the protection** — 87 assertions, no server started. It probes **every** route in `residentRecords.js` and `documentRequests.js` with all five roles through the real middleware chain and compares the permitted set against a declared table; **a route with no entry in that table FAILS as undeclared** rather than passing silently. It also invokes the real GET handlers as Staff and as the PB and diffs the returned keys, including whole-payload sweeps that catch a contact detail arriving through an embed no assertion names. Verified non-vacuous: an unguarded route reports all five roles and can never match a viewers-or-Secretary expectation.

## Households

The prerequisite for Events stage 3 (household attendance + fines): `household_records`, `household_qr` and `household_members` existed structurally since migration 001 but were empty with no module managing them.

- **NO MIGRATION.** The live schema was introspected before any code (via PostgREST's OpenAPI document, which reports real columns) and **matches Chapter 3 exactly** — no extra columns, no missing ones, all three tables empty. Everything stage 1 needs already exists, so nothing was altered.
- **A household is identified by its HEAD, not its address.** There is no head column: the head is *derived* as the member whose `role = 'Head'` and whose `date_ended IS NULL`. Two households may legitimately share an address, so there is no uniqueness constraint on address — a duplicate address returns a **non-blocking notice** in the create response, never an error.
- **Roles** live in `constants/households.js` (`Head | Spouse | Child | Relative | Other`; `Other` added so boarders/wards aren't forced into a wrong role). `ROLE_ORDER` drives the members-list ordering. **Stage 1 only ever writes `Head`.**
- **Stage 1 implemented (Secretary-only** — Staff, PB, Treasurer and residents all get 403; widening access is a later stage): `GET /api/households` (paginated + searchable), `GET /api/households/:id` (household + members, head first), `POST /api/households` (create + install head).
- **The list mirrors the resident master list exactly** — same 25/page (max 100), same multi-word case-insensitive AND-ed search, same `{ rows, total, page, per_page, total_pages }` shape, same PGRST103 empty-page handling. Those rules now live in `utils/listQuery.js` and `residentRecords.js` was refactored to import them, so there is **one implementation** rather than a copy. Search matches address, household number, and any current member's name (which covers the head, since the head is a member) — the member hop resolves `resident_records` → `household_members` → household ids, the same two-hop the blotter's party search uses. Ordered by household number ascending, because the head's name lives behind a join and can't be sorted on in the query.
- **Create validation:** head must exist and must NOT be archived; a resident may hold only ONE active membership, so a head already in a household is refused with **409 carrying that household's id and head name** so the Secretary can go straight to it; address is required, trimmed, ≤255.
- **Atomicity:** supabase-js still has no transactions, so create uses the established compensation pattern — insert `household_records` → `household_members` (role `Head`, `date_started` = today in Manila, `date_ended` null) → `household_qr` (`crypto.randomUUID()` token, active), unwinding anything already written if a later step fails. A household must never exist without its head, nor a head without a QR row. No column in these tables has a DEFAULT, so every NOT NULL value is set explicitly.
- **`activity_logs` is deliberately NOT written** — no existing module writes it, so this one doesn't invent the pattern.
- **UI:** `/secretary/households` ("Households" tab, next to Resident records) — paginated table (Household #, Head, Address, Members, Registered, Status) with row-click into an in-page detail view (household header, address/registered/status, then a members table with Name/Role/Sex/Age/Date started, plus a warning banner if the head's resident record is archived). Create is a **modal** (the app's only one; every other form is inline) with a resident picker for the head that auto-fills the address from that resident, editable; the duplicate-address notice is shown inline after a successful create. The debounced resident picker was extracted to `components/ResidentPicker.jsx` and the blotter now imports it, so both screens share one search.
### Stage 2 implemented — member management, headship, edit/deactivate, Staff read access

**NO MIGRATION.** Stage 2 uses only the columns Chapter 3 already documents; nothing was altered.

**Endpoints added** (`routes/households.js`): `POST /:id/members`, `PATCH /:id/members/:membershipId` (role), `DELETE /:id/members/:membershipId` (ends it), `POST /:id/head` (reassign), `PATCH /:id` (address and/or `is_active`), `GET /unassigned-residents`.

**Access changed from router-level to per-route guards.** Stage 1 had `router.use(requireRole('secretary'))`; stage 2 replaces that with `router.use(authenticate)` plus `requireRole(...VIEW_ROLES)` on every GET (`secretary` + `staff`) and `requireRole('secretary')` on every write. The Punong Barangay, Treasurer and residents still get 403 on everything. `GET /unassigned-residents` is declared **before** `GET /:id`, or the param route would swallow it — the same layering the events viewer uses.

**Policies (all enforced server-side):**
- A resident holds **at most one active membership** (`date_ended IS NULL`) at a time.
- Leaving a household **sets `date_ended` to today (Manila); a membership row is NEVER deleted** — the history is the audit trail.
- The **head's membership cannot be ended or role-edited directly** (409 telling the Secretary to reassign the head or deactivate the household). Headship changes only via `POST /:id/head`, so a role edit can never mint a second head — `Head` is rejected by the shared `assignableRole()` used by both member endpoints.
- A household has **at most one active head**.
- **Deactivating ends ALL active memberships** in one bulk statement (so they all end or none do) and returns `memberships_ended`; the freed residents can then join other households. Adding to an inactive household is refused.
- **Reactivating does NOT restore memberships** — members must be re-added. **This is deliberately asymmetric with the resident archive/unarchive cascade**, which *does* reactivate the linked account: a dissolved household's members have usually moved on, and blind restoration could double-assign someone who has since joined another household, violating the one-active-membership rule. Restoring an account can't collide with anything; restoring a membership can.
- **Archived residents cannot be added** as members or promoted to head.
- **Transfers** (`transfer: true`) end the old membership and start a new one today, using the established compensate-on-failure pattern: if the insert fails the old membership is un-ended, so a resident is never left belonging to nothing. Without the flag a placed resident returns **409 carrying `{ household_id, head_name, head_is_self }`** — the same shape and self-reference rule as the stage 1 create conflict, so the UI handles both with one code path.
- **Head reassignment demotes the sitting head first, then promotes** — chosen so a mid-failure leaves the household briefly with NO head (which the detail screen already flags) rather than TWO, where "the head" would be ambiguous; the demotion is restored if the promotion fails. `demote_current_head_to` is required only when a head exists.
- **`GET /unassigned-residents`** computes active residents minus placed residents **in Node rather than with a `NOT IN` filter** — the placed set can run to thousands of ids, which would not survive being serialised into a PostgREST query string. Both halves select only `resident_id`, so the payload stays small and the count/paging stay exact.

**UI:** `HouseholdsPage` now takes `{ title, nav, canManage }` like `RentalBookingsPage`/`DisputesPage` — Secretary at `/secretary/households` (`canManage`), Staff at `/staff/households` **read-only, with every write control absent rather than disabled**. The detail view gained add-member (resident picker + role, with a transfer confirmation step when the 409 fires), per-row role change, end-membership, and "Make head" (which prompts for the sitting head's new role); ended memberships are listed de-emphasised with their end date behind a show/hide toggle. The header gained inline address edit and deactivate/reactivate, whose confirmation states how many memberships will end and that reactivating won't restore them. A second view, **Unassigned residents**, shows the count prominently — it is the gap the Secretary works down.

**Not built (stage 3+):** QR issuance/rotation beyond the token created on insert, and household attendance itself (Events stage 3).

## Dispute / Blotter Records

- A **sensitive** module: `secretary` manages (create/edit/mark settled), `punong_barangay` views only, and **everyone else — Staff, Treasurer, residents — gets 403** (residents must never see blotter cases, not even their own party entries). Two tables only (`dispute_records` + `dispute_parties`); no hearing schedules, mediation logs, summons, or settlement documents (out of documented scope).
- **Party model:** a party is EITHER a linked resident (`resident_id`, name from the record) OR a typed non-resident walk-in (`first_name`/`last_name`, `resident_id` null) — blotter cases routinely involve non-residents. Roles are `Complainant | Respondent` (`constants/disputes.js`); a case requires at least one of each. `nature_of_case` is a fixed `Criminal | Civil | Others` (varchar(20)).
- **Routes** (`/api/disputes`, `router.use(authenticate)` then per-route role guards): `GET /` (paginated like resident records — `page/per_page/total/total_pages`; `?search=` across case no / filed_for / party name, `?settled=open|settled|all`, `?nature=`, newest `date_filed` first; each row carries a server-computed `party_summary` "A & B vs. C") and `GET /:id` (full parties) are **Secretary + PB**; `POST /`, `PUT /:id` and `PATCH /:id/settle` are **Secretary-only**. Party-name search is a two-hop: linked parties store no name, so it resolves matching `resident_id`s from `resident_records` first, then `dispute_parties`, then filters cases by `dispute_id.in.(…)`.
- **Atomicity (no supabase-js transactions):** create inserts the case then its parties, deleting the case if the party insert fails (a dispute is never party-less). Edit updates case fields, inserts the new parties, then deletes the old ones by their captured ids — reverting case fields and dropping the new rows on any failure. `barangay_case_no` uniqueness is enforced in the app (friendly 409 pre-check + 23505 backstop); **migration 012 adds an OPTIONAL UNIQUE index** — the module runs without it. Referenced `resident_id`s are existence-checked for a clear error instead of a raw FK violation.
- **UI:** shared `DisputesPage` — Secretary's Blotter tab (`/secretary/blotter`, `canManage`: search + open/settled + nature filters, Record case, detail with Edit and a Settle/Reopen toggle) and the same page read-only on the Punong Barangay's Blotter tab (`/punong-barangay/blotter`, no write actions). The create/edit form has case fields + a repeatable parties section; each party toggles between a **resident picker** (debounced search reusing `/api/resident-records`) and typed non-resident names, with a role selector, and enforces ≥1 complainant/≥1 respondent client-side (server is the real gate).

## Events & Activities

- **Two record kinds in one `events` table**, split by `type` (`constants/events.js`): an **`activity`** is a real timed event (start/end REQUIRED, end after start — "General Assembly, Aug 3 8:00 AM–5:00 PM") and an **`announcement`** is an informational notice with NO required window (start/end/location may be null — "Barangay office closed Monday"). Validation enforces the rules per type: an activity without a schedule is a 400, an announcement without one is fine.
- **Migration 013** (REQUIRED — routes select the new columns) adds `type varchar(20) NOT NULL DEFAULT 'activity'` and `is_archived boolean NOT NULL DEFAULT false`, **drops NOT NULL from `start_datetime`/`end_datetime`/`location`** (they were NOT NULL in Table 5, which made announcements impossible), and adds CHECK backstops mirroring the app rules (valid type; activity ⇒ start+end present; end after start when both present).
- **Auto-hide finished activities is DISPLAY LOGIC ONLY** — a past activity is computed from `end_datetime < now` at query time. `is_archived` is never flipped by time and there is no scheduled job. Status is likewise DERIVED, never stored (`deriveStatus()` adds `status` to every row): announcements are always `posted`; activities are `upcoming | ongoing | past`. **Manual archive is separate** (`PATCH /:id/archive|unarchive`, soft delete only; archived records stay readable in the detail route).
- **Stage 1 implemented** (management CRUD + archive; **Secretary AND Staff both manage** — no PB approval gate, since the activity diagram has the PB and residents as view-only): `/api/events` behind `requireRole('secretary', 'staff')` — `GET /` (paginated like resident records; `?view=active|past|archived|all`, `?type=`, `?search=` across title/description/location), `GET /:id`, `POST /`, `PUT /:id`, `PATCH /:id/archive|unarchive`. **View semantics:** `active` = not archived AND (announcement OR activity not yet finished); `past` = not archived AND activity past its end; `archived` = `is_archived` true. **Ordering:** active puts the soonest activity first (`start_datetime` asc, nulls last) with announcements after, newest first; past is most-recently-finished first; archived/all are newest-created first. UI: shared `EventsPage` on `/secretary/events` and `/staff/events` — list splits Activities and Announcements into separate sections, the create/edit form's fields adapt to the chosen type, and status badges show Upcoming/Ongoing/Past/Posted/Archived.
- **Stage 2 implemented** (read-only viewer for `resident` + `punong_barangay`, no migration, no new validation — it only EXPOSES stage 1 data): `GET /api/events/public[/:id]`. The list and detail handlers were factored into shared `listEvents()` / `getEvent()` helpers that both audiences call with a `publicOnly` flag, so the viewer returns the **same shape and the same derived statuses** as management. `publicOnly` limits `?view=` to `active|past` (archived is not an allowed viewer value), adds a belt-and-braces `is_archived = false` filter, and makes the detail route **404 on an archived record** — archived events are invisible to viewers, not merely hidden. The viewer routes are declared BEFORE the `requireRole('secretary','staff')` gate (the layering document types and rental items use), so those roles have no create/edit/archive path at all; the treasurer is excluded from events entirely. UI: `PublicEventsPage` on `/resident/events` and `/punong-barangay/events` — same Activities/Announcements sectioning, search, type filter and Current-&-upcoming/Past views, reusing the stage 1 display constants, with no write actions anywhere.
- **Stage 3 is complete** (3a household attendance recording, 3b fines for absent households, 3c the resident QR page, 3d QR scanning) — see below. Build order so far: Reporting (done) → GCash gateway (done) → Households stages 1–2 (done) → attendance 3a (done) → 3b fines (done) → 3c resident QR (done) → **3d QR scanning (done)** → pre-deployment security.

### Stage 3 (attendance + fines) — decided design, PARKED

**Decision: Option B — attendance and fines are per HOUSEHOLD, not per resident.** Confirmed by the user with the barangay Secretary: at an assembly **one household signs the sheet once**, and a household with no signature is fined. Households are identified by their **HEAD, not by address** — two households can share an address and are distinguished by head. The barangay keeps this in a logbook + Excel today. Consequently `charges.household_id` (which Table 15 already describes as *"Household responsible (mainly for fines)"*) is the payer link and **no `charges.resident_id` is needed**.

**Agreed build order for this work:** (1) a **Households module** (create household, assign head, add members) → (2) household-based attendance recording at events → (3) fines per absent household through the EXISTING charges system (Treasurer verifies them on the normal payments screen; no parallel payment path).

**Schema investigation findings (live DB, before any code):**
- `event_attendees` originally had only three columns — `event_attendee_id`, `event_id`, `resident_id` (NOT NULL) — with no timestamp, no recorded-by, no present/absent status and no UNIQUE guard. Empty. **Superseded by migration 015**, which repoints it at households (see below).
- `charges` has `event_id` (nullable) ✓ and `household_id` (nullable) ✓, but **no `resident_id`**. All 21 existing charges (DOCUMENT ×11, RENTAL ×10) set `user_id` + their own link; `household_id`/`event_id` are unused so far.
- `events` has **no fine-amount field and nothing marking attendance as required** (columns are event_id, title, description, start/end_datetime, location, date_created, type, is_archived).
- `household_records` and `household_members` exist structurally but are **both empty, with no module anywhere that creates or manages them** — which is why the Households module must come first.
- Only **8 of 47** active residents have a linked user account, which is a further reason fines cannot key off `users`.

**Migration 015 — `event_attendees` repointed at households (WRITTEN, NOT YET APPLIED).** The table contradicted the agreed design by being keyed on `resident_id`. Migration 015 drops that column and adds:
- `household_id bigint NOT NULL` (FK → `household_records`) — the household is the unit that signs and the unit that is fined.
- **UNIQUE `(event_id, household_id)`** — so **"one household, one signature" is enforced by the schema, not by application convention**. It also makes attendance recording idempotent: re-submitting a sheet cannot create a second row for the same household at the same event.
- `recorded_at timestamptz NOT NULL DEFAULT now()` and `recorded_by_user_id bigint NOT NULL` (FK → `users (user_id)`) — **the accountability pair, folded into this migration deliberately so Chapter 3 Table 6 is edited once instead of twice.** Attendance is the evidence base for a *fine*, so a household disputing a charge must be answerable with who recorded them and when; every other money-adjacent table already carries it (`payments.received_by_user_id`, `rental_requests.returned_by_user_id`, `document_requests.processed_by_user_id`). Type and FK target were verified against the live schema to match `payments.received_by_user_id` exactly — but this one is NOT NULL, because a gateway payment legitimately has no staff receiver whereas attendance is always recorded by a person.

There is deliberately **no present/absent status column**: absence is derived as "no row for this household at this event", which the UNIQUE constraint makes reliable, and an explicit absent row would be a second representation of the same fact that could disagree. `attendance_required` / `fine_amount` are **not** in this migration either — they belong on the `events` table in the Stage 3 migration.

The table name, the `event_attendee_id` primary key and the `event_id` FK are deliberately unchanged (renaming would cost another Chapter 3 edit for no functional gain). Safe because the table was verified **empty (0 rows)** and **nothing in `backend/src` or `frontend/src` references it** — the attendance module isn't built. It is self-guarding too: `ADD COLUMN … NOT NULL` without a DEFAULT aborts on a non-empty table. **Chapter 3 TABLE 6 still needs the matching manuscript edit** (the schema doc carries the same note).

### Stage 3a implemented — household attendance recording

**Migration 016 (REQUIRED — `routes/events.js` selects the new columns, so EVERY Events endpoint 500s until it is applied).** Adds `events.attendance_required boolean NOT NULL DEFAULT false` (opt-in per event — most events don't take attendance, a General Assembly does), `events.fine_amount numeric(10,2)` **nullable on purpose** (null ≠ zero: it means attendance is tracked but nothing is chargeable), and a CHECK that `attendance_required` may only be true when `type = 'activity'` — an announcement has no schedule, so "who attended" is meaningless for one.

**The partial unique index on `charges (event_id, household_id)` is for stage 3b** and is deliberately **partial** (`WHERE event_id IS NOT NULL AND household_id IS NOT NULL`). Verified against live data: all 34 existing charges have BOTH columns null, because every charge so far is a DOCUMENT or RENTAL keyed on its own link. PostgreSQL treats NULLs as distinct in a UNIQUE, so a full index would appear to work while guaranteeing nothing for those rows. Restricted to rows where both are present, it means exactly what 3b needs: at most one charge per (event, household), so re-running fine generation can never double-charge.

**ABSENCE IS DERIVED, NEVER STORED.** A household is absent iff there is no `event_attendees` row for it at that event. There is no present/absent status column and must not be one: the derivation is only trustworthy because `UNIQUE (event_id, household_id)` (migration 015) guarantees at most one row per pair, and an explicit absent row would be a second representation of the same fact — free to disagree with the first, and a silent way to fine the wrong household. There is likewise no "which member represented the household": the household signs once, as a unit.

**Attendance deletion is a HARD delete**, unlike household memberships which are only ever ended with `date_ended`. The difference is what the row *means*. A membership row is a historical fact ("they belonged here from X to Y"), so ending it preserves truth. An attendance row is not a fact about a period — it *is* the presence marker, so a soft-deleted one would still make the household look present to every reader that didn't know about the flag, and would make 3b fine the wrong households. Deleting restores exactly the state before the mis-recording.

**Endpoints** (all `secretary` + `staff`, declared after the management gate so residents and the PB get 403):
- `GET /api/events/:id/attendance` — the roster: every ACTIVE household with `head_name`, `address`, `member_count`, and `attendance` (null, or `{ recorded_at, recorded_by_username }`), plus a `summary` of total/recorded/missing. **400 unless the event is an activity with `attendance_required`.** Sorted by head surname then household number, with **headless households LAST rather than hidden** — a household with no head is a data problem the Secretary should see. Sorting and paging happen in Node because the head's name sits behind two joins and can't be ordered on in the query; the summary counts cover ALL active households, not the filtered page, because that ratio is what gets worked down at an assembly.
- `POST /api/events/:id/attendance` — records one household, named by `household_id` (tapping) or `qr_token` (scanning, 3d). **A 23505 unique violation is treated as SUCCESS**, returning when it was first recorded and by whom. Recording twice must be harmless: 3d scans QR codes into this endpoint, where repeat reads are normal and must never look like an error.
- `DELETE /api/events/:id/attendance/:householdId` — undo a mis-recording (hard delete, see above); 404 if no such row.
- Event create/edit accepts `attendance_required` + `fine_amount`; `attendance_required` on an announcement is a 400, and `fine_amount` must be null or > 0 with ≤2 decimals (zero is rejected rather than stored as "free"). **Turning attendance off keeps existing rows** and reports `attendance_kept` so the caller can warn — the roster is evidence and 3b may still need it.

**UI:** the event form gained an "Attendance required" checkbox (activities only; switching to announcement clears it) and a fine field that appears only when checked. The roster is an in-page view of the shared `EventsPage`, reached from an activity's detail — so Secretary and Staff get identical controls with no new route, the same way the module already shares one page. Summary counts are displayed large, each row has "Mark present" or a timestamp + Undo, and the table collapses to stacked blocks with full-width 44px targets under 640px because this is used on a phone at an assembly.

Attendance applies to `activity` records only, never announcements; Secretary + Staff record it, residents and the PB never do.

### Stage 3c implemented — the resident's household QR code

**NO MIGRATION.** `household_qr` has existed since migration 001 and every household has carried an active row since Households stage 1 created one on insert (`crypto.randomUUID()` token).

- **`GET /api/my-household`** (`routes/myHousehold.js`, resident-only) — **the household is derived from the session and nothing else.** There is no `household_id` parameter in the path, query or body, so a resident cannot ask for someone else's code by guessing an id; the route never reads `req.params`/`req.query`/`req.body` at all (asserted by the test). The chain is token → `users.user_id` → `profiles.resident_id` → the one active `household_members` row → `household_qr`.
- **The response carries ONLY what draws the code** — `qr_token` plus `is_head` for wording the caption. No household number, no head name, no address, no member list: a code held up on a phone at an assembly must not double as a roster of who lives where.
- **"No code to show" is never an error.** All four outcomes (`no_resident_record`, `no_membership`, `household_inactive`, `no_qr`) return **HTTP 200** with `has_household: false` and a reason, and the page explains itself instead of rendering an error — a resident who simply isn't in a household is a normal state.
- **UI:** `/resident/household` ("My household" in the resident nav), rendering `qrcode.react` (`QRCodeSVG`, ISC, zero deps) at 256px with a white quiet zone — scanners need the light margin to lock on. There is deliberately **no Secretary-side QR view**: households with no account behind them are handled by the Secretary marking them present by hand, which already works.
- Verified on a real phone: the code at `/resident/household` for `@juan_test_mr4iarwh` scans as household 7's `qr_token`.

### Stage 3d implemented — QR scanning on the attendance roster

**NO MIGRATION.** `qr_token` is `NOT NULL UNIQUE` (migration 001), so a token identifies exactly one household or none at all — which is what makes token-only resolution safe.

- **Scanning is not a second way to RECORD attendance, only a second way to NAME the household.** `POST /api/events/:id/attendance` now takes **either** `household_id` (tapping "Mark present") **or** `qr_token` (scanning) — **exactly one, never both** (400 otherwise) — and both converge on the same insert, so what a scan writes and what a tap writes can never drift apart. No new route was added, so the scan path inherits 3a's Secretary+Staff gate; a test asserts the gate is still declared *before* the route so moving it can't silently expose attendance.
- **The token is the only thing that crosses.** The client sends no household id alongside it and the server would not trust one if it did — the household is whatever `household_qr` says owns that token.
- **An unknown code (404 `qr_unknown`) is told apart from a deactivated one (409 `qr_inactive`)**, because the operator has to do something different in each case. Nothing deactivates a QR yet; the check is there for future rotation.
- Tokens are case-folded and trimmed on the way in. They are minted with `crypto.randomUUID()`, which is always lowercase, so this makes the **typed fallback** forgiving with no risk of folding two distinct tokens together.
- **Every reply names the household** (`head_name` + `address`, resolved through the head's two-hop join): a scanner is pointed at a code, not at a person, so the operator needs the name to check against whoever is in front of them. A household with no head is a data problem, not a reason to refuse a signature — the lookup never fails the recording.
- **Decoder: `jsqr` (1.4.0, Apache-2.0, zero dependencies)** — chosen over the native `BarcodeDetector` API, which Safari/iOS does not implement at all, and over `@zxing/*`/`html5-qrcode`, which are far larger and bring their own UI. One code path that behaves identically on every device beats a fast path plus a fallback path.
- **THE TYPED FALLBACK IS NOT A SECOND-CLASS PATH.** `getUserMedia` requires a **secure context**, so over plain `http://<lan-ip>:5173` on a phone the camera is blocked by the browser outright — the page detects this and says so rather than showing a dead camera. Permission refusal, missing hardware, a camera held by another app and a worn printed code all end at the same always-visible token box. (For a camera demo on a phone, the frontend must be reached over https — e.g. a tunnel — or from localhost.)
- **Repeat reads are absorbed client-side too.** A code sits in front of the lens for seconds; the server treats repeats as a no-op anyway, so the 4s per-token cooldown only stops the request flood — and it is **refreshed while the code stays in view**, so a token is re-sent only after it has left and come back. Decoding pauses while a request is in flight, and `inversionAttempts: 'dontInvert'` halves the per-frame work since the codes are standard dark-on-light.
- **The camera stream is stopped on close and on unmount**, including when the panel is closed while the permission prompt is still open — otherwise the camera indicator stays lit after the scanner is gone.
- **UI:** `components/AttendanceScanner.jsx` (decoding only — the roster owns the request), opened from a full-width "Scan QR code" button directly under the roster counts and above the fines panel, since scanning is what happens *during* an assembly and fines are what happen after it. Staff and Secretary both scan.
- **Camera lifecycle (fixed after a real black-screen bug).** The `<video>` is only rendered once `camState === 'live'`, so the stream **cannot** be attached inside `startCamera()` — `videoRef.current` is still null there, and the original `if (videoRef.current)` guard silently skipped the attach: the camera stayed open (the browser reported "Using now"), the panel rendered, and **nothing ever decoded**. The attach now happens in an effect keyed on `camState`, the first moment the element is committed. Three things make that class of failure self-reporting: `play()` rejections are **surfaced, never swallowed** (a blocked play leaves a stream attached that never renders); a **3s watchdog** (`FRAME_WATCHDOG_MS`) fires if no frame arrives, releases the camera and tells the operator to use the token box; and the live **resolution is displayed** once frames arrive, so working is proven rather than inferred from the absence of an error. Device label/settings go to the console at attach. Diagnostic note for the future: a black rectangle here is `.scan-stage`'s `#0f172a` showing through an unpainted video — a camera genuinely producing black frames would be `#000`.
- **Test: `cd frontend && npm run test:scan`** (no backend required) — 33 assertions mounting the real component in jsdom against a stubbed `getUserMedia`: the stream **is** attached to the element in the DOM and `play()` **is** called, the autoplay attributes, the resolution readout, the watchdog, the surfaced `play()` rejection, the insecure-context and permission-refused paths, the typed fallback, and that the camera is released on close **and** on unmount. Verified to FAIL against the pre-fix component (**15 failed / 18 passed**, including `0 srcObject assignments` and `0 play() calls`), so it is a real regression guard rather than a test that passes either way. It asserts POSITIVE facts — a stream *is* attached, frames *are* reported — because the bug it exists for was a guard quietly skipping the only thing that mattered while nothing threw.
- **Test: `cd backend && npm run scan:test`** — 33 assertions, **no server started**: it invokes the real route handler with a mock req/res, so the handler runs its real queries. Covers token resolution, the accountability fields, re-scan idempotency, typed-fallback tolerance, all four refusal paths (unknown / deactivated / inactive household / malformed) asserting **none of them writes a row**, the one-way-of-naming rule, and a 3a regression pass on the tap path. It creates its own test event and throwaway households and deletes everything it wrote; real households are only ever READ (their tokens are scanned against the *test* event, so no real attendance is touched).

### Stage 3b implemented — fines for absent households

**NO MIGRATION.** The live schema was introspected before any code and everything needed already existed. The deciding question was `charges.user_id`, which turned out to be **nullable** — confirmed twice, from PostgREST's `required` list and by a real insert with `user_id: null` that was accepted and then rolled back. That is what makes household fines possible at all: a fine is owed by a HOUSEHOLD, and most households have no account behind them (8 of 47 active residents had one at last count). `CHARGE_TYPE.FINE` was already in `constants/charges.js`, and migration 016's partial unique index was already applied and verified.

- **Generation is an explicit Secretary action** — never a timer, never triggered by the event ending, never a side effect of recording attendance. Money must not appear on a household's record because a clock ticked over. **Fines are Secretary-only**, unlike attendance recording which Staff also do: marking a roster and raising a charge are different kinds of act (Staff, Treasurer, PB and residents all get 403 on every fine route).
- **A fine is an ordinary `charges` row** (`charge_type = 'FINE'`, linked by `event_id` + `household_id`, `user_id` = the head's account when they have one, else null). It lands on the Treasurer's existing Payments queue and is verified exactly like a document or rental fee — no parallel payment path, and nothing in the charges/payments model changed.
- **Endpoints** (`routes/events.js`, after the attendance section): `GET /api/events/:id/fines` — preview that **creates nothing** and reports `can_generate` + `blocked_reason` rather than erroring, because a Secretary facing a refusal needs to know what to fix; `POST /api/events/:id/fines` — raise them; `POST /api/events/:id/fines/:householdId/void` — cancel one.
- **Generation guards:** the event must be an activity with `attendance_required`, not archived, with a `fine_amount > 0` (null means attendance is tracked but nothing is chargeable), and **it must have ENDED** — you cannot fine people for missing an assembly still in progress.
- **A household registered AFTER the event ended is never fined.** It could not have attended, so charging it would be simply wrong. Reported separately in the summary as `registered_after`.
- **Safe to re-run.** The partial unique index `charges_event_household_unique` means at most one charge per (event, household), so a second run cannot double-charge. The route pre-filters against charges already on file so it can report accurately, and treats a 23505 from a concurrent run as "already fined" rather than an error. Inserts are chunked at 200 with a per-row fallback on collision, so one clash cannot lose the rest of the batch. Neither query uses `.in()` on a household id list — at barangay scale that list runs to four figures and would not survive being serialised into a PostgREST query string (same reason as `GET /unassigned-residents`).
- **VOIDING IS MANUAL, ALWAYS — recording attendance NEVER touches a charge.** Money must not move as a side effect of an attendance edit. The reason is the unique index: because it covers `(event_id, household_id)` whatever the status, **a void is PERMANENT for that event** — no replacement charge can ever be raised for that pair. An automatic void would therefore let a single mis-tapped "Mark present" destroy a chargeable fine for good, and undoing the attendance would not bring it back. Manual voiding puts a deliberate click in front of an irreversible act. (An earlier draft auto-voided on late attendance; that was rejected for exactly this reason.)
- **A disagreement surfaces as a MISMATCH instead.** A household marked present that still holds a **live (non-VOID) fine** — `UNPAID` *or* `PAID` — gets `state: 'mismatch'` in the preview, is counted separately in the summary (never folded into another bucket), is flagged on its own roster row, and is listed in a warning on the fines panel with a direct Void button. The **PAID** case matters most: it has no automatic remedy at all, so it must be visible. Voiding it is still refused (409) — money received is a record and refunds happen at the Barangay Office — so the warning says so rather than offering a button that would fail.
- **PAID fines cannot be voided** (409), whether reached from the mismatch warning or the fine list.
- **UI:** a Secretary-only **Fines panel** inside the existing attendance roster — it states who would be charged and how much *before* the button is pressed, explains itself when generation is blocked instead of hiding, lists the raised fines with their status and a Void action, and shows the mismatch warning described above. Mismatched households are also badged "Fine outstanding" on their roster row, so the clash is visible where the attendance edit was made and not only in the panel. Every void is confirm-guarded and states that it cannot be undone. Staff see the roster exactly as before with no fines panel at all. `PaymentsPage` renders FINE charges by naming the household head (falling back to the household number) and "Missed <activity>" with the household address, since a fine has no document or rental behind it and often no payer account either; `routes/charges.js` embeds `events` + `household_records` and resolves the head's name in one extra query (it sits two joins away and cannot be embedded with a "current head only" filter).
- **Test: `cd backend && npm run fines:test`** (backend must be running) — 64 assertions covering the role matrix on all three routes, the read-only preview, every generation guard, generation itself, re-run safety plus a direct DB-level duplicate attempt, voiding (including the PAID refusal), the manual-void policy (late attendance leaves the fine **UNTOUCHED** and raises a mismatch that only a deliberate void clears, with the PAID-and-present case asserted separately), and the fine arriving on the Treasurer's queue and being paid end to end. It creates its own test event and households and **deletes everything it wrote**, asserting the cleanup; the barangay's real event and attendance are only ever read.

## Reporting

- **Read-only aggregation over existing data** — no new schema, no migration, no writes anywhere in `routes/reports.js`. Roles per Chapter 3: **administrative** reports (`/document-requests`, `/residents`, `/facility-utilization`) are `secretary` + `punong_barangay`; the **financial** report (`/collections`) is `treasurer` + `punong_barangay`. The **PB sees both sets** (oversight); Staff and residents get 403 on every report.
- **Default date range: the last 12 months** — the first day of the month 11 months ago through today, so the series always shows 12 labelled buckets. `?from=&to=` override it. Ranges are **capped at 10 years and REJECTED (400) beyond that** rather than silently truncated, which would leave the monthly chart disagreeing with the headline totals.
- **Aggregation strategy:** PostgREST has no `GROUP BY`/`SUM` without a database function, and this module was scoped as no-migration. So plain totals use `count: 'exact', head: true` (computed in the DB, zero rows transferred) and grouped aggregates run **one narrowly-projected query per report**, bucketed in Node — one round trip beats dozens, and the projection keeps the payload small. If volume ever outgrows this, the fix is SQL aggregate functions in a migration (the pattern migration 003 already uses).
- **Data notes:** `rental_requests` has no created-at column, so facility utilization is keyed on `start_datetime` (the date the item was actually used — the meaningful axis anyway), and cancelled bookings are excluded from usage counts. Resident `sex`/`civil_status` are almost entirely null in the current data, so those breakdowns bucket nulls as **"Not specified"** rather than dropping them. Resident population totals are point-in-time and deliberately NOT date-filtered; only new registrations respect the range.
- **CSV export:** `?format=csv` on the **same endpoint** (one convention everywhere), so role checks and the date range apply identically to JSON and CSV. Sends `text/csv` + `Content-Disposition: attachment` with a `<report>-<from>-to-<to>.csv` filename, a UTF-8 BOM so Excel renders the peso sign, and a barangay/period/generated header block above the sections.
- **PDF export: client-side, `html2canvas` + `jsPDF`** — chosen so the recharts SVGs appear exactly as rendered on screen (a server-side rebuild would mean re-implementing every chart). `utils/exportPdf.js` captures the report node at 2× scale, draws an A4 header (barangay name, report title, period covered, generated timestamp) and a page-numbered footer, and **slices across pages at `data-pdf-block` boundaries so a chart is never cut in half**.
- **UI:** shared `ReportsPage` on `/secretary/reports`, `/treasurer/reports`, `/punong-barangay/reports` — a report picker (grouped Administrative/Financial, filtered to the role), from/to date controls, headline stat tiles, recharts line/bar charts, and a plain table of the same numbers underneath so they are checkable. Loading, error, and empty ("No data for this period") states are all handled — an empty range renders the empty state, never a broken chart.
- **Render test:** `cd frontend && npm run test:reports` (needs the backend on :5000). The API tests never mounted the components, which is how a payload from one report reached another report's renderer and blanked the screen in the browser while every API test passed. This bundles the real components with the project's own bundler and server-renders each against LIVE data, plus mounts the `ErrorBoundary` in jsdom — **React error boundaries do not catch during SSR**, so boundary behaviour is only verifiable with a client mount. Cross-report payloads are asserted to throw, as a regression guard. **Limit of what it covers:** the per-report checks server-render, so duplicate-key bugs are structurally invisible to them — React validates keys only in the client reconciler (see `25fe20b` under Frontend Layout).

## GCash Payment Gateway (PayMongo) — implemented

- **Flow: Checkout Sessions** (decided over Sources and Payment Intents) — PayMongo hosts the payment page, so **no payment details ever touch BrgyServe**: one call out, one webhook back. Test mode; keys in `backend/.env` (gitignored, placeholders in `.env.example`), read via `process.env`. **`PAYMONGO_SECRET_KEY` is server-only** — never logged, never sent to the frontend; the browser only ever receives a `checkout_url`.
- **The manual flow is UNCHANGED and remains the fallback.** Cash onsite and the resident-declared GCash reference verified by the Treasurer work exactly as before. A gateway payment produces the *same kind of* `payments` row, so it lands on the Treasurer's normal screen; the only difference is `received_by_user_id` staying **NULL** (Table 16 already described this as "null for online automated payments"), which is the discriminator between a staff-verified and an automated payment. Nothing in the charges/payments model was reworked.
- **Migration 014** adds `charges.paymongo_session_id` and `charges.paymongo_payment_id`, both nullable and **both UNIQUE**. Charges paid at the hall never acquire either.
- **Routes** (`routes/payments.js`, client in `services/paymongo.js`): `POST /api/payments/gcash/checkout` (owner-only — a charge belonging to someone else 404s, not 403; rejects PAID/VOID/zero-amount; **resumes an in-flight session** instead of opening a second one), `GET /gcash/status/:chargeId` (owner-only, what the return page polls — **local read only, it never contacts PayMongo**), `POST /gcash/recheck/:chargeId` (owner-only, the resident's own re-check — see trigger 4 below), `POST /gcash/reconcile/:chargeId` (`treasurer` + `secretary`), and the unauthenticated webhook.
- **Amounts are in CENTAVOS.** Every peso↔centavo conversion goes through `toCentavos`/`toPesos` in one place so a ×100 error cannot creep in. Verified live: a ₱200 charge produced a PayMongo intent of `amount: 20000`.
- **Webhook security — the signature IS the authentication** (PayMongo cannot log in, so an unverified endpoint would let anyone mark charges paid for free). Header `Paymongo-Signature: t=…,te=…,li=…`; HMAC-SHA256 over `` `${t}.${rawBody}` `` keyed with the **webhook's own `secret_key`** (`PAYMONGO_WEBHOOK_SECRET`), NOT `PAYMONGO_SECRET_KEY`. Two hardenings PayMongo's own SDK lacks: `crypto.timingSafeEqual` and a 300s timestamp window against replay. Test-mode keys also refuse `livemode: true` events. The route is mounted in `server.js` with `express.raw()` **BEFORE the global `express.json()`** — the HMAC covers the exact bytes sent, so a parsed-and-reserialised body would fail verification on every genuine call.
- **Idempotency, three layers:** (1) early no-op when this exact PayMongo payment is already recorded; (2) the status-guarded claim `UPDATE … WHERE status = 'UNPAID'` — the same pattern manual verification uses, so concurrent deliveries serialise; (3) `UNIQUE(paymongo_payment_id)` as the database backstop, turning any duplicate that slips past (2) into a 23505 treated as "already recorded". A charge the Treasurer already settled manually is **never** double-recorded. The charge is resolved from the session's `metadata.charge_id`, not from a stored session id, so a late callback for an abandoned-then-recreated checkout still lands correctly.
- **FOUR triggers can settle a charge, all funnelling through ONE function (`settlePaidCharge`)** — that single funnel is the design point: every trigger inherits the same idempotency, so adding one can never create a second way to double-record. Adding the fourth (`c95fd4e`) required no change to the funnel at all, which is the argument for it.
  1. **The signature-verified webhook** — automatic, and the primary path.
  2. **Treasurer reconciliation** — manual recovery, because PayMongo auto-disables endpoints and never replays missed events.
  3. **The checkout-resume interlock** — if a resident starts checkout again on a charge whose stored session PayMongo reports as already paid, the charge is settled there. This exists to prevent a **double payment**: without it the resident would be handed a fresh checkout page for money PayMongo has already collected. Settling (rather than merely refusing) avoids knowingly holding a charge UNPAID after the server has just proven it paid. It is opportunistic — it only fires if the resident clicks again — so it supplements reconciliation rather than replacing it.
  4. **The resident's own re-check** (`POST /gcash/recheck/:chargeId`, `c95fd4e`) — the self-service version of (2), for the resident whose webhook never arrived. Before it, `GET /gcash/status` re-read the local `charges` row and nothing else, so "Check again" could only ever repeat UNPAID however many times it was pressed. **What makes it different from the other three:** it is **owner-scoped** (`charge.user_id !== req.user.user_id` ⇒ **404, not 403**, so charge ids cannot be probed); it **cannot open a checkout session**, only ask about one that already exists, which makes it strictly narrower than (3), the path that already let an owning resident trigger a settlement; a charge with no `paymongo_session_id` is a **409**, not a silent no-op that would read as "GCash says you have not paid"; and it **reuses `RESUME_MESSAGES`** rather than adding a third map, so `gateway:test`'s coverage assertions already govern its wording. It is deliberately NOT the reconcile route with its role guard relaxed — **that one has no ownership check at all**, which is exactly why it stays `treasurer` + `secretary`.
- **Outcome wording is pinned, not incidental.** `SETTLE_OUTCOME` names every outcome in one place, and `RESUME_MESSAGES` / `RECONCILE_MESSAGES` must cover all of them. This followed a real bug found in manual browser testing: the resume path ignored `settlePaidCharge`'s return value and always answered "This charge has already been paid" — including for `underpaid` and `void`, where the money was NOT applied. Telling a resident they have paid when they have not is the worst failure this module can produce. `npm run gateway:test` (backend) enforces it: every outcome has wording in both maps, unsettled outcomes never claim payment succeeded and always point the resident to the Barangay Office, and no raw outcome literal escapes `SETTLE_OUTCOME`. It makes no network calls and does not need the API running.
- **Reconciliation is part of the module, not optional.** PayMongo auto-disables an endpoint after 12 failed retries on each of 3 consecutive events and **never replays what was missed**, so a tunnel/server outage could otherwise strand a genuinely paid charge as UNPAID forever. "Re-check with PayMongo" on the Payments screen re-reads the checkout session and settles through the *same* `settlePaidCharge()` the webhook uses — so it can never double-record.
- **The redirect is NOT proof of payment.** `PaymentResultPage` (`/resident/payment-result`) reads the charge's real status back from the API and polls until the webhook lands; if confirmation never arrives it tells the resident **not to pay again** and to show their GCash receipt to the Treasurer. Residents see three clearly distinguished options: **"Pay online via GCash"** (gateway), "Pay onsite", and **"I already paid via GCash"** (the unchanged manual reference flow).
- **The two buttons on that page do different things, deliberately.** "Check again" re-reads our own record (the local poll, right while the webhook is seconds away); **"Ask GCash directly"** is trigger 4 and names the system it queries so the two are tellable apart by someone who has paid and is worried. It locks for **10 seconds** after each press — an outbound PayMongo call per click, and **there is no server-side rate limiting anywhere in `server.js`**, so the cooldown is client-side only and is not a security control.
- **The billing prefill sends the phone as BARE NATIONAL DIGITS** — `9171234567`, no country code and no leading zero — because PayMongo renders **"+63" as a fixed label beside the input**, and their own placeholder in that field reads `917 123 4567`. `toNationalMobileDigits()` in `routes/payments.js` normalises the stored `09XXXXXXXXX` on the way out; an unparseable number returns null and the field is **omitted rather than sent malformed**, the same rule already used for a number that is absent (42 of 47 residents have none). **Verified by screenshot of the hosted page on 18 Aug 2026, and this describes their CURRENT UI, not a documented contract** — the field has now changed behaviour twice, so re-check the rendered page rather than this note if the prefill ever looks wrong again. See also the E.164 attempt under Decided Against.
- **Verified end to end against the live sandbox** (27/28 + 9 authorisation + 8 signature checks, plus a full manual browser run-through): a real test GCash payment → PAID charge with one `payments` row (`gcash`, reference = the `pay_…` id, `received_by_user_id` NULL) visible on the Treasurer's screen; duplicate webhook delivery → `already_recorded`, still one row; Treasurer-settled-first → no second row, manual record kept; webhook disabled → charge stranded UNPAID → reconcile recovers it, and reconciling twice is a no-op. Forged, tampered, replayed and stale-signature requests are all rejected. **Known PayMongo sandbox defect:** their "Fail Test Payment" endpoint (`/sources/{id}/fail`) returns HTTP 500 for GCash sources — their bug, not ours; the resulting state is still correct (source stays `pending`, charge stays UNPAID, no `payments` row), which is also what an abandoned checkout produces. On PayMongo's hosted test page the button to click is **"Authorize Test Payment"**; avoid "Fail Test Payment" because of that defect.
- **Trigger 4 verified in the browser, 18 Aug 2026** (`c95fd4e`): the **409** on a charge with no checkout session; the reached-PayMongo wording on an abandoned session — which is the proof the route really leaves the server, since the local poll cannot produce that sentence; the **10s cooldown** locking the button between presses; and the **`recorded` path settling a real sandbox payment**, leaving **one** `payments` row on the Treasurer's screen. That last one is the assertion that matters: a second row would have meant the funnel's idempotency did not hold from the new entry point.

### Dev tunnel (webhook reachability) — HISTORICAL, DO NOT RUN

**NEVER run `npm run tunnel` again — it breaks payments on the live system.** There is only ever ONE PayMongo webhook, and it is now registered against the deployed Render origin (`https://brgyserve-api.onrender.com`). `npm run tunnel` repoints *that* webhook at a fresh temporary cloudflared hostname, which stops existing the moment the terminal closes. PayMongo would then deliver every GCash payment into nothing and charges would silently stop settling — with no error anywhere to show for it, because a webhook that is never delivered looks exactly like a resident who abandoned checkout. (Reconciliation could recover them one at a time, but only once somebody noticed.)

**`npm run tunnel:sync -- https://brgyserve-api.onrender.com` is the safe command**, and the fix if the webhook is ever found pointing somewhere else. It takes the **base origin** (the script appends `/api/payments/gcash/webhook` itself), updates the webhook in place, and is **idempotent** — given the url it already holds it reports "already points at this url" and changes nothing. `PAYMONGO_WEBHOOK_SECRET` survives the update unchanged, so no redeploy follows.

The rest of this section is kept as the record of how webhook delivery worked during development; the mechanics still explain why there is exactly one permanent webhook.

- Webhooks need a public HTTPS URL but dev runs on `localhost:5000`. **cloudflared quick tunnels** (`winget install --id Cloudflare.cloudflared`) — free, no account, clean install. ngrok was rejected: Windows Defender flags its download.
- **PayMongo validates the URL when it is registered** (a placeholder is rejected with `url could not be resolved`), and quick tunnels hand out a new random hostname per start — but `PUT /v1/webhooks/{id}` can change a webhook's url in place. **Verified empirically: the `secret_key` SURVIVES the PUT unchanged and is also readable from `GET`.** So there is exactly ONE webhook, forever; each tunnel start just repoints it, and `PAYMONGO_WEBHOOK_SECRET` never changes (no API restart needed). This matters because PayMongo can only *disable* webhooks, never delete them.
- `npm run tunnel` (backend) starts cloudflared, reads the hostname from its metrics server at `/quicktunnel`, waits for the hostname to actually resolve before registering (a fresh one is not immediately live), repoints the webhook, and **re-enables it if PayMongo had auto-disabled it**. It **adopts an already-running cloudflared** rather than starting a second one — which is also the fallback if spawning one fails. `npm run tunnel:sync <url>` repoints without a tunnel. `PUBLIC_BASE_URL`, `PAYMONGO_WEBHOOK_ID` and `PAYMONGO_WEBHOOK_SECRET` are written to `.env` automatically; no hostname is ever hardcoded.
- **This was dev scaffolding, and it has been dropped.** Cloudflare states quick tunnels are testing-only (no uptime guarantee). That step is done: `PUBLIC_BASE_URL` is the Render origin, `tunnel:sync` was run against it, and the tunnel is out of the workflow for good — see the warning at the top of this section.

## Notifications

**NO MIGRATION.** `notifications` (Table 17) has existed since migration 001; it was empty and nothing read or wrote it. `status` is `varchar(50)` with no CHECK, so the extended vocabulary needed no schema change — only the Table 17 doc edit, which is done.

- **Nothing is sent. `SMS_MODE` defaults to `SIMULATED`** (unset behaves as SIMULATED, so a missing value can never send anything) — messages are composed, addressed and recorded, and stop there. No provider, no API key, no HTTP call anywhere in the codebase.
- **`SIMULATED` is its own status, never `SENT`.** Recording SENT for a message nobody sent would make the log assert something untrue, which is the whole point of choosing this over a half-finished real integration. `sent_at` stays NULL for the same reason — "when it was sent" has no honest answer. The screen states plainly that sending is simulated.
- **`SKIPPED` rows are written when there is no contact number** (43 of 47 active residents). The row is kept rather than dropped: `destination` is NOT NULL so it stores an empty string, the status carries the reason, and the screen's "No contact number" count becomes the barangay's list of residents it cannot reach — the argument for collecting numbers.
- **The provider seam is one function body.** `PROVIDERS` in `services/notifications.js` maps mode → adapter; `SIMULATED` is implemented, `SEMAPHORE` is a documented placeholder that returns FAILED without making a request. Going live is: write that body, set `SMS_MODE=SEMAPHORE`. No call site, route or screen changes.
- **FAILURE ISOLATION — `notify()` and `notifyMany()` NEVER throw.** Their whole bodies are wrapped and they return `{ ok, status }`. Every call site runs *after* its business write is committed, so a notification problem cannot roll back an approval, a rejection, a payment or a fine. `notifyMany()` batches fine generation into ONE insert — an assembly can cover every household and must not become a write each.
- **Phone number source of truth: `resident_records.contact_number` wins — with ONE documented exception.** `profiles.phone_number` is what the resident *claimed* at registration; the record is what the barangay maintains, and eight of the nine call sites read it. **The exception is registration rejection**, where the applicant usually has no linked resident record at all — being unmatchable is the commonest reason to reject one — so the claimed number is the only number in existence. That call site reads `profiles.phone_number` **by availability, not by preference**; see Auth & Account Approval. **Bug found and fixed:** `POST /api/secretary/pending-residents/:userId/link` (link to an EXISTING record) silently discarded the claimed number, while the create-and-link path copied it — so linking to a record with no number on file lost the only number the barangay had. `/link` now backfills, but **only into a blank**; a number the Secretary entered is never overwritten. Reported as `contact_backfilled` in the response.
- **Encoding matters and is enforced.** `₱`, `—` and `×` are outside GSM 03.38 and force UCS-2, cutting the segment from 160 characters to 70. Replacing them with `PHP`, `-` and `x` took one round of all ten templates from **18 credits to 10 (44% cheaper)**. A test asserts no template contains those characters, so it cannot regress.
- **Screen:** `/secretary/notifications` (Secretary-only — it exposes contact numbers and message content). Read-only: no re-send, no delete, no POST route. Filters by status and by what the message relates to; summary counts run over the whole log, not the page.
- **Test: `cd backend && npm run notif:test`** — no server, no network, `SMS_MODE` forced to SIMULATED. The centrepiece is failure isolation: the `notifications` table is sabotaged to throw, a real document-request approval is invoked through its actual route handler, and the test asserts the approval still returns **200**, the request is still `approved`, the charge still exists, and no notification row was written (proving the failure was real and not skipped).

## Decided Against — do not revisit

Each of these was investigated, measured, and deliberately left as it is. They are recorded so the same ground is not covered a second time.

- **The payments table overflowing `.table-wrap` below about 1135px.** It is correct at **1280 and 1920, so no demo resolution is affected**, and `.table-wrap { overflow-x: auto }` already provides the scroll. Hiding columns was rejected on domain grounds: **"Declared payment" is precisely what the Treasurer checks against GCash** before verifying, so hiding it would make the screen useless for its main task. Shortening the button labels was **measured impossible** — with every button removed the Actions column still measures exactly 200px, its `.row-actions` floor, so that approach can recover at most 27.7px against a 91px gap at 1024.
- **Row dividers not painting under the action column.** Diagnosed by rasterising the rendered page: a `display: flex` `<td>` is not stretched to its row's full height, and **the shortfall varies with row content**, so no single shadow offset can cover it. Both remaining fixes change table-cell display app-wide — a blast radius out of all proportion to a cosmetic divider.
- **E.164 for the PayMongo billing phone.** Sending `+639171234567` rendered on their hosted page as **`+63  +639171234567`** — composing to `+63639171234567`, worse than the bug it replaced (a stored `09171234567` showing as `+63 09171234567`, one digit too many). Their `+63` is a **fixed label beside the input**, so the field must carry the bare national number only.
